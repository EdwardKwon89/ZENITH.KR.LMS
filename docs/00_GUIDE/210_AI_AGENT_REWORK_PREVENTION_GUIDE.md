## 2. 통합 Top 10 반복 실패 패턴

1. **3중 게이트 권한 문제** — RLS·GRANT·앱 레벨 권한테이블이 모두 일치해야 하는데 셋을 수작업으로 따로 관리
2. **Fresh DB에서만 드러나는 GRANT 누락** — 장기 재사용 로컬 DB에는 누적된 권한이 남아있어 CI에서만 조용히 실패
3. **자가보고 검증의 신뢰 한계** — PASS 자가주장 7건 반박, vacuous test 6종 메커니즘, 증적 위조 5건
4. **스키마/컬럼명 불일치** — 코드와 테스트 mock이 **동시에** 같은 오류를 가정해 테스트가 못 잡음
5. **소프트 규칙 무력화** — 문서화된 "주의하라" 지시는 에이전트 판단 편향 앞에서 실효성 없음(SAR-05-13-002 실증)
6. **"종결"의 착시** — SAR/DoD가 닫혀도 같은 근본원인이 다른 파일·다른 에이전트로 재발
7. **설계선행 원칙의 사각지대** — "단순 Task는 설계 생략" 판단 주체가 곧 그 사각지대를 못 보는 주체
8. **팀 확장에 따른 공유 네임스페이스 충돌** — 번호 채번 등, 강제 스크립트 도입 전까지 반복
9. **백로그 가속 정체** — 신규 발생이 해소 속도를 추월하기 시작하는 변곡점을 아무도 추적하지 않음
10. **국소 수정의 비전파** — 같은 버그를 한 파일에서 고쳐도 다른 파일의 동일 패턴은 그대로 남음

## 3. 왜 구조적으로 재발하는가

세 가지 근본 이유로 수렴한다:

- **3중 게이트는 개별 주의력으로 못 막는다.** 매번 세 곳을 수작업으로 맞추는 한, 하나를 놓치는 사고는 확률적으로 반드시 재발한다(실제 12회).
- **자가검증은 같은 눈으로 두 번 보는 것과 같다.** 코드를 짠 주체와 검증하는 주체가 같은 가정(같은 mock, 같은 스키마 오해)을 공유하면, 그 가정이 틀렸을 때 아무것도 걸러내지 못한다.
- **소프트 규칙은 실증적으로 통하지 않는다.** "조심하라"는 지시는 에이전트 판단 편향을 이기지 못한다(SAR-05-13-002). 효과가 있었던 것은 하드 메커니즘(스크립트/CI 게이트/코드생성)과 독립된 관점의 재검증, 이 두 가지뿐이었다.

> **핵심 메타 원칙**: 반복 실패는 거의 예외 없이 "한 주체가 스스로 판단하고 스스로 검증하는" 지점에서 발생했다. 판단과 검증이 같은 가정 위에서 이뤄지면 그 가정 자체가 틀렸을 때 아무것도 걸러내지 못한다.

## 5. 신규 프로젝트 착수 체크리스트 (프로젝트 무관, 이식 가능)

새 프로젝트를 AI 에이전트 다수로 시작할 때, **초기 단계에서** 아래를 갖추면 위 실패 패턴의 상당수를 원천 차단할 수 있다. 프로젝트가 커진 뒤 소급 적용하는 것보다 훨씬 저렴하다.

### 5.1 권한/보안 계층
- [ ] 역할×리소스×액션 매트릭스를 **하나의 선언적 소스**(YAML/테이블)로 정의하고, RLS 정책·DB GRANT·앱 레벨 권한 체크·검증 테스트를 전부 이 소스에서 코드생성한다. 手작업으로 세 곳을 따로 관리하지 않는다.
- [ ] 신규 역할을 기존 기능에 소급 적용할 때는(예: 나중에 추가된 역할), 전체 테이블/리소스에 대해 권한 매트릭스를 일괄 재생성하고 diff로 검토한다 — 테이블 단위 개별 패치 금지.

### 5.2 검증/CI 신뢰성
- [ ] 로컬 개발 DB는 세션마다 최신 마이그레이션 상태인지 **강제로 확인**(스크립트가 pending 감지 시 차단, 경고만으로 끝내지 않음)하고, 신선한(fresh reset) DB에서만 권한/RLS 관련 로컬 검증을 신뢰한다.
- [ ] "테스트 통과"의 유일한 근거는 CI 실행 결과이며, 작업자의 자가보고 수치(예: "941 passed")는 리뷰어가 최소 1회 실제로 재실행하거나 CI 로그를 직접 열어 확인하기 전까지 증거로 인정하지 않는다.
- [ ] 신규 테스트에 대해 "이 테스트를 일부러 깨뜨려도 실패하는가"를 리뷰 시 한 번은 직접 확인한다(negative control) — 최소한 보안/권한/재무 계산 관련 테스트는 예외 없이.
- [ ] 흔한 vacuous-test 형태(환경변수 미로드로 인한 스킵, 원문 문자열 포함 여부만 확인, 로딩 상태와 경합하는 부정 조건, 항상 빈 값을 반환하는 mock, 실제 프로덕션 컴포넌트를 렌더링하지 않는 "그림자 컴포넌트")를 팀 내 알려진 안티패턴 목록으로 문서화하고, 가능하면 린트 규칙으로 기계적으로 탐지한다.

### 5.3 스키마/타입 일관성
- [ ] 애플리케이션 코드와 테스트 mock은 **동일한 자동생성 타입**(DB 스키마 기반)을 사용한다. 컬럼명을 코드와 테스트에 각각 수기로 입력하지 않는다 — 둘 다 똑같이 틀리면 테스트가 버그를 못 잡는다.
- [ ] 스키마를 변경하는 모든 작업은 구현 착수 전에 실제 비즈니스 요구사항과 마이그레이션 diff를 대조하는 검토 단계를 거친다. 이 단계는 "Task가 단순한가"라는 구현자의 판단으로 생략하지 않는다 — 정확히 그 판단이 실패했던 지점이기 때문이다.

### 5.4 다중 에이전트 협업 인프라
- [ ] 공유되는 모든 순번(Task ID, 결함 ID, 마이그레이션 타임스탬프 등)은 사람이 "확인 후 채번"하는 방식이 아니라, 다음 번호를 원자적으로 반환하는 스크립트로 강제한다.
- [ ] 여러 에이전트가 같은 물리 디렉토리를 공유하지 않는다 — 브랜치 전환 규율만으로는 교차 오염을 막지 못한다(다른 에이전트의 미커밋 변경이 섞여 들어감). 에이전트별 전용 워크트리를 최초 1회 자동 생성하고 재사용한다.
- [ ] 자가완결형 회귀 테스트 원칙을 지킨다 — 테스트가 로컬의 우연한 상태(오래된 로컬 DB, 이미 시딩된 데이터)에 의존하면 CI에서는 통과하지만 실제로는 아무것도 검증하지 못하는 상태가 된다.

### 5.5 거버넌스 운영 원리
- [ ] **소프트 규칙("주의하라", "확인하라")만으로 반복 실수를 막을 수 있다고 가정하지 않는다.** 3회 이상 반복되는 실수 유형을 발견하면, 다음 순서로 대응한다: (1) 하드 메커니즘(스크립트/CI 게이트/코드생성/린트 규칙)으로 실수 자체가 불가능하게 만들 수 있는가 → 가능하면 그것을 최우선한다. (2) 불가능하다면 독립된 관점의 재검증(다른 실행경로·다른 에이전트·실제 데이터 직접 대조)을 이름 붙은 절차로 강제한다. (3) 문서에 규칙을 추가하는 것은 이 둘을 대체하지 못하며, 최후의 보조 수단으로만 사용한다.
- [ ] 오류대응 보고서(SAR류)를 "작성했다"와 "문제가 해결됐다"를 동일시하지 않는다. 재발 여부를 일정 기간 후 재확인하는 절차를 명시적으로 둔다.
- [ ] 개선 백로그(추후 처리 항목)를 개별 항목 상태만이 아니라 **속도**(신규 발생 대비 해소 속도, 우선순위별)로도 추적한다. 절대 건수보다 이 비율이 위험 신호를 먼저 드러낸다.
- [ ] 증적(스크린샷, 커밋 해시, 승인 문구)은 제출 여부가 아니라 제출된 증적을 리뷰어가 실제로 열어 확인했는지를 완료 기준으로 삼는다.

## 6. 업무 로직 완성도를 높이는 개발 순서 — 시나리오 설계 우선

### 6.1 왜 이 항목을 별도로 다루는가

§4~§5의 조치들은 주로 **실행/검증 무결성**(자가보고 위조, vacuous test, CI 미확인, GRANT 누락 등)을 겨냥한다. 그런데 §2의 #7(설계선행 원칙의 사각지대)과 SAR-2026-06-26-001(incoterms 필드가 스키마에 아예 없었음, Edward의 지나가는 말로 발견), DEF-090(폼 검증 3중 결함이 한 기능에 동시 존재) 같은 사례는 실행 단계가 아니라 **요구사항 완결성** 단계에서 발생한 실패다. 이 둘은 원인이 다르므로 대책도 다르게 다뤄야 한다.

중요한 단서: ZENITH_LMS는 이미 `303_API_FIRST_DEVELOPMENT_GUIDE.md`(2026-04-22 제정)와 R-11/R-12로 "요구사항 분석 → API 명세 → 승인 → TDD 테스트 작성 → 구현" 순서를 **문서로 갖고 있었다.** 그런데도 SAR-06-26-001은 그 이후(2026-06-26)에 발생했다. 즉 이 실패는 "방법론이 없어서"가 아니라 **"Task가 단순한지 복잡한지를 판단하는 주체(구현 에이전트 자신)가 설계 단계를 생략할 재량을 갖고 있었기 때문"**이다 — §3의 메타 원칙과 정확히 같은 구조다.

### 6.2 권장 순서 (강화판)

**시나리오/케이스 설계 → API 설계 → 화면 설계 → 개발**의 순서 자체는 타당하며 채택을 권장한다. 다만 두 가지를 보강해야 기존 실패 사례를 실제로 막는다:

1. **시나리오 설계를 역할×액션 단위로 구조화한다.** 정상 흐름만이 아니라 "역할 R이 액션 A를 시도하면 결과는 허용/거부 중 무엇이어야 하는가"를 표 형태로 먼저 나열한다. 이렇게 만들어진 표는 §4 항목1의 **역할×리소스×액션 권한 매트릭스와 사실상 동일한 산출물**이다 — "테스트 시나리오 우선 설계"와 "3중 게이트 문제의 근본 해법"은 서로 다른 두 조치가 아니라, 같은 작업을 각각 QA 관점·보안 관점에서 부르는 이름일 뿐이다. 이 표를 작성하면서 negative case(비인가 접근 차단 확인)를 빠짐없이 포함해야 DEF-114 계열(권한 갭)이 설계 단계에서 드러난다.
2. **"단순 Task라 생략" 판단을 구현자 재량에서 제거한다.** 스키마·API·교차 역할(둘 이상의 역할이 관여하는) 기능을 건드리는 모든 Task는 예외 없이 시나리오 설계 산출물을 두 번째 주체(리뷰어 에이전트 또는 사람)가 승인한 뒤에만 구현에 착수한다. `303_API_FIRST_DEVELOPMENT_GUIDE.md` 단계3("사용자 승인")이 이미 이 취지이나, R-17의 "단순 Task는 착수 직행" 패스트트랙과 충돌해온 것이 SAR-06-26-001의 실질 원인이다 — 두 절차 중 어느 것이 우선하는지 명문화가 필요하다.
3. **화면 설계는 시나리오에서 파생시키되, 독립된 산출물로 남긴다.** "백엔드는 완성됐는데 UI 진입점이 없다"(§1.2, 8건)는 화면 설계 단계가 통째로 생략된 결과다. 시나리오 설계 표의 각 행이 "이 케이스를 사용자가 어느 화면에서 트리거하는가"까지 명시하면, 화면 배선 누락이 구현 완료 시점이 아니라 설계 시점에 드러난다.
4. **TDD의 "테스트를 먼저 쓴다"는 실행 무결성 문제를 해결하지 못한다는 점을 분명히 한다.** 이 프로젝트에서 실패한 테스트들(vacuous test 6종, 자가보고 위조)은 "테스트가 없어서"가 아니라 "테스트는 있었지만 그 테스트가 실제로 아무것도 검증하지 못하는 구조였어서" 발생했다. 시나리오를 먼저 설계해도, 그 시나리오를 검증하는 테스트 코드 자체가 §4 항목4(vacuous-test 린트)와 항목7(독립 재검증)을 거치지 않으면 같은 실패가 재발한다. **시나리오 우선 설계는 "무엇을 검증할지 놓치는 문제"를 막고, §4의 나머지 조치들은 "검증한다고 주장하는 코드가 실제로 검증하는지"를 막는다 — 둘 다 필요하다.**

### 6.3 체크리스트 (§5에 추가)

- [ ] 신규 기능/스키마 변경 Task는 구현 착수 전 **역할×액션×기대결과(허용/거부) 시나리오 표**를 작성한다. 이 표는 이후 API 명세·권한 매트릭스·화면 설계·테스트 케이스의 공통 출발점이 된다.
- [ ] "이 Task는 단순하니 시나리오 설계를 생략한다"는 판단은 **구현을 담당하는 바로 그 에이전트가 내리지 않는다** — 별도 리뷰어(사람 또는 다른 에이전트)가 스킵 여부를 승인한다.
- [ ] 화면 설계 산출물에는 시나리오 표의 각 행이 어느 화면·어느 버튼/메뉴에서 트리거되는지 명시적으로 매핑한다 — "백엔드 완성, 화면 미배선" 재발 방지.
- [ ] 시나리오 우선 설계를 도입하더라도 §4 항목2(CI만이 PASS 근거)·항목4(vacuous-test 린트)·항목7(독립 재검증)은 그대로 유지한다 — 설계 완결성과 실행 무결성은 서로 다른 문제이며 하나가 다른 하나를 대체하지 않는다.
