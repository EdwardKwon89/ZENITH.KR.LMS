## 0. 이 문서의 성격과 배경

본 문서는 [305_NEW_PROJECT_BASELINE_GUIDE.md](./305_NEW_PROJECT_BASELINE_GUIDE.md)(Aiden)·[306_NEW_PROJECT_REUSE_REVIEW.md](./306_NEW_PROJECT_REUSE_REVIEW.md)(B_Kai)·[307_NEW_PROJECT_CPO_REVIEW.md](./307_NEW_PROJECT_CPO_REVIEW.md)(Riley)에 대한 **IMP Executor(구현 담당) 관점의 검토 의견서**다.

305(아키텍처/거버넌스)·306(검증/테스트)·307(제품/CPO)은 각각 신뢰할 만한 단일 출처다. 그러나 **이식 판정의 최종 수요자이자 이식 작업의 실제 수행 주체인 구현자의 관점이 빠져 있다.** 본 문서는 305 §1.6 채택 원칙("실제 적용 결과가 검증된 것만 채택")을 기준으로, 307이 제시한 4대 실전 자산을 **코드 실사**로 재검증하고(§1), 307 로드맵의 갭을 보완하며(§2), 구현 관점에서 착수 전 확인이 필요한 추가 사항(§3)·GitNexus(R-20) 활용성 평가(§4)를 제시한다.

**채택 원칙**: 305 §1.6·306 §0과 동일 — "좋아 보이는가"가 아니라 "이 프로젝트에서 실제로 적용해 본 결과가 의미 있었는가"로만 판정한다.

## 1. 307의 4대 실전 자산 판정 — 코드 실사 기반 재검증

307 §2의 4대 자산을 ZENITH_LMS 코드 실사 결과와 대조했다. 결론: **4개 중 2개는 판정 등급을 하향 조정해야 하고, 1개는 "그대로"가 아닌 "리팩토링 포함" 항목으로 재정의해야 한다.**

### 1-1. 자산 A (Server Action 표준) — 판정 동의, 단 305 §2.3 경고와 반드시 결합

| 항목 | 내용 |
|:---|:---|
| 실존 여부 | ✅ `validateUserAction()` — `src/lib/auth/guards.ts:120` 실재 |
| 307 판정 | 그대로 이식 (VERY HIGH) |
| D_Kai 의견 | **동의하되 등급 유지 조건 추가** |

**근거**: "권한 체크·세션 파싱·예외 처리를 단 3줄로 축약"이라는 서술은 과장이다 — `validateUserAction()`이 실존함에도 **AGENCY 역할 누락 사고가 8회 이상 반복**됐다(DEF-114/116/117/DEF-B-002/010/014/017/019, 305 §2.3). 즉 "가드 함수가 있다"는 것 자체가 누락을 방지하지 못한다는 것이 이미 실증된 사실이다.

**권고**: 자산 A 이식 시 305 §2.3의 **"미들웨어 화이트리스트·앱 레벨 권한표·RLS·DB GRANT 4계층 일치"** 경고와 306 §2(A-2)의 **"역할 한정 화면 실브라우저 검증"** 요건을 1:1로 묶어 이식할 것. 가드 함수 단독 복사는 반쪽 이식이다.

### 1-2. 자산 B (i18n 에러코드 분리) — "개선 이식"이 아닌 "미검증 제안"으로 재라벨링

| 항목 | 내용 |
|:---|:---|
| 실존 여부 | ❌ `ERR_AGENCY_REVERSE_MARGIN` 형태의 **에러코드는 코드베이스 어디에도 존재하지 않는다** — 307 문서 내에만 존재 |
| 307 판정 | 패턴 개선 이식 (HIGH) |
| D_Kai 의견 | **305 §1.6 기준 미검증 제안으로 재라벨링** — "반증은 존재, 제안은 미검증" |

**근거**: 실측 결과, 서버 액션 50개 이상이 한글 인라인 문자열을 그대로 반환한다(`error: '오더를 찾을 수 없습니다.'` — `src/app/actions/finance/ups-actual-charges.ts:39`, `settlement.ts:136`, `admin/auth.ts:22` 등 다수). 즉 "서버 인라인 한글 반환"은 실존하는 **반증 사례**이고, "에러코드 분리 아키텍처"는 **이 프로젝트에서 한 번도 적용·검증되지 않은 제안**이다.

**권고**: 자산 B는 "이식" 등급이 아니라 **"신규 프로젝트 최초 구현 설계안"**으로 취급할 것. 다만 반증 근거(한글 인라인 반환으로 인한 다국어 확장 한계, 305 §4.1 DEF-115/061/023)는 명확하므로, 에러코드 스키마(`ERR_*` 코드 네임스페이스·클라이언트 매핑 규칙)를 착수 시점에 새로 정의하는 방향은 지지한다. 이식 대상이 아니라 **신규 설계 대상**이라는 점이 핵심이다.

### 1-3. 자산 C (상태머신 엔진) — "도메인 분리 이식"은 리팩토링 항목이며, 감사 로깅·변형 축이 빠졌다

| 항목 | 내용 |
|:---|:---|
| 실존 여부 | ⚠️ `canChangeStatus()` — `src/lib/logistics/status-machine.ts:46` 실재하나 **`OrderStatus` 13개 물류 전용 enum(`REGISTERED`~`MASTERED`)에 전면 결합**(실측 — 305 v1.12 재검증 결과) |
| 307 판정 | 도메인 분리 이식 (VERY HIGH) |
| D_Kai 의견 | **"그대로 이식" 아님 — "제네릭 상태머신 재설계" 항목. 감사 로깅·변형 축 요건을 함께 명시해야 함** |

**근거 (코드 실사)**:
1. **도메인 분리 미실현**: `TRANSITION_RULES`·`ROLE_PERMISSIONS`가 물류 상태 enum에 하드코딩 — 다른 도메인(결제·결재·티켓)에 쓰려면 열거값·전이맵을 제네릭으로 추출하는 **리팩토링이 선행**되어야 한다. 복사만 하면 물류 도메인 재구현과 같다.
2. **"status_history 자동 감사 로깅"은 307의 부풀린 설명**: `canChangeStatus()` 자체에는 감사 로깅이 없다 — `order_status_history` 기록은 호출부 수동 처리(`src/lib/repositories/order.repository.ts:203`, `src/lib/actions/ups-daily-close.ts`)다. 자산 구성에 포함된 기능이 실제 코드에는 없는 상태이므로, 307의 판정 근거가 부정확하다.
3. **변형 축 누락**: 305 §4.5·304 §4.5가 지적한 대로 현재 `canChangeStatus()`는 역할×상태만 다루고 `transport_mode`(변형 축)가 없다 — DEF-B-031~033 연쇄의 근본 원인 중 하나(.planning/DECISIONS.md #13). 신규 프로젝트라면 **역할×변형×상태전이 트리플 설계로 처음부터 시작**해야 한다.

**권고**: 자산 C는 "도메인 분리 이식 (VERY HIGH)"이 아니라 **"제네릭 상태머신 재설계 (참고 패턴, 재구현 필요)"** 등급이다. 재설계 시 ①제네릭 열거·전이맵 추출 ②감사 로깅 내장(전이 함수가 로깅을 책임) ③변형 축 포함 — 3가지를 착수 스캐폴드에 명세할 것.

### 1-4. 자산 D (UI 아티팩트 승인 워크플로우) — 80% 수치의 근거 미확인, 방법론으로만 남길 것

| 항목 | 내용 |
|:---|:---|
| 실존 여부 | ⚠️ "UI 재작업 80% 이상 감축 실증" — **저장소 어디에도 해당 측정 근거(어느 세션·어느 Task 기준인지)가 없다** |
| 307 판정 | 방법론 이식 (HIGH) |
| D_Kai 의견 | **305 §1.6 기준 미검증 제안. 근거 출처 명시 전까지는 "검토 중 방법론"** |

**권고**: 307 §2.4에 **"80% 감축" 수치의 출처(측정 기간·지표·대조군)**를 명시할 것. 출처 확인 전까지는 306 §6-1과 동일한 논리(실패 이력·주관적 경험은 "제안이 작동한다"는 증거가 아님)로, **신규 프로젝트 첫 스프린트에서 아티팩트 선승인 흐름을 도입하고 재작업 건수를 실제 측정**하는 파일럿 방식만 허용한다.

## 2. 307 §3 통합 로드맵(4단계)에 대한 보완 의견

307의 4단계 로드맵(인프라→거버넌스→코드 스캐폴드→프로세스 표준화)은 합리적인 실행 순서다. 다만 306의 최우선 보완 항목이 반영되지 않아 다음을 추가할 것을 제안한다.

### 2-1. 0단계 — 규모 게이지(Tier) 확정을 추가 (306 C-1)

로드맵 2단계가 "GOV_COMMON R-00~R-20 포팅"을 **전면 적용 전제**로 서술한다. ZENITH_LMS는 다중 에이전트+다중 팀 초대형 전제로 만들어진 체계라, 소규모(1~2인) 프로젝트에 전체 이식 시 관리 비용이 개발 비용을 초과한다(306 §4 C-1).

**제안**: 1단계 이전에 **"규모 게이지 → Tier별 채택 세트 확정"**을 0단계로 추가할 것:

| Tier | 기준 | 로드맵 적용 범위 |
|:---|:---|:---|
| Tier 1 | 1~2인 · 단일 에이전트 | GOV_COMMON 축소판·R-08 회귀·CI만 — 로드맵 3단계 자산 A(단순화)만 |
| Tier 2 | 소수 인원 · 멀티 에이전트 | + ACTIVE_TASK 상태머신·채번·워크트리 — 305 §7.2는 참고안으로만 |
| Tier 3 | 다중 팀 병행(≥2팀) | 305 전면 적용·sync 워크플로우 3종 — 로드맵 전 단계 |

### 2-2. 로드맵 3단계에 테스트 스캐폴드·RBAC 검증 요건을 명시

3단계(코드 스캐폴드)가 "Server Action 응답 규격·상태머신 엔진·ZenUI 컴포넌트"만 나열하고 **테스트 자산 시작점**(306 A-1/A-5 — Playwright 설정 3종 용도 매핑·TestCase 템플릿·빈 LIVE_REGRESSION_TEST_MAP 골격)과 **RBAC 4계층 검증 E2E 케이스**(306 A-2)를 빠뜨렸다. 스캐폴드 단계에서 함께 생성하지 않으면, 검증 체계는 항상 코드보다 늦게 따라붙는 패턴이 반복된다.

### 2-3. 로드맵 2단계에 로컬 DB 신뢰성 모듈 포함 (306 A-3)

`check-db-freshness.sh`(R-08-2, DEF-128 재발 방지) — CI는 `supabase db reset`으로 fresh DB를 보장하지만 로컬 DB는 개인별로 stale해질 수 있어 "로컬 검증 PASS"가 CI와 다른 결과를 낼 수 있다. 로드맵 1단계(인프라 셋업)에 이식할 것.

## 3. 구현 관점 추가 검토 사항

### 3-1. 305 §1.5(도구 실제 연결 확인)는 구현 계획 수립 전에 실측할 것

R-06(Context7)·R-20(GitNexus) 같은 MCP 기반 규칙은 "문서에 규칙을 적어놔도 각 에이전트 실행 환경에 MCP가 실제 연결되어 있는지는 별개"라는 것이 ZENITH_LMS에서 확인됐다(GitHub Issue #987). 신규 프로젝트 착수 시 **참여할 모든 에이전트의 실행 환경(모델/CLI)에서 해당 MCP가 실제 호출 가능한지**를 스캐폴드 이식 전에 실측할 것. 구현자가 가장 먼저 부딪히는 문제다.

### 3-2. R-08-2의 "로컬 검증 = CI 기준과 다를 수 있다" 원칙 이식

GOV_COMMON R-08-2(DEF-128, 2026-07-28 신설) — 자가보고 회귀수치를 증거로 불인정하고 CI 실행 결과만 인정하는 원칙은 그대로 이식 가치가 높다(305 §1.2). 신규 프로젝트 CI 골격(305 §5.2)을 복사할 때, **"로컬 검증 결과 보고"와 "CI 결과"를 구분하는 보고 형식**을 함께 명세할 것 — 이 구분이 없으면 자가보고 PASS가 다시 증거로 둔갑한다.

### 3-3. 워크트리 격리·커밋 해시 삽입은 Tier 2 이상에서 필수

`agent-worktree-init.sh`(공유 디렉토리 교차 오염 방지, Issue #358 — 수기 안내로 3회 재발 후 스크립트로 해결)·`insert-commit-hash.sh`(해시 수기 타이핑 오류 방지)는 멀티 에이전트 환경에서 실증된 모듈이다(305 §7.1). 단일 개발자 프로젝트(Tier 1)에는 불필요 — 306 §4 C-1 게이지와 연동해 채택 여부를 결정할 것.

### 3-4. Seed 멱등성·Rate Limiting·API 감사로그 — 최우선 복사 대상

305 §5.1이 판정한 "그대로 이식" 4건(Seed 멱등 패턴·Rate Limiting·알림 래퍼·외부 API 감사로그)은 도메인 무관 코드로 확인됐다. **이 4건이 4대 자산보다 이식 우선순위가 높다** — 실증되었고(실제 반복 사용) 결합도가 없으므로, 신규 프로젝트 착수 첫 주 안에 복사해 넣을 것.

## 4. GitNexus(R-20) 활용성 평가

305 §1.2는 R-20을 "그대로, 단 사전확인 필수"로 판정했고, 305 §1.5(GitHub Issue #987)는 "문서에 규칙을 적어놔도 각 에이전트 실행 환경에 MCP가 실제 연결되어 있는지는 별개 문제"임을 기록했다. 본 절은 신규 프로젝트에서 GitNexus 도입 여부를 판단하기 위한 **활용성 실측 평가**다.

### 4-1. 실증된 가치 (채택 근거)

| 용도 | 가치 | 실증 사례 |
|:---|:---|:---|
| **교차 심볼 관계 탐색** | ★★★★★ | GOV_COMMON.md R-20 근거 — grep으로 놓친 `canChangeStatus()` 중앙 게이트 존재·UPS 전용/일반 물류 가격엔진 분리 사실을 GitNexus 사용 즉시 발견 (DEF-B-031~033 분석) |
| **편집 전 영향도 분석** (impact) | ★★★★☆ | 공유 코드(RBAC·상태머신 등) 수정 전 호출자·영향 프로세스 파악 — IMP 구현 시 필수 사전 단계 |
| **A→B 경로 추적** (trace) | ★★★★☆ | "어떤 함수가 어떤 함수까지 도달하는가" — grep으론 수 회 홉이 필요한 탐색을 1회 호출로 해결 |
| **커밋 전 영향 스코프** (detect_changes) | ★★★☆☆ | R-17 커밋 전 예상 심볼만 변경됐는지 확인 — 회귀 감시용 |
| **보안 taint 분석** (explain) | ★★☆☆☆ | `--pdg` 인덱스 필요 + 클로저·콜백·프로퍼티 흐름 미추적 — 참고용 |

### 4-2. 제약·실패 사례 (이식 시 반드시 함께 전달할 것)

1. **인덱스 staleness가 최대 실패 모드** — GOV_COMMON이 기록한 실제 사례는 **인덱스가 HEAD 대비 1813커밋 뒤처진 상태**였으며, 그 상태의 분석 결과를 맹신하면 왜곡된다. (2026-08-04 실측: 정상 운영 중에도 인덱스가 HEAD 대비 1커밋 뒤처져 있음을 확인.) "사용 강제"만으로는 부족하고 **"인덱스 freshness 확인 → 결과 재검증" 절차 병행**이 필수다.
2. **실행 환경별 연결 여부는 별개 문제** — 305 §1.5/#987: Team B(비-Claude Code 모델) 실행 환경에 GitNexus MCP가 실제 연결되어 있는지 확인되지 않은 채 R-20이 적용된 전례. 문서 규칙과 실제 연결을 분리 검증해야 한다.
3. **grep 대체가 아니라 보완** — 커버리지 한계(클로저·콜백·프로퍼티 흐름 미추적)가 도구 계약상 공식적으로 명시되어 있다. 분석 결과는 원본 코드 재확인으로 교차 검증해야 한다.
4. **인덱스 유지 비용** — 심볼 변경마다 `gitnexus analyze` 재실행 필요. 무인덱스 상태의 실시간 결과를 주는 도구가 아니다.

### 4-3. 신규 프로젝트 이식 판정

**도구 자체는 도메인 무관 → 이식 가능. 단, R-20 거버넌스 규칙은 조건부 채택:**

- **Tier 2 이상(멀티 에이전트)에서만 채택** — 단일 개발자 환경(Tier 1)엔 인덱스 유지 오버헤드가 이득보다 크다 (306 §4 C-1 게이지 연동)
- 채택 전 **모든 참여 에이전트 환경에서 MCP 실제 연결 실측** (305 §8 체크리스트 2번)
- 규칙 텍스트에 **"인덱스 freshness 확인 → 결과 재검증" 절차를 R-20과 함께 명문화** (1813커밋 사례를 각주로)

**종합 등급**: 가치 4/5 — 코드베이스 성숙도·심볼 수가 커질수록 효용이 급증하는 도구다. 초기 스프린트부터 인덱스 유지 루틴을 확정하면 최고 효용을 얻는다. 신규 프로젝트에는 "도구만 이식"이 아닌 **"도구 + freshness 검증 절차 + 환경 연결 확인" 3종 세트로 이식**할 것을 권장한다.

**핵심 논지**: 307의 "이식 (VERY HIGH)" 등급 3건 중 2건(자산 B·C)이 305 §1.6 채택 원칙에 부합하지 않는다 — 자산 B의 에러코드 아키텍처는 미존재(반증만 존재), 자산 C는 도메인 결합 상태라 "분리 이식"이 아닌 "재설계"다. 이식 판정은 **"그대로 가져가서 쓰는 것"과 "참고해서 새로 만드는 것"을 구분**해야 하며, 본 문서 §1의 재검증 표가 그 구분 기준이 된다.

**신규 프로젝트 적용 순서 (D_Kai 제안)**:
1. 305 §5.1 "그대로 이식" 4건 복사 (§3-4)
2. 306 A-2 기준으로 RBAC 이식 + 4계층 검증 E2E 스캐폴드 (§1-1)
3. 자산 C는 제네릭 상태머신 재설계 + 변형 축 + 감사 로깅 내장 (§1-3)
4. 자산 B는 에러코드 스키마 신규 설계 (§1-2)
5. 로드맵 0단계(Tier 게이지) 확정 후 Tier별 채택 세트 적용 (§2-1)
6. GitNexus는 Tier 2 이상에서 "도구 + freshness 검증 절차 + 환경 연결 확인" 3종 세트로 도입 (§4)
