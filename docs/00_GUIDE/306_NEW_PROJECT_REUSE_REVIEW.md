## 0. 이 문서의 성격과 범위

본 문서는 [305_NEW_PROJECT_BASELINE_GUIDE.md](./305_NEW_PROJECT_BASELINE_GUIDE.md)의 **보완·추가 검토 의견**이다.

305는 "신규 저장소에 **무엇을 이식할 것인가**"에 대해 뛰어난 단일 출처다. 그러나 이식 대상 명세에 비해 **①이식 후 운영·검증을 어떻게 할 것인가**와 **②신규 도메인의 테스트 자산을 어떻게 시작할 것인가**가 상대적으로 약하다. 본 문서는 이 두 축에서 305의 갭을 보완하고, 신규 프로젝트 착수 시 결정이 필요한 추가 검토 사항을 제시한다.

> ⚠️ **정합성 주의 (2026-08-04)**: 305가 본 문서 작성 직후 v1.5로 갱신되어 §7(Task 관리 체계 이식 가이드 — 채번 스크립트·sync 워크플로우·ClickUp·사내 Git 플랫폼 실사)이 신설되었다(이후 v1.6으로 §8(306 링크) 추가). **B항목 중 B-1·B-2는 305 §7과 상당 부분 겹치므로 §7과 함께 읽어야 한다.** 또한 §7(v1.5) 권장안 **자체에 대한 검토 이견**을 본 문서 **§6**(6-1~6-7)에 수록한다.

**채택 원칙**: 305 §1.6과 동일 — "좋아 보이는가"가 아니라 "이 프로젝트에서 실제로 적용해 본 결과가 의미 있었는가"로만 판정한다. 아래 각 항목은 ZENITH_LMS에서 실제 관측된 사건(Issue #688·#358·#609, DEF-096/097/128 등)을 근거로 한다.

## 2. 보완 검토 사항 A — 테스트/검증 자산 재활용 (최대 공백)

### A-1. 테스트 자산은 "구조"만 있고 "명세"가 없다

**지적**: 305 §5.1은 `tests/{unit,integration,e2e}` 3계층 구조만 언급한다. 신규 프로젝트에서 "빈 3계층 폴더"를 가져가면 재현이 불가능하다.

**근거**: ZENITH_LMS에는 실제 재사용 가능한 테스트 자산이 구조를 넘어 존재한다 — Playwright 설정 3종(`playwright.config.ts`·`playwright-e2e.config.ts`·`playwright-e2e-quick.config.ts`, 용도 구분 필요), E2E 헬퍼/픽스처, `scripts/seed-local.ts`의 멱등 시드 호출부(`scripts/seed-local.ts`, CI 미실행 로컬 전용), `scripts/test_with_filter.sh` 등.

**보완 제안**: 305 §5.1에 다음을 명세로 추가할 것.
1. Playwright 설정 3종의 용도·실행 명령 매핑
2. E2E 헬퍼·픽스처의 복사 가능한 목록
3. `seed-local.ts` 멱등 패턴(자연키 조회→생성)의 호출부 명세
4. `tests/` 3계층의 최소 파일 골격(설정·픽스처·헬퍼 포함)

### A-2. "역할 한정 화면 실브라우저 검증" 원칙이 RBAC 이식과 미연결

**지적**: 305 §2(RBAC 스캐폴드 이식)와 검증 요건이 분리되어 있다. RBAC를 이식하면서 **해당 검증 규정을 함께 이식하지 않으면** 같은 사고가 신규 프로젝트에서 재발한다.

**근거**: AGENTS.md의 B_Kai/Baker "필수 검증 항목"(2026-07-22 신설) — 역할·조직유형 한정 화면은 단위 테스트(서버 액션 직접 호출, `validateUserAction` mock)만으로는 Next.js 미들웨어(`src/lib/auth/proxy.ts`)의 라우팅 화이트리스트 버그를 잡을 수 없다. 실제 사례 Issue #688(SUB_ADMIN 역할 라우팅 버그 미검출) — `rbac.ts`의 `STATIC_PERMISSIONS`(앱 레벨)와 `proxy.ts` 화이트리스트(미들웨어 레벨)는 별도 관리되므로, 실제 브라우저 네비게이션으로 둘의 일치를 확인해야만 한다.

**보완 제안**: 305 §2에 검증 요건을 1:1로 묶어 명문화할 것.
- RBAC 스캐폴드 이식 시, 역할·조직유형 한정 화면은 **실제 로그인 → `page.goto()` 네비게이션**으로 검증 의무화
- 미들웨어 화이트리스트 ↔ 앱 레벨 권한표 ↔ RLS ↔ DB GRANT의 4계층 일치를 확인하는 전용 E2E 케이스를 착수 스캐폴드에 포함

### A-3. `check-db-freshness.sh`(R-08-2)가 카탈로그에 누락

**지적**: 305 §5에 로컬 DB staleness 방지 모듈이 없다. 신규 프로젝트도 동일 문제를 겪는다.

**근거**: GOV_COMMON.md R-08-2(DEF-128 재발 방지, 2026-07-28 신설) — CI는 매 실행 `supabase db reset`으로 fresh DB를 보장하지만, **로컬 개발 DB는 에이전트가 마지막으로 reset한 시점에 따라 개인별로 stale**해질 수 있다. 이 상태의 로컬 검증 결과("로컬 검증 PASS" 보고)는 CI 기준과 다를 수 있다. `scripts/check-db-freshness.sh`(`--fix` 옵션: `supabase db reset --yes` + `seed-local.ts`)가 이를 차단한다. `agent-worktree-init.sh` 실행 시 자동 확인된다.

**보완 제안**: 305 §5.1 "그대로 이식" 항목에 `check-db-freshness.sh`와 R-08-2 원칙(로컬 검증 신뢰성은 DB 최신성 전제)을 추가할 것.

### A-4. 회귀 스위트 실행 전략 미명세

**지적**: 305 §5.2 CI 파이프라인 판정은 "골격 재사용"뿐이다. 회귀 스위트의 **실행 방식**이 명세에 없다.

**근거**: `pr-checks.yml`은 전체 회귀 스위트를 단일 job으로 실행한다. ZENITH_LMS에서 이 방식이 러너 큐 혼잡을 유발했고(Issue #609), sync 봇이 매 Issue 라벨 변경마다 전체 회귀를 도는 것을 `if: github.head_ref != 'bot/sync-active-task'` 조건으로 막은 이력이 있다.

**보완 제안**: 신규 프로젝트는 착수부터 다음을 설계할 것.
- 회귀 스위트의 **sharding/병렬 분할** 여부와 임계치(스위트 실행 시간 기준)
- 커버리지 게이트(`vitest` coverage 80%+) 설정 명세 — ZEN_A4가 명시하는 기준을 실제 도구 설정으로 고정
- CI 전용 브랜치(`bot/*`) 회귀 실행 제외 조건

### A-5. 테스트 케이스 카탈로그(템플릿) 부재

**지적**: 회귀 테스트 케이스 자체는 전부 ZENITH 도메인 결합이라 신규 도메인에서 처음부터 작성해야 한다. `LIVE_REGRESSION_TEST_MAP.md`는 "맵"이지 "카탈로그"가 아니며, vacuous-test 안티패턴(210 §2) 참조만으로는 작성 시작점이 없다.

**보완 제안**: 305에 다음을 추가할 것.
1. **TestCase 작성 템플릿** — 시나리오명·사전조건·입력·기대결과·검증계층(서버액션/미들웨어/UI) 필드
2. **LIVE_REGRESSION_TEST_MAP.md 골격** — 신규 도메인 첫 케이스를 작성하기 위한 빈 맵 템플릿
3. 회귀 케이스 확장 의무(R-09)를 CI 게이트와 연결하는 방식

## 3. 보완 검토 사항 B — 관리 자동화 모듈

### B-1. `agent-worktree-init.sh` 이식 — 305 §7.1로 해소, 잔여 검토는 "멀티 에이전트 채택 여부"

**상태**: 305 v1.5 §7.1이 `scripts/agent-worktree-init.sh`를 실사 인벤토리에 포함하고 "그대로 이식 가치 높음"으로 판정 → 본 항목의 지적(카탈로그 누락)은 **해소됨**.

**근거**: 공유 물리 디렉토리 교차 오염(Issue #358)은 ZENITH_LMS가 가장 반복적으로 실패한 영역 중 하나였다 — 수기 안내로는 재발했고(PR#367·#368·#370), 스크립트 강제(페르소나별 영속 워크트리 + `git stash` 보존 + `origin/develop` 복귀)로 해결했다. 2026-07-21 Team A까지 확대 적용된 실증 모듈이다.

**잔여 보완 제안**: 이식 여부는 **멀티 에이전트 채택 여부에 종속**된다. 단일 개발자/단일 세션이면 불필요 — 306 §4(C-1 규모 게이지)와 연동해 채택 여부를 착수 결정 사항으로 명시할 것.

### B-2. 태스크 관리 자동화 명세 — 305 §7과 정합 후 잔여 갭(템플릿 부재)만 보완

**상태**: 305 v1.5 §7.1이 라벨 스키마·sync 워크플로우 3종(`sync-issue-to-active-task.yml`·`sync-label-to-project.yml`·`sync-project-to-label.yml`)·`sync_active_task.py`·채번 스크립트 2종·커밋해시 삽입 스크립트를 **실사 인벤토리로 정리**했다. §7.2는 나아가 "GitHub Issue 번호를 Task ID로 직접 쓰면 별도 채번 체계 자체가 불필요해진다"는 판정을 내려 **본 항목의 "패키지 명세" 요청보다 진전된 안**을 제시했다 → 인벤토리 관점 지적은 해소, 단, 다음 잔여 갭이 남는다.

**잔여 갭 — Task 파일 템플릿 부재**: §7.1 자체가 `.agent/tasks/*.md`는 "정식 템플릿 파일 없이 기존 파일 구조를 관례적으로 복제 — 재사용성 낮음"임을 인정한다. 신규 프로젝트는 최초 스캐폴드부터 **Task 상세 파일·DEF 보고서·완료보고 섹션(`[작업 결과]`·`[발견 이슈]`·`[Aiden 검토]`)을 포함한 정식 템플릿**을 정의할 것 — 이는 306 §2(A-5)의 TestCase 템플릿과 함께 "문서 템플릿 스캐폴드"로 묶어 305 §8 체크리스트에 추가 검토할 것.

### B-3. 위반 페널티는 "기록"이 아닌 "게이트"와 연결해야 실질 보완이 된다

**지적**: 305 §1.6의 반증("VIOLATION_TRACKER에 기록해도 재발이 줄지 않았다")에 동의하되, **보완책**이 제시되지 않았다.

**근거**: `.agent/VIOLATION_TRACKER.md`는 위반 이력 가시화에는 효과가 있었지만(Issue #987 분석 근거), 기록 자체가 재발을 막지 못했다. `pr-checks.yml`의 `task-file-check` job은 "advisory(비차단) 경고"에 그친다.

**보완 제안**: 신규 프로젝트는 기록과 **자동 게이트**를 처음부터 연결할 것.
1. 위반 카운터 N회 초과 시 **PR 생성 차단**(CI required check)
2. `task-file-check`를 비차단 경고에서 **차단 게이트로 승격**하는 명시적 기준(승격 시점·근거)
3. `commit-msg` 훅(`insert-commit-hash.sh`)의 커밋 해시 삽입을 그대로 이식

## 4. 추가 검토 사항 C — 규모·환경별 조정 규칙

### C-1. 프로젝트 규모별 이식 스코프 조정 규칙 부재

**지적**: 305는 ZENITH_LMS(다중 에이전트 + 다중 팀 초대형) 전제로 작성되었다. 소규모(1~2인·단일팀) 신규 프로젝트에 전체 거버넌스(R-17 상태머신 + 워크트리 + sync 워크플로우 3종)를 이식하면 **관리 비용이 개발 비용을 초과**한다.

**보완 제안**: **규모 게이지**를 305 §8 체크리스트에 추가 검토할 것.

| Tier | 기준 | 최소 채택 세트 |
|:---|:---|:---|
| **Tier 1** | 1~2인 · 단일 에이전트 | GOV_COMMON 축소판 · R-08 회귀 · Issue 템플릿 · CI |
| **Tier 2** | 소수 인원 · 멀티 에이전트 | + ACTIVE_TASK 상태머신 · 채번 스크립트 · 워크트리 격리 |
| **Tier 3** | 다중 팀 병행(≥2팀) | 305 전면 적용(R-19 포함) · sync 워크플로우 3종 · 라벨 스키마 |

### C-2. 최소 문서 트리 스캐폴드 명세 부재

**지적**: 305 §6은 리포 A/B 배치 기준은 있지만, **빈 docs 트리 골격**이 없다. 최초 스캐폴드에서 폴더를 확정하지 않으면 신규 프로젝트도 같은 드리프트를 반복한다.

**근거**: 305 §1.6이 스스로 실증 — `04_Database` vs `database`, `09_Checklists` vs `09_TEMPLATES` 중복 폴더가 현재도 존재하며, 수동 문서번호 컨벤션은 드리프트했다. 실제 효과가 있었던 것은 자동화 스크립트였다.

**보완 제안**: 305에 **최소 docs 트리 골격**(`00_GUIDE`~`99_Manual`의 Tier별 폴더 세트)을 명세로 추가할 것. 폴더 하나당 생성 근거(어느 R-규칙이 요구하는지)를 함께 기재.

## 5. 추가 검토 사항 D — 결정 필요 오픈 이슈

### D-1. E2E 결과물의 git 잔류 정책

305 §6.3은 LFS/스쿼시 정책으로 대응하지만, R-10/R-17의 **감사 증적 보존 요구**와 리포 경량화는 정면 충돌한다. 대안을 동등 검증할 것:
- (a) 결과물 자체를 커밋하지 않고 봇이 외부 아카이브에 산출, git에는 매니페스트(결과 인덱스)만 유지
- (b) git-lfs 트래킹(R-10/R-17 증적처럼 이력 자체가 가치 있는 경우)

### D-2. Git 호스트 의존성 — 305 §7.5(Q4)로 해소

305 v1.5 §7.5가 사내/자체호스팅 Git 플랫폼(GitHub Enterprise Server vs GitLab CE vs Gitea/Forgejo) 비교와 "목적(레지던시/비용/접근통제) 우선 확정" 권고를 이미 담았다 → 본 항목 지적은 **해소됨**. §7.5 기준으로 신규 프로젝트의 Git 호스트를 착수 전 확정할 것.

### D-3. 공개 리포 vs 사내 리포

`GH_PROJECT_TOKEN`(Admin PAT) + 봇 PR·수동 병합 구조는 Public 리포 기준. **Private/Enterprise는 branch protection 동작이 달라** 워크플로우 세부 조정이 필요하다(워크플로우 상단 주석에 이 한계가 이미 기록됨). §7.5의 플랫폼 비교에 이 "Public/Private 리포에서의 CI·봇 권한 차이" 검토를 함께 결합할 것을 권장한다.

### D-4. 잔여 도구 이식 판정 명시

아래 항목은 305 §5에 누락된 채 가벼운 항목으로 남는다 — **이식/미이식 판정을 명시**할 것.
- `rtk`(토큰 최적화 CLI 프록시) — 프로젝트 전용 래퍼
- `.env.example → .env.local` + CI의 `supabase status --output env` env 생성 패턴
- 모니터링(Sentry `@sentry/nextjs`) — 도메인 무관, 프로젝트 스택 확정 후 이식 여부 결정
- 자동 감사 스크립트(`scripts/audit-rbac.ts`·`scripts/audit-i18n.ts`) — RBAC/다국어 채택 시 함께

## 6. 305 v1.5(§7 Task 관리 체계) 변경사항에 대한 검토 이견

305 v1.5 §7은 **실사 인벤토리(§7.1)**와 **방향 제안(§7.2~§7.5)**으로 구성된다. 인벤토리(§7.1)는 실측 기반이라 신뢰한다. 그러나 **방향 제안 중 §7.2의 핵심 권장안(GitHub Issue 번호 = Task ID + ACTIVE_TASK 100% 자동생성 read-only 캐시)**에 대해서는 이견이 크다. 아래 7건을 검토 의견으로 제시한다.

### 6-1. [핵심 이견] §7.2 권장안은 305 §1.6 "실제 적용 결과" 채택 원칙을 위반한 미검증 제안이다

**지적**: §7.2는 "Task ID = GitHub Issue 번호, 별도 채번 체계 폐지, ACTIVE_TASK는 100% 자동생성 read-only 캐시"를 권장한다. 근거는 오직 **현 체계의 실패 이력**(Issue #358·#773)뿐이고, 제안된 새 구조가 ZENITH_LMS에서 **적용·검증된 적이 없다.**

**근거**: 305 §1.6의 채택 원칙은 "좋아 보이는가"가 아니라 "실제 적용 결과가 의미 있었는가"다. 실패 이력은 "현 체계가 안 좋았다"는 증거이지 "새 구조가 작동한다"는 증거가 아니다. 또한 §1.3·§1.6은 VIOLATION_TRACKER에 기록돼도 재발한 근본 원인이 **규정 미집행**임을 실증했다 — 위반은 "수기 반영이 여러 곳이라" 발생했다기보다 **집행하지 않아서** 반복됐다. §7.2는 원인을 "수기 절차의 다중 반영"으로 재정의하며 §1.3의 진단(규정 미집행)을 희석한다.

**권고**: §7.2 권장안은 "신규 프로젝트 즉시 적용"이 아니라 **"ZENITH_LMS에서 파일럿 적용 → 검증 → 이식" 등급**으로 명시할 것. 검증 지표(예: R-17 위반 건수 감소, 완료보고 소요 절차 단계 수)를 사전 정의하고, 검증 전까지는 306 §4(C-1) Tier 2 이상에 한해 참고안으로만 둘 것.

### 6-2. "100% 자동생성 read-only 캐시"는 즉시성(staleness) 문제를 새로 만든다

**지적**: §7.2는 ACTIVE_TASK.md를 "수기 표 없이 자동생성 캐시"로 바꾸는 안이다. 그러나 현재 sync 워크플로우는 **PR을 생성하고 Aiden이 수동 병합**하는 구조(R-17)라, **병합 전까지 develop 브랜치의 ACTIVE_TASK는 갱신되지 않는다.**

**근거**: §7.1 스스로 봇은 push하지 못하고 PR만 생성한다고 인정한다. PR 병합 지연(검토 대기·CI 대기)이 발생하면 R-16(세션 시작 시 최신 상태 확인)이 **stale 캐시를 읽는 것**이 된다. 현 체계의 수기 표는 드리프트 가능성은 있으나 **즉시성은 있었다** — 자동 캐시는 그 반대(드리프트↓·즉시성↓)로, R-16의 목적이 실질적으로 약해질 수 있다.

**권고**: 자동 캐시 채택 시 **병합 지연 완충**을 함께 설계할 것 — 예: 봇 PR이 미병합 상태여도 해당 브랜치의 캐시를 세션 시작 시 fetch, 또는 GitHub API 폴백. "자동생성"이 곧 "최신"을 보장하지 않음을 명시할 것.

### 6-3. §7.2(GitHub 전제)와 §7.5(타 호스트 허용)는 내부 모순

**지적**: §7.2의 "Issue 번호 = Task ID + GitHub Actions sync" 구조는 **GitHub에 더 깊이 결합**된 선택이다. §7.5는 GitLab 등 대안을 열어두면서도, §7.2가 전제한 GitHub 전용 구조가 그대로 유지 가능한 것처럼 서술한다.

**근거**: GitLab 채택 시 Issue 라벨 API·Project 보드·sync 워크플로우는 전부 재작성 대상(§7.5 스스로 "높음" 비용 인정). Task ID 체계 자체는 호스트 무관하나, 이를 전제로 한 **자동화 세트는 호스트 종속**이다.

**권고**: §7.2 채택 여부는 **Git 호스트 확정 이후에만** 판단하도록 결정 순서(호스트 확정 → Task ID 구조 → 자동화 세트)를 명문화할 것.

### 6-4. §7.5 비교표에 "셀프호스티드 러너/인프라 운영 비용"·"에이전트 자동화 호환성" 축이 누락

**지적**: §7.5는 GHES/GitLab CE를 "마이그레이션 비용" 중심으로 비교하지만, **데이터 레지던시 목적의 자체호스팅이 에이전트 자동화에 미치는 영향**을 평가하지 않는다.

**근거**: 자체호스팅으로 전환하면 GitHub.com 호스팅 러너에서 CI·봇 sync 워크플로우(§7.1)를 돌릴 수 없어 **셀프호스티드 러너 별도 구축·네트워크 허용 목록 운영**이 필요해진다. 이는 305 §1.5(MCP 실제 연결 확인)와 동일한 검증 원칙의 연장이다 — "자체호스팅에서도 `gh` CLI/Actions가 동일하게 동작하는지"를 사전 확인하지 않으면 자동화 의존 구조가 깨질 수 있다.

**권고**: §7.5 비교표에 ③인프라(셀프호스티드 러너·운영 부담) ④에이전트 자동화 호환성 축을 추가하고, "목적 우선 확인"의 판단 축을 4개로 확장할 것.

### 6-5. Issue 번호 = Task ID의 암묵적 가정 — "1 Issue = 1 Task"와 PR 동일 네임스페이스

**지적**: GitHub에서 Issue와 PR은 **같은 번호풀**을 쓴다. Task ID로 Issue 번호를 쓰면 PR 번호와 혼동 가능성이 있다. 또한 "1 Issue = 1 Task"라는 암묵적 가정은 에픽성 Issue(예: Issue #164 "UAT-Epic"처럼 다중 작업 단위를 묶는 Issue)에서 매핑이 모호해진다.

**권고**: 순수 단일 작업 위주 프로젝트엔 유효하나, **에픽/스프린트 단위 이슈**를 쓰는 체계에서는 Task ↔ Issue ↔ PR 간 명시적 매핑 규칙(하위 작업·체크리스트 항목)을 별도 정의할 것.

### 6-6. ClickUp 네이티브 GitHub 연동의 플랜/기능 제약 미검증

**지적**: §7.3은 "네이티브 GitHub 연동으로 시작, 커스텀 코드 불필요"라 판정하나, ClickUp 네이티브 연동의 **플랜별 기능 제약**(연동 리포 수·양방향 지원 여부·브랜치/커밋 참조 범위)을 검증하지 않은 낙관적 판정이다.

**권고**: "연동 기능 범위 사전 확인 후, 부족분만 §7.1의 sync 패턴으로 보완"하는 **조건부 판정**으로 명시할 것.

### 6-7. [경미] 3계층 모델에서 레이어 1(GitHub Issue)은 여전히 다중 쓰기 주체

**지적**: §7.4의 "동일 상태값을 두 곳 이상이 쓰기 권한을 갖지 않도록" 원칙은 **레이어 간**에는 지켜지지만, 레이어 1 내부에서 에이전트·팀 리더·Aiden이 모두 쓰기 권한을 가져 **이벤트 레이스(상태 충돌)** 여지가 남는다.

**권고**: 상태 전이는 "사람"이 아니라 **라벨 전이 검증 자동화**(불법 전이 차단)로 중재하고, 권한 모델을 "시스템 단일 소스 + 사람 단일 소유"로 명문화할 것.

**소결**: §7.1(인벤토리)은 실증 기반으로 채택 가치가 높다. §7.2~§7.5의 방향 제안은 "ZENITH_LMS 파일럿 검증 후 이식" 등급으로 조정하고, 특히 **6-1(§1.6 원칙 복원)**과 **6-2(캐시 즉시성)**을 착수 전 반영할 것을 권장한다.
