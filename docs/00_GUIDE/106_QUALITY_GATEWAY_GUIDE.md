# [106] 제니스 물류 플랫폼 2단계 품질 게이트웨이 가이드 (v1.2)

> **문서번호**: 106 
> **작성자**: Antigravity (CEO Agent) · v1.1~v1.2 추가: Aiden (Claude, ZEN_CEO)
> **상태**: 공식 채택 (Official Standard)

본 문서는 ZENITH_LMS 프로젝트의 품질 무결성을 확보하기 위한 **[2단계 품질 게이트웨이(Two-Phase Quality Gateway)]** 방법론에 대해 정의합니다. 모든 코드 배포 및 검증 절차는 본 가이드를 최우선적으로 준수해야 합니다.

---

## 🏛️ 제1원칙: 품질은 논리로부터 시작된다
품질 검증은 '화면이 보이는가'가 아닌 '논리가 정밀한가'에서 출발합니다. 이를 위해 검증 프로세스를 이원화합니다.

### Phase 1: 논리적 실드 (Logic Shield - Automated)
논리적 처리와 로직의 무결성을 코드로 증명하는 단계입니다.
- **도구**: Vitest (Unit / Integration Test)
- **대상**: 
  - 비즈니스 알고리즘 (요율 계산, 환율 변동 등)
  - 데이터 스키마 밸리데이션 (Zod Schema)
  - 권한 처리 로직 (RBAC Rules)
- **성공 요건**: 모든 테스트 케이스 100% 통과 (Coverage 80%+ 권장)

### Phase 2: 운영의 혈맥 (Operational Pulse - Scenario-based)
증명된 논리들이 실제 운영 화면(UI)과 결합되어 유기적으로 동작함을 입증하는 단계입니다.
- **도구**: Playwright (E2E), Manual Browser Testing
- **대상**:
  - 실제 비즈니스 시나리오 (예: 오더 생성 -> 배송 완료)
  - UI/UX 반응성 및 다국어 렌더링
  - DB 통합 데이터 정합성 (UI 조작 $\to$ DB 저장)
- **성공 요건**: 사전에 정의된 UAT 시나리오의 모든 단계가 실제 화면에서 오차 없이 수행됨

---

## 🏛️ 제니스 통합 테스트 명세서(ZEN Integrated Test Spec) 작성 표준

모든 테스트 시나리오는 단순한 행위 기술을 넘어 다음의 **[4계층 구조]**를 포함하여 수직적 무결성을 증명해야 합니다.

1. **도메인 및 ID (Domain ID)**: R, O, C, S 등 비즈니스 도메인과 고유 번호 식별.
2. **논리 실드 (Phase 1: Logic Shield)**: 로직 무결성을 검증할 `Vitest` 테스트 파일 및 핵심 함수 명시.
3. **운영 혈맥 (Phase 2: Operational Pulse)**: 실제 UI 조작 경로 및 기대 반응 명시.
4. **통합 매트릭스 (Integrated Matrix)**: Phase 1(로직)과 Phase 2(화면)의 성공 여부를 한눈에 기록.

---

## 🛠️ 검증 운영 표준 (SOP v2.0)

1. **통합 명세서 작성**: 검증 전 `docs/08_Self_Audit/UAT/` 하위에 통합 시나리오를 작성한다.
2. **Phase 1 (Logic) 수행**: 엔진의 논리적 버그를 선제적으로 제거하고 코드 증거를 남긴다.
3. **Phase 2 (Screen) 수행**: 입증된 엔진 위에서 실제 화면 시나리오를 전수 검증한다.
4. **중앙 집중식 결과 기록**: 모든 검증 결과와 특기 사항은 해당 시나리오 파일의 [매트릭스] 섹션에 즉시 기록하여 보존한다.

## 🏛️ 제3실천: 지속적 품질 자산화 (CQA - Mandatory)

제니스의 품질은 축적되어야 합니다. 모든 신규 개발 및 수정 사항은 다음의 **[회귀 프로토콜]**을 통과해야 합니다.

1. **상시 증명**: 모든 작업 완료 보고 전, 표준 명령어(`npm run test:regression`)를 수행하여 기존 기능의 파괴 여부를 자가 진단한다.
2. **증거 기반 승인**: 에이전트는 작업 완료 보고 시 회귀 테스트 성공 결과를 증거로 첨부하여 품질 무결성을 시각적으로 입증한다.
3. **자산화**: 신규 기능 개발 시, 해당 기능을 위한 Phase 1/Phase 2 테스트를 기존 수트에 누적(Cumulative)하여 미래의 품질 관문으로 삼는다.

## 🏛️ 제4실천: 단계 종료 Gate — Code Review (Stage-Gate Code Review, v1.1 신설)

> **도입 배경 (2026-10-03, Edward 지시)**: 타 프로젝트에서 단계 종료 Gate로 Code Review를 실시해 Null 처리·미정의 데이터 처리 로직 누락 등 유의미한 조치 사항이 도출된 사례를 참고해 도입. ZENITH_LMS에서도 DEF-137(2026-04월 도입 이래 반년 가까이 아무도 못 찾은 RLS 정책 소실)·DEF-B-149(5개월간 미탐지된 재고이력 insert 실패) 등 **"터져서야 발견된" 유형의 결함**이 반복됐다 — 이는 Phase 1(Vitest)·Phase 2(E2E)만으로는 "작성 당시 의도대로 동작하는가"는 검증되지만 "애초에 놓친 케이스(Null/미정의 데이터/엣지케이스)"는 못 잡는다는 구조적 한계를 보여준다. Stage-Gate Code Review는 이 공백을 메우기 위한 **사람(Aiden)·LLM 보조 정적 검토**로, 자동 테스트와 상호 보완 관계다(대체 아님).

### 목적과 Phase 1/2와의 차이

| | Phase 1 (Logic Shield) | Phase 2 (Operational Pulse) | **Phase 0 — Stage-Gate Code Review** |
|:---|:---|:---|:---|
| 검증 대상 | "작성된 로직이 의도대로 동작하는가" | "화면과 유기적으로 동작하는가" | **"애초에 놓친 케이스가 있는가"**(Null/미정의값/예외 처리 누락 등) |
| 방식 | 자동(Vitest) | 자동/수동(Playwright, 수동 브라우저) | **정적 리뷰**(코드를 실행하지 않고 읽어서 판단) |
| 전제 | 테스트 케이스를 "작성한 사람"이 놓친 게 없어야 함 | 시나리오를 "설계한 사람"이 놓친 게 없어야 함 | 테스트·시나리오 설계 단계의 사각지대 자체를 다른 시점에 재검토 |

### 실시 시점 (Gate)

아래 세 시점 중 하나에 해당하면 실시한다 — 정기 주기가 아니라 **이벤트 기반 Gate**:

1. **단계(Phase/Milestone) 종료 시점** — 기능 개발 단계가 마무리되고 다음 단계로 넘어가기 직전
2. **집중 운영·고위험 기간 진입 직전** — 예: Pilot 집중 운영, 대규모 배포, 성수기 등 돌입 전(이번 ZENITH_LMS 10/5~10/15 Pilot 집중 운영이 최초 적용 사례)
3. **반복적으로 "터져서 발견된" 결함이 누적될 때** — 동일 유형(예: RLS 정책 누락, 반환값 기반 실패 무기록)의 결함이 2건 이상 발생하면, 그 유형에 한정한 타겟 리뷰를 Gate로 추가 발동(R-18 발견 이슈 누적과 연동)

### 범위 선정 원칙 — 전체 코드베이스 재검토는 지양하되, Gate 성격에 따라 "전체"의 기준이 다르다 (v1.2 명확화)

"전수 리뷰 지양"은 **매번 전체 코드베이스를 다시 훑지 않는다**는 뜻이지, 각 Gate 안에서 결과물을 임의로 골라낸다는 뜻이 아니다. Gate 유형별로 범위는 이렇게 정의된다:

- **단계 종료 Gate**: 범위 = **해당 단계 동안 추가·수정된 코드 전체**(선별 없음). 이미 "그 단계의 작업분"으로 자연히 경계가 정해져 있으므로, 그 안에서 다시 "핵심적인 것만" 골라내지 않는다 — 단계 시작 시점 커밋 ~ 종료 시점 커밋 사이 `git diff` 범위(또는 그 단계 동안 머지된 PR 전체)를 그대로 리뷰 대상으로 삼는다. "모듈 단위로 좁힌다"고 오독되지 않도록 반드시 **전체 diff**를 기준으로 할 것.
- **집중 운영·고위험 기간 진입 직전 Gate**: 이 경우는 "그동안 쌓인 전체 코드베이스"가 모수이므로 전수 리뷰가 비효율적 — 그 운영 기간에 실제로 많이 호출될 핵심 경로(예: 오더 등록→창고 처리→UPS 등록/출고→통관→정산)로 **의도적으로 좁힌다**. 범위 축소가 필요한 건 이 유형뿐이다.
- **반복 결함 기반 Gate**: 범위 = 해당 결함 패턴이 나타날 수 있는 유사 코드 전체(GitNexus `gitnexus_query`로 유사 패턴 탐색 권장) — 이 역시 "패턴에 해당하는 전체"이지 일부 샘플링이 아니다.

### 실시 방법

1. Aiden이 Gate 시점·범위를 판단해 GitHub Issue로 등록(`type:review` 성격, 실시 시점을 명시)
2. `code-review` 스킬(또는 `security-review`, 보안 관련 범위일 경우)로 대상 경로를 리뷰 — effort level은 범위 크기에 따라 조정
3. 발견 사항은 심각도에 따라 **R-18(결함 — DEF 등록)** 또는 **R-15(개선사항 — IMP 등록)** 절차를 그대로 따른다 — Stage-Gate Code Review 전용의 별도 트래킹 체계를 만들지 않는다(이중 기록 방지 원칙, ACTIVE_TASK.md 폐지 사례와 동일 교훈)
4. 발견된 결함 유형이 반복 패턴이면(§"반복적으로 터져서 발견된 결함" 참조) ZEN_A4 코딩 원칙(본 문서 상위의 실패 관측성 의무 등)에 신규 원칙으로 승격할지 Aiden이 검토
