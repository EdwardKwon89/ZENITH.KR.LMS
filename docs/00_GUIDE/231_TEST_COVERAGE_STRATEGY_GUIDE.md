## 1. 배경과 목적

### 1.1 문제의식

현재 품질은 **SAR(사후 오류 분석) + 회귀 테스트**로 확보한다. 이 체계는 필수이지만, 다음 한계가 확인되었다.

| # | 한계 | 근거 |
|:-:|:--|:--|
| 1 | **사후 대응형** — 결함이 나온 뒤에 케이스가 추가되어, 같은 종류 결함이 필드·모듈만 바꿔 반복된다 | DEF-B 제목 기준(부록 B): SHXK/UPS 연동 필드 누락·불일치 7건 이상, RLS·GRANT 누락 6건 이상, CN 코드 불일치 2건(B-044·045, 동일 원인). `validate-payload.ts` 필드 제약이 TASK-B-277/283/332/337(Issue #1052·#1069·#1239·#1251)에 걸쳐 사후에 하나씩 추가됨(Riley) |
| 2 | **미커버 영역이 보이지 않는다** | 커버리지 측정 설정 없음 — `vitest.config.ts`에 coverage 블록, `package.json`에 `@vitest/coverage-v8` 없음 (Riley·B_Kai 각자 확인) |
| 3 | **테스트의 검출력이 측정되지 않는다** | Team B가 PR마다 "구현을 되돌려 테스트가 실패하는지"를 수작업 확인(변이 테스트의 수동판). "통과하지만 검증하지 않는 단언" 금지 규칙이 필요했던 사실 |
| 4 | **mock 단위 테스트로 원리상 못 잡는 결함군** | RLS·GRANT, 외부 API 명세 불일치, 컬럼·스키마 불일치는 mock 환경에서 드러나지 않음 |
| 5 | **계층 간 계약 단절** *(Riley 제안)* — 각 계층은 개별로 동작하나 계층 사이 계약이 어긋난다 | ① 라우팅(`proxy.ts`)↔권한(`rbac.ts`): Issue #688(역할×라우트 불일치)·DEF-085(공통 허용 경로 누락) ② 서버 액션 반환↔클라이언트 캐시(`revalidatePath`): DEF-B-057·147 ③ 코드의 번역 키 호출↔`messages/*.json`: Issue #946(DEF-B-023) |
| 6 | **테스트 데이터·명세의 불안정** *(B_Kai 제안)* — 시드·장기 실행 DB·환경 차이로 인한 비결정성(flaky), 그리고 "명세에서 도출"하려 해도 명세가 부재·변경되는 경우 | SAR-2026-07-27-001(자기완결 fixture 원칙). 저장소 전반 flaky 이력은 미확인 |

> **증거 기반 주의**: 부록 B의 결함 분류는 제목 기준 임시 분류이며, 현재 `.agent/defects/`에는 Team A `DEF-NNN` 86건 + Team B `DEF-B-NNN` 84건이 있다. PoC 단계 3에서 전수 재분류한다. **저장소 기준 주의**: 위 건수는 develop 체크아웃 기준이다. **`TeamB_Dev`에는 develop에 아직 없는 DEF가 있다** — 예: DEF-B-157은 TeamB_Dev에만 존재(develop 0건). 2차 검증에서 3인이 develop만 보고 "DEF-B-157 부재"로 합의했으나 사실이 아님을 Aiden이 확인했다(합의가 사실을 보증하지 않음). 이후 DEF·Task 번호를 인용할 때는 **기준 브랜치를 함께 적는다**.

### 1.2 이 문서가 다루는 것 / 다루지 않는 것

- **다룬다**: 테스트 차원 모델, 케이스 도출 방법, 커버 맵, 검출력 측정, Agent 규칙, 도입 로드맵(PoC).
- **다루지 않는다**: 기존 R-04(LIVE 체크리스트)·R-08(전체 회귀 PASS)·R-09(회귀 확장)·SAR 절차의 변경. 본 문서는 이를 **대체가 아닌 보완**한다.
- **전제**: "모든 것을 테스트로 덮는 방법"은 존재하지 않는다. 대신 **무엇이 덮였고 무엇이 비었는지 보이게 하고, 빈 칸을 위험도 순으로 채우는 구조**를 목표로 한다.

### 1.3 적용 시점과 대상 — 프로젝트별로 다르다

이 문서는 **결함이 난 뒤 케이스를 보태는 방법(사후)이 아니라, 결함이 나기 전에 케이스를 도출하는 방법(사전)과 그 측정**을 함께 정의한다(§4.9). 다만 적용 시점은 프로젝트마다 다르다.

| 프로젝트 | 현재 단계 | 적용 시점 | 적용 방식 |
|:--|:--|:--|:--|
| **ZENITH_LMS** | **Pilot 운영 중** — 운영 코드·실데이터가 이미 존재 | **Pilot 운영 단계부터** (이미 만들어진 시스템에 도입) | 전수 소급 적용을 하지 않는다. **① PoC 기간에는 PoC 3모듈과 위험 기준 2개 이상 Issue에 사전 도출 절차(§4.9)를 시범(권고) 적용하고, 전면 필수화는 PoC 성과 확인 후 §10 #14에서 결정 ② 핵심 모듈 PoC(§8)로 효과 검증 ③ 커버 맵으로 공백을 점진 해소**. 테스트·재현 시험은 **로컬 Supabase를 원칙**으로 하며(R-14), 원격(Pilot) DB 접속은 R-14에 따라 Edward 승인 후에만 하고 실데이터는 보전한다 |
| **MLFF BOS** | 초기(착수 전·초기) | **초기부터(Day-0)** | 요구사항·설계 단계에서 §4.9를 처음부터 적용하고, 커버 맵을 모듈 생성과 함께 작성한다(§8.6). LMS PoC의 성과를 확인한 뒤 도구·규칙을 이식한다 |

> LMS는 "이미 있는 것을 점검"하는 비중이 크고(§5 커버 맵, §8 PoC), MLFF는 "처음부터 같이 만드는" 비중이 크다. 같은 문서를 쓰되 **LMS에서는 §5·§8, MLFF에서는 §4.9·§8.6을 먼저 본다.**

## 2. 핵심 원칙

1. **명세에서 도출한다 (Builder vs Breaker)** — 테스트 케이스는 구현 코드의 분기를 따라가지 않고 요구사항·Ds-11 명세·도메인 규칙(105)에서 도출한다. 구현자와 다른 주체(R-01 Auditor)가 도출할수록 좋다. 명세가 없거나 모호할 때의 처리는 §7-1.
2. **결함은 "클래스"로 막는다** — 결함 1건을 고칠 때 그 건의 테스트만 추가하지 않고, 같은 원인 클래스(예: "외부 payload 필수 필드 누락")를 한 번에 막는 구조 테스트를 추가한다.
3. **테스트의 품질도 측정한다** — 테스트 개수가 아니라 검출력(변이 점수·되돌리기 검증)으로 평가한다.
4. **커버 현황을 가시화한다** — 모듈 × 차원 커버 맵으로 빈 칸을 드러낸다 (§5).
5. **실DB·실계약이 필요한 영역은 mock 테스트로 대체하지 않는다** — RLS·GRANT·외부 명세는 별도 계층으로 검증한다.
6. **도입은 PoC 성과 후 확대한다** — 도구·규칙을 전면 도입하기 전에 과거 결함 재현 시험으로 효과를 입증한다 (§8). **저비용·고효과 항목은 도구 도입에 앞서 선행한다** *(B_Kai)*.

## 4. 차원별 케이스 도출 방법

### 4.1 D1·D5 — 업무 분기와 상태 전이: 결정표·전이 매트릭스

**결정표**: 규칙을 조건 열 × 결과 열로 적고, **핵심 위험 조합이 행으로 존재**하는지(전수 조합이 폭발하면 아래 2번 기준으로 우선순위화) 확인한 뒤 각 행을 테스트 1건(표 기반 `it.each`)으로 만든다.

```text
예) 운임 계산 결정표 (축약 — 실제 조건은 105 §2 및 Ds-11에서 도출)
| 요율카드 존재 | 중량 구간 | 목적지 Zone | 결과(기대)            |
|:-:|:-:|:-:|:--|
| Y | 일반 | 매핑됨 | 슬랩 요율 적용        |
| Y | 일반 | 미매핑 | 명시적 오류(무음 금지)|
| N | -    | -      | 명시적 오류 / 기본값 정책 |
| Y | 경계(구간 상한±1) | 매핑됨 | 구간 경계 정확성 |
```

**전이 매트릭스**: `역할 × 현재 상태 × 요청 액션 → 허용/거부` 전 칸을 표로 만들고, 표 자체를 테스트 데이터로 사용한다. **표에 없는 조합은 "거부"가 기본값**임을 단언한다. 금지 전이(Negative)를 허용 전이만큼 중요하게 취급한다 (QAM 2.1 Negative Test와 정합).

**조건 축을 쪼개는 기준** *(B_Kai·Riley 공통 지적 — 상태 외 요인이 결과를 바꾸는 함수가 있음)*:
1. **순수 함수 매트릭스**와 **상태 결합 매트릭스**를 분리해 작성한다.
   - 순수 함수: 입력만으로 결과가 정해지는 것 (예: `canChangeStatus(current, target, role)` — 3변수, 즉시 표 기반 테스트화 가능).
   - 상태 결합: DB 상태 등 외부 사실이 결과에 영향 (예: 수정 가능 여부가 `status × transport_mode × 외부 라벨 활성 여부(zen_ups_labels.is_voided) × 청구 상태(`billing_status`)`에 의존). 이 경우 조건 열에 외부 사실을 명시하고, 외부 사실은 fixture로 고정한다.
2. 조합이 폭발하면 **금전·권한 영향이 큰 행 + 경계값을 우선**하고, 나머지는 사유와 함께 후순위로 기재한다 (전수 망라를 목표로 하지 않는다).
3. 초안 작성 예시는 [B_Kai 보고서 §4-1](../08_Self_Audit/Reviews/231/bkai_review.md) 참조 (`getOrderEditScope`·`canChangeStatus` 매트릭스 초안 — 코드 판독 기반이며 **구현 전 명세·AC와 대조 필요**).

**완료 기준**: 결정표 배열의 길이 = `it.each`로 실행되는 표 기반 테스트 건수(1:1). 결정표 밖의 예외·네거티브 테스트는 별도 `describe`로 분리해 집계한다 *(Riley·B_Kai 조율)*. 분기 커버리지 보고서에서 해당 모듈의 미실행 분기가 0이거나, 남은 분기에 사유가 기재됨.

### 4.2 D2 — 입력 조건 예외

**입력 유형별 필수 점검표** (필드마다 해당 유형 행을 적용):

| 유형 | 반드시 시험할 값 |
|:--|:--|
| 문자열 | 빈 문자열, 공백만, 앞뒤 공백, **최대 길이 -1 / 정확히 / +1**, 한글·영문·중문·이모지·결합문자, 쉼표·따옴표·줄바꿈·`<`·`%`·`\`, 숫자만 있는 문자열 |
| 공백·정규화 변형 *(B_Kai)* | 탭·줄바꿈·NBSP·전각 공백·제로폭 문자·중간 다중 공백, 유니코드 정규형(NFC/NFD), 전각/반각 숫자·기호 |
| 숫자 | 0, 음수, 소수, 매우 큰 값, `NaN`, `Infinity`, 문자열로 들어온 숫자, 소수점 자릿수 초과, **부동소수점 오차(IEEE 754)**, 통화 단위 혼입 *(Riley)* |
| 선택/코드 | `null` vs `undefined` vs `""`(**세 값은 서로 다른 입력**), 미존재 코드, 대소문자 차이, 비활성 코드, **ISO 2자리(`KR`) vs 3자리(`KOR`) 국가코드** *(Riley, DEF-080)* |
| 날짜·시간 | 경계 시각(자정·월말·윤일), 시간대(KST/UTC), 과거·미래 한도 |
| 배열·묶음 | 0건, 1건, N건, 최대 N+1건, 중복 항목, 일부만 유효한 경우, **1건 오류 시 전체 실패/부분 허용 일관성**, **멀티패키지 비대칭**(패키지별 치수·중량·내용물(DOC/NONDOC)이 서로 다른 경우 — Issue #952) |
| 교차 필드 *(B_Kai)* | "A 또는 B 중 하나 필수"(전화/휴대폰), 국가에 따라 필수 필드가 바뀌는 조합(우편번호·도시·주) |
| 전화·주소 등 형식 | 하이픈·괄호·공백 혼입, 자리수 초과, 국제 형식(`+`), 정규화 전/후 저장형 vs 전송형 |
| **레거시 저장분 재통과** *(둘 다 지적)* | 입력 시점에는 막지만 **이미 DB에 저장된 비정규 값**(하이픈 포함 전화, 쉼표 포함 주소)이 재조회·재저장·외부 전송 단계로 넘어올 때 정제되는가 |

**속성 기반 테스트(도입 시)**: 입력 하나하나를 나열하는 대신 **불변식**을 정의하고 무작위 입력으로 위반 여부를 탐색한다. zod 스키마를 입력 생성기로 재사용한다.

```text
불변식 예시
- 어떤 입력이 와도 payload 빌더는 예외를 던지지 않는다 (오류는 반환값으로)
- validate(x)의 오류 메시지는 같은 x에 대해 항상 같다 (결정성)
- normalize(normalize(x)) == normalize(x) (멱등)
- save 후 load한 값 == 정규화된 입력 (왕복 보존)
```

**운영 조건** *(B_Kai)*: 생성기 **seed를 고정**하고(재현성), **실행 시간 상한**을 둔다(CI·로컬 운영 가능성). 생성기 품질이 낮으면 무의미한 탐색·느린 실행이 되므로 **순수 함수 성격이 강한 대상**(입력 검증·정규화·빌더)에 국소 적용한다.

**반례 편입**: 탐색이 찾은 실패 입력은 일회성 디버깅으로 끝내지 않고 **고정 회귀 테스트로 커밋**한다 (R-09와 동일 취지).

### 4.3 D3 — 권한 매트릭스

권한 결함은 **앱 계층(라우팅·서버 액션)과 DB 계층**에서 각각 발생하므로 둘로 나누어 다룬다 *(Riley)*. 앱 계층(D3-A)은 다시 URL 라우팅(`proxy.ts`)과 서버 액션 권한(`rbac.ts`)으로 나뉘며, **두 정의의 불일치 자체가 결함 원인**이다(§1.1-5).

| 구분 | 계층 | 대상 | 방법 |
|:--|:--|:--|:--|
| **D3-A** | URL 라우팅·서버 액션 | `proxy.ts`·`routes.ts`의 라우트 가드, `rbac.ts`의 액션 권한 | `역할 × 라우트/액션 → 허용/거부` 매트릭스. 라우팅과 권한 정의의 **불일치 자체**를 검사(§1.1-5) |
| **D3-B** | DB (RLS·GRANT) | 테이블 정책, `authenticated`·`service_role` GRANT | `역할 × 테이블 × 연산(SELECT/INSERT/UPDATE/DELETE) × 소유 관계(자기 조직/타 조직/무소속)` — **실DB** |

**D3-B 운영 원칙**
- mock으로는 RLS·GRANT가 평가되지 않으므로 **mock 테스트로 대체 불가**.
- 테스트는 **자기완결형 fixture**(테스트 내부에서 고유 ID로 생성·검증·정리 — SAR-2026-07-27-001, R-08-2). `scripts/seed-local.ts` 계정에 의존하지 않는다 (앞선 테스트가 데이터를 바꾸면 뒤 테스트가 깨지는 flaky 원인).
- **초기 대상 범위 한정(안)**: 전수(모든 테이블×14개 역할(`rbac.ts` USER_ROLES 기준)×4연산)는 조합 폭발이므로 **핵심 멀티테넌시 테이블**부터 — `zen_orders`, `zen_order_packages`, `zen_ups_labels`, `zen_rate_cards`, `zen_invoices`, `zen_agency_shippers` + `service_role`/`authenticated` GRANT 검증 *(Riley 제안, 최종 대상은 PoC에서 확정)*.
- **fixture 공통 헬퍼** *(B_Kai)*: 조직·사용자·역할 셋업(자기 조직/타 조직/무소속)·정리 패턴을 PoC에서 함께 정리해 테스트 작성 비용과 flaky 위험을 줄인다. **현행 패턴이 이미 있다**: `tests/integration/ups-edit-before-registration.test.ts`의 `makeJwt`·`makeSessionClient`·`setupFixture`·`cleanupFixture`(고유 UUID 자기완결 fixture + JWT 세션으로 실DB RLS 조회, TC-339-INT-⑤), `def-b151-ups-product-guard.test.ts`(TC-336-RLS), `iss1075-order-items-rls-insert.test.ts` *(Riley 확인, Aiden 확인)*. PoC 1단계에서 이를 공통 헬퍼로 추출한다.
- 신규 테이블·정책 추가 시 매트릭스에 행을 추가하지 않으면 완료로 인정하지 않는다. 이때 '매트릭스'는 문서 커버 맵이 아니라 **실DB 권한 테스트 파일 안의 매트릭스 데이터(배열)** 이며 위치는 PoC 단계 1에서 확정한다(문서 커버 맵은 §5.3대로 PR에서 직접 수정하지 않는다).

### 4.4 D4 — 외부 연동 계약 (SHXK/UPS 등)

- 외부 명세(필수/선택, 타입, 길이 제한, 허용 값)를 **스키마(JSON Schema 또는 zod)로 한 번 정의**하고, payload 빌더의 출력을 이 스키마로 검증한다. 필드가 하나씩 뒤늦게 발견되는 패턴(B-054→055→059→144→145→146→153)을 구조적으로 차단한다.
- **스키마의 기준은 "연동 경로상 가장 엄격한 하류(Downstream) 제약"이다** *(Riley)*. 중계 API(SHXK) 공식 명세보다 하류 캐리어(UPS) 실측 제한이 더 엄격해 결함이 난 전례가 있다(`shxk-limits.ts` 주석: 품명 SHXK 500자 vs UPS 실측 35자, 전화 SHXK 100자 vs 15자리).
- **명세와 실제 응답이 충돌하면 실측을 우선**한다 *(B_Kai 제안 — 우선순위·기록 위치 명시)*. 기록 위치: 스키마·상수 파일의 근거 주석(`shxk-limits.ts` 방식) + 명세 출처·버전. R-12(명세-코드 동기화)와 연결해 Ds-11에도 환류한다. **Ds-11(전사적 API 상세 명세서)의 현행 위치는 `docs/02_Analysis/Ds_11_API_상세_명세서.md`**(554줄, 마지막 수정 2026-07-15)이다. 다만 2026-07-15 이후 신규 Server Action 파일 7개가 이 문서에 파일명으로 언급되지 않고, 303 가이드 등 4곳은 구 경로(`docs/03_Design/`)를 가리킨다(§10 #11).
- 외부 응답 오류(거부 사유)로 새 제한이 발견되면 **스키마에 먼저 추가**한 뒤 코드를 고친다.
- **역할 분담** *(Riley)*: E2E는 외부 API를 실호출하지 않고 로컬 Mock/Virtual Provider를 기본으로 하며(인증키·외부 상태 의존 제거), payload 규격 자체는 이 **스키마 계약 테스트(단위 계층)에서 100% 검증**한다.

### 4.5 D8 — 실패 관측성 정적 검사

GOV_COMMON의 "실패 관측성 의무"(반환 전 `logger.error/warn`)는 현재 사람의 검토에 의존한다. 이를 **정적 검사 규칙(lint 또는 AST 스크립트)** 으로 자동화한다.
- 대상: `{success:false}`·`{error:…}`·`null` 반환 지점, `catch` 블록의 에러 객체 폐기.
- 위반을 신규 코드에서는 차단하고, 기존 코드는 위반 목록을 IMP로 관리한다. 위반 수는 커버 맵의 자동 산출 열(§5.2)로 쓴다.

### 4.6 D6·D7 — 정합성·동시성

- **왕복 보존**: 저장 → 재조회 → 재저장 후 값이 변하지 않는가 (B-056 오더 수정 시 아이템 소실 유형). **스냅샷 보존**(요율·주소 스냅샷 — DEF-099·088)과 **마이그레이션↔TypeScript 타입·시드 동기화**(DEF-067·078) 포함.

### 4.8 D8·D9와 연결되는 단언 원칙 — 에러 코드 단언 *(Riley 제안)*

서버가 한글 문장을 반환하고 테스트가 `toContain('…')`로 그 문자열에 결합하면, 문구 수정이나 다국어 전환 시 테스트가 대량으로 깨진다(취약한 테스트). **실패 케이스는 자연어 메시지 대신 명시적 에러 코드(`errorCode`) 또는 구조화된 필드 경로를 단언한다.** (적용 시점은 §10 #9 — 로케일 정합화 Task와 정합 확인 필요.) **과도기 규칙**: 에러 코드가 도입되지 않은 모듈은 export된 에러 메시지 상수(예: `UPS_REGISTERED_EDIT_BLOCK_MESSAGE`) 또는 구조화 필드 경로(`path`) 단언을 허용하고, 하드코딩한 부분 문자열(`toContain('권한')` 등)만 금지한다. 에러 코드 의무화는 신규 액션과 에러 코드 리팩토링(307 §2.2)을 적용한 모듈부터 단계적으로 발효한다 *(2차 검증 합의)*.

### 4.9 사전 도출 절차 (Shift-left) — 결함이 나기 전에 케이스를 만든다

**시나리오 단위 사전 도출 (E2E·UAT)** — 단위·계약 테스트로는 드러나지 않는 흐름은 시나리오로 도출한다.

- 사용자 관점 점검은 §4.7 8개 항목(raw key, stale UI, 고아 페이지, 콘솔 오류 등)을 시나리오 체크리스트로 재사용한다.
- **마스터 UAT·E2E 시나리오는 CPO**(PRD·UAT 계획서)가 관장하고, **개별 Issue 착수 시점의 시나리오는 담당 Agent가 도출해 PR 리뷰로 검증**받는다. 구현 Agent는 시나리오를 E2E로 옮길 때 §4.7 단언을 따른다.

## 7. Agent 준수 규칙

1. **도출 소스와 명세 부재 처리** *(B_Kai·Riley 보완)*: 신규 테스트는 명세에서 도출하고 task file에 도출 근거(명세 §)를 기재한다. 근거 우선순위는 **확정된 명세(Ds-11 현행본의 해당 절·105·코드 상수의 근거 주석) > Issue DoD(·AC) > 도메인 규칙·실측 결함**(Ds-11의 현행 위치는 `docs/02_Analysis/`이며 2026-07-15 이후 갱신이 확인되지 않음 — §10 #11. **105 §3 상태 전이는 현행 코드와 불일치하므로 현행화 전에는 근거로 쓰지 않는다** — §8.1). 명세에 없거나 모호하면 **근거 문서(105 또는 상수 파일 주석)를 먼저 갱신**한 뒤 도출하고, 불가피한 가정은 task file에 기록해 Aiden 승인을 받는다 (R-12와 연결).
2. **Worker/Auditor 분리와 선행 테스트 방식** *(Riley·B_Kai·D_Kai 3차 수렴)*: 금전·권한·외부 계약 등 **고위험 모듈은 구현자와 다른 주체가 테스트를 도출·검토**한다(R-01). 구현 전에 **결정표와 선행 테스트를 먼저 확정**해 구현 편향을 차단하되, **R-08(커밋 전 `test:regression` 전체 PASS, `GOV_COMMON.md`)을 깨뜨리는 '실패하는 테스트 커밋'은 금지**한다(pre-commit hook·CI가 차단). 선행 테스트 형태는 **심볼 존재 여부로 나눈다**: **(a) 기존 심볼의 결함 재현·분기 변경 = `it.fails`**(되돌리기 시 FAIL 확인, ReferenceError 등 우연한 예외에 의존 금지 — `it.fails`는 어떤 예외든 "통과"시키므로 미구현 심볼에 쓰면 검증력이 없다) / **(b) 아직 심볼이 없는 신규 = `it.todo`/`describe.skip`**(결정표 고정용이며 **2차에서 `it`로 전환하기 전까지 실적 불인정** — 존재하지 않는 모듈을 import하면 collection 단계 실패로 R-08 위반). 참고: 현재 `tests/` 전체의 `it.fails/todo/skip` 사용은 1건뿐이라 선례가 거의 없다. **진행 방식의 원칙은 (A) 별도 Spec PR이다(Edward 결정 2026-11-13)** — Breaker가 결정표+선행 테스트 PR(`src/` 미수정)을 먼저 머지하고 Worker가 구현 Issue를 수행한다(Riley·B_Kai 선호). **난이도(위험 기준, §4.9)에 따라 분리 운영한다**: 위험 기준 2개 이상(고위험)은 (A)를 적용하고, 그 외 변경에 **(B) 단일 Issue 내 Draft PR 게이트**(1 Issue=1 Agent 유지, 1차 커밋=결정표+선행 테스트 → Aiden 검수 → 2차 구현 커밋, D_Kai 제안)를 허용할지는 **PoC 후 결정**한다(§10 #10). (A)가 R-17 절차에 주는 부담(Issue 2건·머지 순서)은 PoC에서 측정한다. 고위험 외에는 사후 Auditor 리뷰로 단계 적용한다.
3. **검증력 훼손 금지**: 테스트를 통과시키기 위해 단언·기대값·계약 조건을 완화하거나 테스트를 삭제하지 않는다. PR diff에서 기존 단언의 삭제·완화를 점검한다. 불가피하면 **사유·영향 범위·승인자·후속 IMP**를 task file에 기록한다(예외 템플릿).
4. **vacuous 단언 금지와 에러 코드 단언**: `toBeDefined()`·`toBeTruthy()`·단독 `typeof`·의미 없는 `toContain` 등 값을 확정하지 않는 단언만으로 DoD를 충족했다고 보고하지 않는다(대표 금지 패턴·허용 예외를 리뷰 체크리스트에 명시, 정규식/AST 점검 가능). 실패 케이스는 **자연어 메시지 대신 에러 코드·구조화 필드**로 단언한다(§4.8). 단독 사용 금지는 **구체적 기대값 단언(`toBe`/`toEqual`)과 병기하면 허용**하며, 안티패턴 목록은 `210_AI_AGENT_REWORK_PREVENTION_GUIDE.md`의 §2 #3(vacuous test 6종 메커니즘)과 174행 체크리스트(흔한 vacuous-test 형태)를 따른다 *(Riley·D_Kai 조율)*.
5. **반례 영구 편입**: 탐색·결함 분석으로 발견한 실패 입력은 회귀 테스트로 커밋하고 LIVE_REGRESSION_TEST_MAP에 등재한다(R-09). 테스트명에 DEF/Issue 링크를 둔다. (회귀 맵 용량 선행 해소 — §5.1)
6. **클래스 단위 수정과 범위 경계** *(Riley)*: DEF/SAR 해소 시 "같은 원인 클래스가 다른 모듈에 존재하는가"를 점검해 **탐색 결과(검색 키워드·모듈·없음 사유)를 보고서에 필수 기재**한다. 단, **담당 파일 범위 밖이면 직접 수정하지 않고 R-15(IMP)/R-18(DEF)로 분리 등록**한다 (파일 소유권 R-19 준수, PR 비대화 방지).
7. **커버 맵 변동 기재**: 신규 기능·결함 수정 PR은 해당 모듈의 커버 맵 칸 변동을 **PR 본문에만** 기재한다(파일 직접 수정 금지 — §5.3). 커버 맵 신설 승인 후 시행하며, 초기에는 변경 모듈만 점진 적용한다.
8. **Agent 산출 테스트 샘플링 점검** *(B_Kai 제안)*: Agent가 생성한 테스트에 구현 코드를 그대로 옮긴 단언이나 통과 목적의 약한 단언이 섞일 위험이 있다. PoC에서 Agent 산출 테스트를 표본 추출해 **"명세 근거 표기 여부"와 "되돌리기 시 실패 여부"** 를 별도 지표로 점검한다.

### 8.3 단계 3 공정성 조건 *(B_Kai·Riley)*

재현 시험의 판정이 주관적이지 않도록 **착수 전에 아래를 고정**한다.

- 가능하면 D3-B(RLS/GRANT) 실DB 사례 1건을 비교군에 포함.
- **대립 사항의 사전 판정 규칙**(2차 검증): (a) PoC 모듈 내 5건 + 모듈 밖 5건을 재현해 **밖 5건의 추가 검출률이 내부보다 낮거나 같으면 모듈 한정(B_Kai), 높으면 비한정(D_Kai)** (b) 재현 방식은 같은 DEF 1건을 과거 커밋 체크아웃과 수동 재주입으로 2인이 실행해 불일치 케이스는 제외, 3건 중 2건 일치 시에만 지표 반영(D_Kai) (c) '미검출'은 사전 정의 — 현행 회귀 전체 실행 + 해당 DEF 재주입 시 FAIL 없음(B_Kai)

### 8.4 성과 지표 (단계 3 판정용)

- 신규 기법이 **추가로 검출한 결함/위반 수**
- 과거 DEF 재현 시험에서 **현행 대비 추가 검출률**
- 변이 점수 변화 (기준선 대비)
- 소요 비용(작성 시간, CI 시간 증가, flaky 발생)
- Agent 산출 테스트 샘플링 점검 결과(§7-8)

판정 원칙: **비용 대비 추가 검출이 확인되면 확대, 확인되지 않으면 해당 기법은 접는다.** 결과는 Issue/IMP에 기록한다.
