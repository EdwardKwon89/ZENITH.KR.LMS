### 1.3 R-17 "반복 위반 페널티" — 실제로 지켜야 규정이 된다

R-17에는 "동일 유형 위반 3회 누적 시 신규 Task 할당 일시 중단 + 재교육"이라는 명문 조항이 있다. 이 조항 **자체**는 이식 가치가 매우 높지만, **실제로 집행하지 않으면 문서로만 존재하는 죽은 규정이 된다**는 것이 ZENITH_LMS에서 실증된 교훈이다(GitHub Issue #987 — 여러 인원이 3회 기준을 여러 유형에서 반복 초과했음에도 실제 집행이 이뤄지지 않아, 같은 유형의 위반이 계속 재발했다). 신규 프로젝트에 이 조항을 이식할 때는:

- 3회 기준 도달 시 **예외 없이 실제 집행**하거나, 애초에 다른 기준(예: 심각도별 즉시 조치)으로 대체할 것 — "일단 만들어두고 실제로는 안 지킨다"가 가장 나쁜 선택지다.
- "위반 횟수를 소급 면제/미가산 처리"하는 예외를 **여러 번 반복 적용하지 않는다** — 이 자체가 카운터를 무력화하는 구조적 허점이 된다.

### 1.4 구조적 패턴 — GUIDE/LIVE 이원화, 공통규칙 인라인 로드

두 가지 구조 패턴은 코드가 아니라 **문서 조직 방식** 자체가 재사용 자산이다:

1. **GUIDE(불변 표준) vs LIVE(현재 진행 상태) 분리**(R-05) — "표준은 잘 안 바뀌고, 진행상태는 매일 바뀐다"는 것을 문서 구조로 분리해 AI 에이전트가 매번 전체를 다시 읽지 않아도 되게 한다.
2. **공통 규칙(GOV_COMMON.md) + 에이전트별 파일(CLAUDE.md/AGENTS.md/GEMINI.md)의 인라인 로드 구조** — `@GOV_COMMON.md` 형태로 공통 규칙을 한 곳에 두고, 각 에이전트 전용 파일(세션 초기화 절차, 커밋 태그 등 도구별로 다른 내용)은 별도 유지한다. 이 분리 덕분에 R-01~R-20 같은 공통 규칙을 한 번만 고치면 모든 에이전트 도구에 자동 반영된다.

### 1.5 신규 채택 전 반드시 확인할 것 — 도구 실제 연결 여부

R-06(Context7 MCP)·R-20(GitNexus MCP) 둘 다 "이 MCP 도구를 우선 사용하라"는 규칙인데, ZENITH_LMS에서 실제로 다음이 확인됐다: **문서에 규칙을 적어놓아도, 각 에이전트의 실행 환경(모델/CLI)에 해당 MCP 서버가 실제로 연결되어 있는지는 별개 문제**다. Team B(비-Claude Code 모델 사용)에 GitNexus MCP가 실제로 연결되어 있는지 확인이 안 된 채로 R-20을 적용해버린 사례가 있다(GitHub Issue #987 코멘트 참조). 신규 프로젝트에서 MCP 기반 규칙을 채택할 때는, **모든 참여 에이전트의 실행 환경에서 실제로 해당 MCP 도구가 호출 가능한지 사전에 확인**한 뒤 규정화할 것.

### 1.6 VIOLATION_TRACKER.md — 가시화엔 실증, 재발방지엔 반증

문서/폴더 관리(206)·Multi-Agent 운영(104/107) 계열 후보를 §1.6 원칙(실제 적용 결과 기준)으로 재검토한 결과, 대부분 채택 기준을 충족하지 못했다. 유일하게 **조건부로 실증된 항목**이 VIOLATION_TRACKER.md다:

- **실증된 부분**: 위반 이력을 태스크와 분리해 단일 파일에 누적 기록하는 방식이, 이번 세션에서 Team B의 반복 위반 패턴(동일 유형·동일 인물)을 실제로 드러내는 데 효과가 있었다(GitHub Issue #987 분석의 근거 자체가 이 파일이었다) — **가시화 도구로는 채택**.
- **반증된 부분**: 그러나 꼼꼼히 기록되는 것과 재발이 실제로 줄어드는 것은 별개였다 — 같은 파일에 계속 기록되면서도 같은 사람의 같은 유형 위반이 반복됐다(§1.3의 R-17 미집행 사례와 동일 근거). **"기록하면 저절로 개선된다"는 기대는 채택 금지** — 반드시 §1.3처럼 실제 조치(할당중단 등)와 짝지어야 의미가 있다.

## 2. RBAC/권한관리 코드 스캐폴드 이식 가이드

### 2.1 재사용할 패턴 (구조 자체는 우수)

`src/lib/auth/rbac.ts` + `guards.ts` + `zen_role_permissions` 테이블 조합은 다음 패턴을 구현한다 — **이 패턴 자체는 이식 가치가 높다**:

```
역할(Role) × 경로/리소스(Path) → 허용 여부
  ├── STATIC_PERMISSIONS: 코드 내 fallback 맵(DB 장애 시 대비)
  ├── zen_role_permissions 테이블: DB 기반 동적 권한(관리자 UI로 CRUD 가능)
  └── checkPermission()/checkPermissionDB(): 서버 액션 진입점에서 호출하는 단일 진입점 함수
```

- `normalizePath()`로 다국어 라우트 접두사(`/ko`, `/en` 등)를 제거하고 순수 경로로 비교하는 방식 — 다국어 라우팅을 쓰는 프로젝트라면 그대로 유용
- 미들웨어(`proxy.ts`) 레벨 화이트리스트와 앱 레벨(`rbac.ts`) 권한표가 **별도 관리**된다는 점 — 두 레벨이 있다는 구조 자체는 정상이나, 아래 §2.2에서 다루는 위험을 안고 있다

### 2.2 반드시 리네이밍/재정의해야 하는 것

- **`USER_ROLES` 13개 열거값**(`ZENITH_SUPER_ADMIN`/`CARRIER`/`CUSTOMS_BROKER`/`AGENCY_SHIPPER` 등) — 전부 ZENITH 물류 도메인 특화. 신규 프로젝트의 실제 역할로 전면 교체 필요
- **`STATIC_PERMISSIONS`의 하드코딩된 경로 목록**(`/admin/ups-rates`, `/logistics`, `/warehouse` 등) — 신규 프로젝트 라우트 구조로 전면 교체
- **`zen_` 테이블 접두사** — 신규 프로젝트 네이밍 컨벤션에 맞게 교체(접두사 자체를 유지할지는 팀 선택)

### 2.3 알려진 구조적 위험 — 반드시 함께 이식할 것

ZENITH_LMS에서 **AGENCY 역할 하나를 여러 권한 체크 지점에 빠뜨리는 사고가 8회 이상 반복**됐다(DEF-114/116/117/DEF-B-002/010/014/017/019). 근본 원인은 "미들웨어 화이트리스트·앱 레벨 권한표·RLS 정책·DB GRANT가 각각 독립적으로 관리되어, 신규 역할 추가 시 네 곳 중 하나를 빠뜨리기 쉬운 구조"다. 이 RBAC 스캐폴드를 이식할 때는 반드시 **304 문서(§4.3)가 제안하는 "역할×리소스×액션을 하나의 선언적 소스에서 코드생성"하는 방향을 함께 검토**할 것 — 스캐폴드만 복사하고 이 교훈을 빠뜨리면 같은 사고가 신규 프로젝트에서도 반복될 가능성이 높다.

## 3. 디자인 시스템(Zen UI) 이식 가이드

### 3.1 컴포넌트 — 그대로 이식 가능

`src/components/ui/`의 `ZenButton`·`ZenCard`·`ZenInput`·`ZenSelect`·`ZenTextarea`·`ZenBadge`·`ZenDataGrid`·`ZenErrorView`·`ZenAurora`·`ZenUI` — 비즈니스 로직과 결합되어 있지 않은 순수 프레젠테이션 컴포넌트다. 그대로 복사해 사용 가능하며, `Zen` 접두사만 신규 프로젝트의 네이밍 컨벤션으로 바꾸면 된다.

### 3.2 디자인 토큰 — 분리 작업 필요

`src/app/globals.css`에 CSS 커스텀 프로퍼티로 토큰이 정의되어 있으나(`--color-brand-*`, `--zen-shadow-*`, `--zen-glass-*` 등), **순수 디자인 토큰(색상·그림자·트랜지션)과 ZENITH 레이아웃 상수(`--sidebar-width: 280px`, `--header-height: 64px` 등)가 한 파일에 섞여 있다.** 예: `--color-accent: #f59e0b; /* Logistics Amber */` — 값 자체는 범용이나 주석이 도메인 특화다.

이식 시:
1. 순수 토큰(색상 팔레트·그림자·트랜지션·폰트 변수)만 별도 `tokens.css` 등으로 분리 추출
2. 레이아웃 상수(사이드바 너비 등)는 신규 프로젝트 화면 구조에 맞게 재정의
3. Tailwind v4 CSS-first 방식(`tailwind.config.*` 파일 없이 globals.css 안에서 `@theme` 등으로 정의)을 그대로 따를지, 별도 config 파일 방식으로 바꿀지는 팀 선택

## 4. 다국어·통화·테마·커스텀필드·워크플로우 이식 가이드

304 문서(Redmine 비교분석) 검토 시 다루지 않았던 나머지 기술 영역을 코드 실사 기준으로 점검한 결과다. 이 다섯 영역은 성숙도 편차가 크다 — **그대로 이식 가능한 것은 하나도 없고, 전부 "패턴은 참고, 구현은 보강 필요"** 등급이다.

### 4.1 다국어(i18n) — 라우팅 골격은 이식 가능, 네임스페이스 충돌 위험 있음

- **구성**: `next-intl`, `src/i18n/routing.ts`(ko/en/zh/ja, 기본 ko) + `src/i18n/request.ts` + `src/app/[locale]/...` 라우트 구조. `messages/{locale}.json`이 기능별 네임스페이스(`Common`/`Navigation`/`Orders`/`UpsInvoice` 등 45개)로 중첩 구성 — flat 구조 아님
- **결함**: 번역키 관련 결함 최소 3건(DEF-115, DEF-061, DEF-B-023). 특히 DEF-B-023은 **네임스페이스를 다른 화면이 재사용하다 28개 키가 충돌**해 페이지당 25건 이상 `MISSING_MESSAGE` 오류가 난 사례 — 네임스페이스 소유권 규칙 부재가 근본원인
- **갭**: 로케일 전환 UI 컴포넌트 자체가 없음 — 라우팅/미들웨어 레벨엔 4개 로케일이 연결돼 있는데 실제 사용자가 언어를 바꿀 방법이 UI에 없음
- **판정**: 라우팅/설정 골격은 그대로 이식. 다만 **네임스페이스 소유권 컨벤션**(어느 화면이 어느 네임스페이스를 쓰는지 명문화)과 **로케일 전환 UI**를 함께 추가해야 재발을 막는다

### 4.2 통화(currency) 처리 — 표시 컴포넌트만 재사용, 변환 로직은 비추천

- **구성**: 공통 변환 유틸리티 없음 — 표시는 `ZenCurrencyDisplay.tsx`(`Intl.NumberFormat` 기반, currency/code-prefix/code-suffix 3종 변형)로 처리하지만, 실제 환율(`applied_exchange_rate`) 값과 변환 로직은 `invoice.ts`/`daily-billing.ts`/`settlement.ts`/`invoice-generator.ts`에 **각각 인라인으로 흩어져 있음**(중앙화 안 됨)
- **결함**: 통화/요율 관련 결함 최소 7건(DEF-B-021 KRW/USD 오표기, DEF-B-032, DEF-B-013/014, DEF-067, DEF-088 등) — 이번 세션에서 다룬 DEF-B-031~034 연쇄도 넓게 보면 같은 계열
- **판정**: `ZenCurrencyDisplay` 표시 컴포넌트만 그대로 재사용. **변환/환율 로직은 이식 비추천** — 중앙화된 단일 함수 없이 여러 곳에 흩어진 구조 자체가 이 세션에서 확인한 결함들의 근본 원인과 같은 패턴(§4.1 GOV_COMMON.md 이식표에서 다룬 "단일 소스" 원칙 위반)이다

### 4.3 화면 Skin/테마 — 이식 비추천, 처음부터 다시 설계할 것

- **구성**: `next-themes` 패키지가 `package.json`에 있으나 **`ThemeProvider`/`useTheme` 사용처가 코드 전체에 단 한 곳도 없음**(설치만 되고 미사용). 다크모드는 Tailwind `dark:` 유틸리티 클래스를 컴포넌트마다 수동으로 흩뿌리는 방식이며, `data-theme` 토글이나 `localStorage` 영속화 없이 OS `prefers-color-scheme`에만 반응
- **결함**: DEF-B-030(상세 테이블이 요약 테이블 마크업을 복사하면서 `dark:` 변형을 통째로 누락)이 이 취약성을 정확히 보여줌 — 테마 적용이 컴포넌트별 수기 작업이라 강제 메커니즘이 없음
- **판정**: **이식 비추천**. 설치돼 있는 `next-themes`를 실제로 연결(ThemeProvider + 토글 + 영속화)하고, 시맨틱 컬러 토큰(예: `bg-surface`, `text-default`)을 통해 다크모드가 컴포넌트 작성자의 수기 작업 없이도 자동 적용되는 구조로 새로 설계하는 게 낫다

### 4.4 커스텀필드 — 304 문서 §4.4 참조

이미 [304 문서](304_RBAC_CUSTOMFIELD_WORKFLOW_ENGINE_REVIEW.md) §4.4에서 다뤘다 — **순수 EAV(Redmine 방식)는 기각, JSONB+필드정의 테이블 하이브리드를 권장**(Postgres 기반 프로젝트 한정). ZENITH_LMS엔 현재 커스텀필드 기능 자체가 없어 이식할 기존 코드가 없고, 신규 프로젝트에서 필요해지면 304 §4.4의 설계 원칙부터 적용할 것.

### 4.5 워크플로우 엔진 — 304 문서 §4.5 참조 + DECISIONS.md #13 진행상황 확인

이미 [304 문서](304_RBAC_CUSTOMFIELD_WORKFLOW_ENGINE_REVIEW.md) §4.5에서 다뤘다 — 도메인에 **"변형 축"**(ZENITH의 `transport_mode`처럼, 같은 리소스가 축에 따라 다른 규칙을 갖는 경우)이 있는지 먼저 확인하고, 있다면 (역할×변형×상태전이) 관계형 트리플 테이블로 처음부터 설계할 것을 권장한다. ZENITH_LMS 자체는 이 설계를 아직 적용하지 않았고(`.planning/DECISIONS.md` #13, 통합 vs 분리 여부 보류 중) 기존 `canChangeStatus()`가 변형 축 없이 역할×상태만 다루는 상태다 — 신규 프로젝트라면 이 갭을 처음부터 피할 수 있다.

## 6. 저장소(리포지토리) 구조 방안 — 멀티 리포 분리 검토

Edward 요청(2026-08-03/04)에 따라 검토한다: ZENITH_LMS는 현재 단일 리포 운영이며, 이 §6은 **ZENITH_LMS 자체를 재구성하는 방안이 아니라 신규 프로젝트를 처음부터 멀티 리포로 착수할 때의 방안**이다(§0 원칙과 동일 — 실제 분리 작업은 이 문서 범위 밖).

### 6.0 배경 — ZENITH_LMS에서 실측 확인된 문제

- `docs/` 67MB 중 59MB가 바이너리(스크린샷·PDF·엑셀, 주로 `99_Manual/`의 E2E 증적)이고, 소스코드(`src/`)는 3.5MB에 불과 — 바이너리가 코드의 약 17배.
- `.git` 143MB 중 상당 부분이 이 바이너리 이력. `.gitattributes`/git-lfs가 설정되어 있지 않아, 같은 스크린샷 파일이 커밋마다 풀사이즈로 **7~8버전씩 누적**되는 것을 실측 확인(예: `docs/99_Manual/E2E_26_Result/01_label_not_issued.png`).
- 원인은 "원자료(스크린샷 등)가 분석/설계 단계에서 1회성으로 소비된 뒤 `.md`로 증류되고, 이후에는 재조회 빈도가 사실상 0에 가까운" 라이프사이클과 "git은 모든 버전을 영구 보존한다"는 전제가 서로 안 맞기 때문.

### 6.1 분리 기준 — "바이너리냐/텍스트냐"·"변경빈도"가 아니라 "코드와의 결합도"

신규 프로젝트에서 멀티 리포를 설계할 때 가장 중요한 판단은 파일 형식(바이너리 vs 텍스트)이나 변경 주기(수시 vs 주/월 단위)가 아니라, **"이 문서가 코드 커밋과 원자적으로 함께 검증돼야 하는가"**다.

- R-12(API 사양 변경 시 명세서 선제 업데이트)·R-04(LIVE_ 체크리스트가 완료판정의 근거)처럼, 코드와 **같은 PR/같은 커밋 시점**에 함께 검증돼야 하는 문서(API 명세·DB 스키마 문서·LIVE_ 체크리스트)를 코드와 다른 리포로 쪼개면 이 동시성 검증 자체가 깨진다 — 멀티 리포의 전형적 실패 패턴(원자적 커밋 불가)이 여기서 발생한다.
- 반대로 코드 커밋과 무관하게 독립적으로 생성·소비되는 자료(원자료/스크린샷/사업관리 보고서 등)는 결합도가 낮아 분리해도 이 문제가 생기지 않는다. 실제로 ZENITH_LMS에서도 결합도 낮은 자료(`99_Manual`·`80_RawData`·`98_images`)가 바이너리 대부분과 거의 정확히 겹친다 — 두 기준(결합도/저빈도)이 우연이 아니라 서로 연동되는 경향이 있다.

### 6.2 권장 구조 — 2-리포 분리 (Core / Reference)

| 리포 | 성격 | 포함 대상 |
|:---|:---|:---|
| **리포 A (Core)** | 코드와 결합도 높음, 수시 변경, 원자적 커밋 필요 | 소스코드 전체 + `00_GUIDE`(거버넌스, §1) + API 명세·DB 스키마 문서(§1.2 R-11/R-12 대상) + LIVE_ 체크리스트/SAR(R-04/R-13 대상) + `.agent/`(Task 관리, §1.2 R-16/R-17) + 방법론/설계 문서 |
| **리포 B (Reference/Archive)** | 코드와 결합도 낮음, 저빈도 참조, 원자적 커밋 불필요 | 원자료(스크린샷·PDF·엑셀 등 분석/설계 1회성 소비 자료), R-10/R-17 감사 증적(E2E 스크린샷 등 완료 후 재조회 목적), 사업관리 보고서(진척/위험/주간/월간 — 코드 커밋 시점과 무관하게 독립 생성) |

세 번째 리포(사업관리 문서 전용)는 기술적 필요보다 **접근권한 분리**(경영진 전용 vs 개발자 공개 등)가 조직적으로 필요할 때만 고려 — 기본값은 2-리포.

### 6.3 리포 B의 바이너리 관리 원칙

- git-lfs 채택 여부를 **자료 성격별로 구분**해서 결정할 것 — 일괄 적용이 능사가 아니다.
  - "1회성 소비 후 재조회 안 됨"이 명확한 원자료(분석 착수 단계의 스크린샷·PDF 등)는 애초에 **버전 이력 자체에 가치가 없다** — git-lfs보다 "최신본만 유지, 과거본은 커밋 이력에 안 남기는" 정책(별도 브랜치에서 스쿼시, 혹은 최종본만 커밋)이 더 단순하고 충분.
  - R-10/R-17처럼 **이력 자체가 감사 증적**인 파일(이 스크린샷이 이 시점에 이 상태였다는 것이 증거)은 git-lfs 적용 권장 — 포인터만 메인 이력에 남아 리포 크기를 억제하면서도 버전 추적은 유지.
- 착수 시점에 `.gitattributes`로 이미지/PDF/xlsx 확장자를 미리 lfs 트래킹 대상으로 지정해두면, ZENITH_LMS처럼 나중에 143MB가 쌓인 뒤 파괴적인 히스토리 재작성(`git filter-repo` 등, 전원 재클론 필요)을 하는 상황 자체를 예방할 수 있다.

### 6.4 상호 참조 방식 — 느슨한 링크 권장, Submodule/Subtree 비권장

| 방식 | 판정 | 사유 |
|:---|:---:|:---|
| Git Submodule | 비권장 | 정확한 커밋 고정은 가능하나 UX 마찰이 크고(detached HEAD, 포인터 갱신 누락 빈발), 저빈도 참조자료에는 관리 비용이 이득보다 큼 |
| Git Subtree | 비권장 | 참조 리포의 바이너리 이력을 메인 리포로 다시 끌어들여, 애초에 분리하려던 목적(리포 A 경량화) 자체를 무효화함 |
| **느슨한 링크 참조**(리포 A 문서에서 리포 B의 URL을 직접 하이퍼링크) | **권장** | 빌드/실행 시점에 물리적으로 필요한 게 아니라 사람·에이전트가 "가서 확인"하는 용도이므로, 별도 git 연결 기능 없이 URL 링크 + 리포 B 내부의 Task/DEF 번호 ↔ 증적파일 매핑 인덱스(매니페스트) 문서만으로 충분 |

Submodule/Subtree는 원래 "빌드 시점에 다른 리포 내용이 물리적으로 필요한 경우"(공유 라이브러리 등)를 위한 도구라, 결합도가 낮다고 판단해 리포 B로 뺀 자료에 다시 적용하면 목적과 수단이 어긋난다.

### 6.5 신규 프로젝트 착수 시 실행 순서 (제안)

1. 리포 A(Core) 생성 — 소스코드 + §1~§5의 이식 대상 거버넌스/설계 문서
2. 리포 B(Reference) 생성 — 착수 즉시 `.gitattributes`로 이미지/PDF/xlsx 등을 lfs 트래킹 대상 지정(§6.3), "1회성 원자료"와 "감사 증적"을 하위 폴더로 구분
3. 리포 A의 `00_GUIDE`에 "리포 B 참조 규칙"(URL 링크 컨벤션, 매니페스트 위치)을 명문화 — 이 §6.4를 그대로 이식
4. 206 방식(Type A/B/C 문서 분류)을 적용하되, "리포 A/B 중 어디에 둘지"를 결합도 기준(§6.1)으로 판단 기준에 추가

## 7. Task 관리 체계(R-16/R-17) 이식 가이드 — 도구·스크립트·GitHub/ClickUp 연동

§1.2/§1.3/§1.6은 R-16/R-17을 **규정 텍스트 수준**에서만 다뤘다. Edward 요청(2026-08-04)에 따라 §2(RBAC)·§3(디자인시스템)과 동급으로 **실제 도구·스크립트·GitHub 자동화**를 코드/워크플로우 실사 기준으로 재검토한다.

### 7.1 실사 인벤토리 — 실제로 존재하는 도구

| 자산 | 위치 | 성격 |
|:---|:---|:---|
| 채번 스크립트 | `scripts/next-task-number.sh`, `next-def-number.sh` | `.agent/ACTIVE_TASK.md`+`.agent/tasks/`(또는 `defects/`) 파일명을 **텍스트로 grep해서 최대값+1을 계산**하는 방식 |
| 커밋 해시 삽입 | `scripts/insert-commit-hash.sh` | R-17 완료보고 시 해시 수기 타이핑 오류 방지 |
| 워크트리 격리 | `scripts/agent-worktree-init.sh` | 페르소나별 영속 워크트리 자동 생성/재사용 |
| Task 실행 명령 템플릿 | `opencode.json`의 `check-R17-DoD` 등 | **OpenCode 전용 명령 정의**(Claude Code의 Skill과 다른 메커니즘) — R-17 절차를 프롬프트 템플릿으로 인라인 |
| GitHub Issue → ACTIVE_TASK.md 동기화 | `.github/workflows/sync-issue-to-active-task.yml` | Issue 이벤트(생성/라벨/종료 등) 발생 시 `GH_ISSUES_SYNC` 블록 재생성. Branch protection 때문에 봇이 직접 push 못 하고 **PR만 생성 → Aiden 수동 병합** |
| Issue 레이블 ↔ GitHub Project 상태 동기화 | `sync-label-to-project.yml`(실시간, 이벤트 트리거) + `sync-project-to-label.yml`(수동 `workflow_dispatch`만) | **완전한 양방향이 아니다** — 개인 계정 리포는 `projects_v2_item` 웹훅을 지원하지 않아 역방향(Project→레이블)은 실시간 자동화가 불가능하고 수동 전체 재동기화로 대체돼 있음(Organization 전환 시 해소 예정) |
| Task 파일 템플릿 | 없음 | `.agent/tasks/*.md`는 **정식 템플릿 파일 없이 기존 파일 구조를 관례적으로 복제** — 재사용성 낮음 |

**이식 판정**: 채번 스크립트류는 §7.2의 설계에 따라 이식 여부가 갈린다(그대로 vs 불필요). 워크트리 격리·커밋해시 삽입은 그대로 이식 가치 높음. OpenCode 명령 템플릿은 사용 에이전트 툴체인에 맞게 재구현 필요(Claude Code라면 `.claude/skills/`로). GitHub Actions 동기화 3종은 **패턴 자체(레이블↔상태 필드 매핑, 이벤트 기반 트리거)는 이식 가치 높지만, "개인 계정 vs Organization" 플랜 제약을 신규 프로젝트 착수 전에 반드시 먼저 확인**할 것 — ZENITH_LMS는 이걸 사후에 발견해 회피 설계(수동 dispatch)로 우회했다.

### 7.2 Q1 — GitHub Issue/PR 중심으로 처음부터 간다면 `ACTIVE_TASK.md`가 불필요한가?

**핵심 근거**: `next-task-number.sh`/`next-def-number.sh`가 존재하는 이유 자체가 "GitHub의 원자적 자동 채번(Issue 번호는 리포 전체에서 절대 중복되지 않음)을 쓰지 않고, `TASK-NNN`이라는 별도 채번 체계를 수동/스크립트로 병행 관리하기 때문"이다. 그 대가로 ZENITH_LMS는 실제 채번 충돌 사고를 반복 겪었다(Issue #358 — TASK 번호 중복, PR#309/313/331/353 등 / Issue #773 — DEF 번호 3연속 충돌). **처음부터 GitHub Issue 번호 자체를 Task ID로 쓰면 이 충돌 자체가 구조적으로 불가능해지고, 채번 스크립트·팀 접두사 체계(R-19)·이 두 Issue가 기록한 사고 이력 전부가 애초에 필요 없어진다.**

다만 로컬 인덱스 파일(`ACTIVE_TASK.md`류) 자체를 완전히 없애는 것과는 별개 문제다 — 남겨야 할 이유:
- R-16이 "세션 시작 시 `ACTIVE_TASK.md` 확인"을 요구하는 이유는 **로컬 파일 1회 읽기가 매 세션·매 에이전트마다 GitHub API를 호출하는 것보다 압도적으로 저렴**하기 때문(ZENITH 기준 Task 453건 규모에서 API 페이지네이션/레이트리밋 부담은 실질적이다)
- "내 팀 담당 중 P1이 몇 건, 뭐가 막혀있나"를 한눈에 스캔하는 용도는 평문 표가 GitHub Issue 목록 필터보다 에이전트 파싱에 유리

**권장안**: 파일을 없애지 말고 **역할을 바꾼다** —
1. Task ID = GitHub Issue 번호 그대로 사용(별도 접두사·채번 스크립트 폐지)
2. `ACTIVE_TASK.md`는 이미 절반은 그렇듯(`GH_ISSUES_SYNC` 블록) **100% 자동생성 read-only 캐시**로 전환 — 지금처럼 "팀별 상세 표"를 별도로 수기 관리하지 않는다. 커밋 해시·테스트 결과 등 상세는 Issue/PR 본문·코멘트에만 존재하게 하고, 인덱스는 그 링크만 가진다.
3. 이렇게 하면 R-17 완료보고 절차가 지금처럼 "task file 🔔 → `ACTIVE_TASK.md` 🔄→🔔 → GH 라벨 변경" **3중 수기 반영**이던 것이 "GitHub Issue/PR 상태 변경 1곳 → 나머지는 자동 파생" 구조로 줄어든다 — 이 3중 반영 자체가 ZENITH_LMS에서 R-17 위반(상태 미변경·해시 미기재)의 상당수가 발생하는 지점이었다.

### 7.3 Q2 — ClickUp 연동 방안

- ClickUp은 **네이티브 GitHub 연동**을 제공한다(브랜치명/커밋메시지/PR 제목에 ClickUp Task ID를 참조하면 자동 링크, PR 머지 시 Task 상태 자동 전환). 단순 연동은 이 기본 기능으로 충분 — 커스텀 코드 불필요.
- 더 세밀한 자동화(예: `team:x` 라벨이 붙은 GitHub Issue가 열리면 자동으로 ClickUp Task 생성)가 필요하면, ZENITH_LMS가 이미 `sync-label-to-project.yml`로 검증한 패턴(이벤트 트리거 → 외부 API 호출)을 그대로 재사용 — 호출 대상만 GitHub GraphQL(Project V2)에서 ClickUp REST API로 바꾸면 된다.
- **양방향 실시간 동기화는 처음부터 만들지 말 것을 권장**한다 — ZENITH_LMS가 정확히 이 패턴(Project 상태 ↔ Issue 레이블 양방향)을 시도하다가 "개인 계정 리포는 역방향 웹훅 미지원"이라는 플랫폼 제약에 부딪혀 결국 수동 dispatch로 물러난 전례가 있다(§7.1). GitHub↔ClickUp도 유사한 플랜/권한 제약에 부딪힐 가능성이 높으므로, **단방향(GitHub Issue 생성 → ClickUp Task 자동 생성/상태 갱신)으로 시작하고, 역방향이 실제로 필요해졌을 때만 검증 후 추가**한다.

### 7.4 Q3 — `ACTIVE_TASK.md` · GitHub Issue/PR · ClickUp 상호 연계 및 운영안

세 시스템에 **동일 상태값을 두 곳 이상이 "쓰기 권한"으로 갖지 않도록** 레이어별로 소유권을 하나씩만 지정한다(양방향 실시간 동기화는 드리프트의 근원이라는 게 §7.1의 Project↔레이블 사례로 이미 실증됨):

| 레이어 | 시스템 | 역할 | 쓰기 권한 |
|:---|:---|:---|:---|
| **1. 엔지니어링 실행 기록(System of Record)** | GitHub Issue + PR | "코드 작업이 실제로 됐는지/리뷰됐는지/머지됐는지"의 유일한 진실 | 에이전트·팀 리더·Aiden |
| **2. 로컬 에이전트 캐시(속도 전용)** | `ACTIVE_TASK.md` | R-16 세션 시작 시 빠른 로컬 조회 — §7.2 권장안대로 100% 자동생성 | 없음(자동생성 전용, 수기 편집 금지) |
| **3. 사업/PM 뷰** | ClickUp | GitHub Issue로부터 단방향 파생 + PM 전용 필드(사업 우선순위·일정·리소싱)로 보강 | PM/팀 리더(PM 전용 필드만), 엔지니어링 상태는 읽기전용 |

이 구조면 이전에 검토한 사업관리 보고서(진척/위험/주간/월간, §07_Project_Management 논의)도 ClickUp 대시보드에서 자동 산출 가능해져, 수기 보고서 작성 부담이 줄어든다.

### 7.5 Q4 — 사내(on-premise)/local Git 플랫폼 운영 검토

현재 GOV_COMMON.md/R-16~R-20 전체가 `gh` CLI·GitHub Actions·GitHub API에 강하게 결합돼 있다는 전제 위에서 비교한다.

| 옵션 | 마이그레이션 비용 | 비용 | 적합 조건 |
|:---|:---|:---|:---|
| **GitHub Enterprise Server(자체호스팅)** | **낮음** — `gh` CLI/API/Actions가 사실상 동일하게 동작, 기존 R-16~R-20 자동화 그대로 이식 가능 | 높음(엔터프라이즈 라이선스, 인프라/HA 운영 부담) | 사내망 격리·데이터 레지던시가 목적이고, 기존 GitHub 기반 자동화를 그대로 유지하고 싶을 때 |
| **GitLab(자체호스팅 CE/EE)** | **높음** — `gh`→`glab`, GitHub Actions→GitLab CI YAML 재작성, 이 문서의 R-16~R-20 자동화 전부 재구현 필요 | CE는 무료 | 비용이 우선이고 워크플로우 재작성 리소스가 있을 때. 성숙한 자체호스팅 생태계 |
| **Gitea/Forgejo** | 중간(API가 GitHub과 유사해 일부 호환) | 매우 낮음(경량) | 소규모·저예산. 다만 Actions류 CI 성숙도가 낮아, 이 프로젝트처럼 자동화 의존도가 높은 워크플로우엔 비권장 |

**우선 확인할 것**: "사내 운영"이 요구하는 게 실제로 무엇인지 먼저 명확히 할 것 — ① 데이터 레지던시/네트워크 격리가 목적이면 GitHub Enterprise Server가 마이그레이션 비용 최소, ② 순수 비용 절감이 목적이면 GitLab CE, ③ 만약 목적이 "접근 통제"뿐이라면 굳이 자체호스팅 없이 **GitHub.com Private repo + SSO/IP allowlist**만으로 해결될 수도 있음(마이그레이션 비용 0) — 이 경우가 아닌지 먼저 배제할 것.
