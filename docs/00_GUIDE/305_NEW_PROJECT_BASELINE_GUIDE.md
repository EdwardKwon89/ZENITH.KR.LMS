## 0. 이 문서의 성격과 범위

Edward 지시(2026-07-31)에 따라 작성한다: 실제 파일 추출/새 저장소 생성 작업은 하지 않고, **"새 저장소" 기준으로 재활용 항목·수정 조정 사항을 문서로만** 남긴다. 범위는 세 가지 — **① 거버넌스/방법론 ② RBAC/권한관리 코드 스캐폴드 ③ 디자인 시스템(Zen UI)**.

**§1.6부터의 채택 원칙(Edward 지시, 2026-07-31)**: 이식 후보는 "이론적으로 좋아 보이는가"가 아니라 **"이 프로젝트에서 실제로 적용해 본 결과가 의미 있었는가"**로 검증한다. 실제 사고를 막았거나 실제로 반복 사용된 증거가 있는 항목만 채택하고, 문서로만 존재하거나 아직 채택되지 않은 제안, 실제로 시도했다가 폐기된 것은 "반증 사례"로만 남긴다.

### 1.3 R-17 "반복 위반 페널티" — 실제로 지켜야 규정이 된다

R-17에는 "동일 유형 위반 3회 누적 시 신규 Task 할당 일시 중단 + 재교육"이라는 명문 조항이 있다. 이 조항 **자체**는 이식 가치가 매우 높지만, **실제로 집행하지 않으면 문서로만 존재하는 죽은 규정이 된다**는 것이 ZENITH_LMS에서 실증된 교훈이다(GitHub Issue #987 — 여러 인원이 3회 기준을 여러 유형에서 반복 초과했음에도 실제 집행이 이뤄지지 않아, 같은 유형의 위반이 계속 재발했다). 신규 프로젝트에 이 조항을 이식할 때는:

- 3회 기준 도달 시 **예외 없이 실제 집행**하거나, 애초에 다른 기준(예: 심각도별 즉시 조치)으로 대체할 것 — "일단 만들어두고 실제로는 안 지킨다"가 가장 나쁜 선택지다.
- "위반 횟수를 소급 면제/미가산 처리"하는 예외를 **여러 번 반복 적용하지 않는다** — 이 자체가 카운터를 무력화하는 구조적 허점이 된다.

### 1.4 구조적 패턴 — GUIDE/LIVE 이원화, 공통규칙 인라인 로드

두 가지 구조 패턴은 코드가 아니라 **문서 조직 방식** 자체가 재사용 자산이다:

1. **GUIDE(불변 표준) vs LIVE(현재 진행 상태) 분리**(R-05) — "표준은 잘 안 바뀌고, 진행상태는 매일 바뀐다"는 것을 문서 구조로 분리해 AI 에이전트가 매번 전체를 다시 읽지 않아도 되게 한다.
2. **공통 규칙(GOV_COMMON.md) + 에이전트별 파일(CLAUDE.md/AGENTS.md/GEMINI.md)의 인라인 로드 구조** — `@GOV_COMMON.md` 형태로 공통 규칙을 한 곳에 두고, 각 에이전트 전용 파일(세션 초기화 절차, 커밋 태그 등 도구별로 다른 내용)은 별도 유지한다. 이 분리 덕분에 R-01~R-20 같은 공통 규칙을 한 번만 고치면 모든 에이전트 도구에 자동 반영된다.

### 1.5 신규 채택 전 반드시 확인할 것 — 도구 실제 연결 여부

R-06(Context7 MCP)·R-20(GitNexus MCP) 둘 다 "이 MCP 도구를 우선 사용하라"는 규칙인데, ZENITH_LMS에서 실제로 다음이 확인됐다: **문서에 규칙을 적어놓아도, 각 에이전트의 실행 환경(모델/CLI)에 해당 MCP 서버가 실제로 연결되어 있는지는 별개 문제**다. Team B(비-Claude Code 모델 사용)에 GitNexus MCP가 실제로 연결되어 있는지 확인이 안 된 채로 R-20을 적용해버린 사례가 있다(GitHub Issue #987 코멘트 참조). 신규 프로젝트에서 MCP 기반 규칙을 채택할 때는, **모든 참여 에이전트의 실행 환경에서 실제로 해당 MCP 도구가 호출 가능한지 사전에 확인**한 뒤 규정화할 것.

### 1.6 VIOLATION_TRACKER.md — 가시화엔 실증, 재발방지엔 반증

문서/폴더 관리(206)·Multi-Agent 운영(104/107) 계열 후보를 §1.6 원칙(실제 적용 결과 기준)으로 재검토한 결과, 대부분 채택 기준을 충족하지 못했다. 유일하게 **조건부로 실증된 항목**이 VIOLATION_TRACKER.md다:

- **실증된 부분**: 위반 이력을 태스크와 분리해 단일 파일에 누적 기록하는 방식이, 이번 세션에서 Team B의 반복 위반 패턴(동일 유형·동일 인물)을 실제로 드러내는 데 효과가 있었다(GitHub Issue #987 분석의 근거 자체가 이 파일이었다) — **가시화 도구로는 채택**.
- **반증된 부분**: 그러나 꼼꼼히 기록되는 것과 재발이 실제로 줄어드는 것은 별개였다 — 같은 파일에 계속 기록되면서도 같은 사람의 같은 유형 위반이 반복됐다(§1.3의 R-17 미집행 사례와 동일 근거). **"기록하면 저절로 개선된다"는 기대는 채택 금지** — 반드시 §1.3처럼 실제 조치(할당중단 등)와 짝지어야 의미가 있다.

**검토했으나 채택하지 않은 항목** (투명성을 위해 근거와 함께 남긴다 — 향후 같은 후보를 다시 검토하는 시간 낭비를 막기 위함):

| 후보 | 미채택 사유 |
|:---|:---|
| `206_DOCS_AND_SCRIPT_GOVERNANCE.md`의 "문서번호 수동 확인" 컨벤션 | 소프트 규칙이라 실제로는 계속 드리프트(`04_Database` vs `database`, `09_Checklists` vs `09_TEMPLATES` 중복 폴더가 지금도 존재) — 실제 효과가 있었던 건 이 수동 컨벤션이 아니라 자동화 스크립트(`next-task-number.sh` 등, 이미 §1.2에 반영)였다 |

## 2. RBAC/권한관리 코드 스캐폴드 이식 가이드

### 2.1 재사용할 패턴 (구조 자체는 우수)

`src/lib/auth/rbac.ts` + `guards.ts` + `zen_role_permissions` 테이블 조합은 다음 패턴을 구현한다 — **이 패턴 자체는 이식 가치가 높다**:

```
역할(Role) × 경로/리소스(Path) → 허용 여부
  ├── STATIC_PERMISSIONS: 코드 내 fallback 맵(DB 장애 시 대비)
  ├── zen_role_permissions 테이블: DB 기반 동적 권한(관리자 UI로 CRUD 가능)
  └── checkPermission()/checkPermissionDB(): 서버 액션 진입점에서 호출하는 단일 진입점 함수
```

- `normalizePath()`로 다국어 라우트 접두사(`/ko`, `/en` 등)를 제거하고 순수 경로로 비교하는 방식 — 다국어 라우팅을 쓰는 프로젝트라면 그대로 유용
- 미들웨어(`proxy.ts`) 레벨 화이트리스트와 앱 레벨(`rbac.ts`) 권한표가 **별도 관리**된다는 점 — 두 레벨이 있다는 구조 자체는 정상이나, 아래 §2.2에서 다루는 위험을 안고 있다

### 2.2 반드시 리네이밍/재정의해야 하는 것

- **`USER_ROLES` 13개 열거값**(`ZENITH_SUPER_ADMIN`/`CARRIER`/`CUSTOMS_BROKER`/`AGENCY_SHIPPER` 등) — 전부 ZENITH 물류 도메인 특화. 신규 프로젝트의 실제 역할로 전면 교체 필요
- **`STATIC_PERMISSIONS`의 하드코딩된 경로 목록**(`/admin/ups-rates`, `/logistics`, `/warehouse` 등) — 신규 프로젝트 라우트 구조로 전면 교체
- **`zen_` 테이블 접두사** — 신규 프로젝트 네이밍 컨벤션에 맞게 교체(접두사 자체를 유지할지는 팀 선택)

### 2.3 알려진 구조적 위험 — 반드시 함께 이식할 것

ZENITH_LMS에서 **AGENCY 역할 하나를 여러 권한 체크 지점에 빠뜨리는 사고가 8회 이상 반복**됐다(DEF-114/116/117/DEF-B-002/010/014/017/019). 근본 원인은 "미들웨어 화이트리스트·앱 레벨 권한표·RLS 정책·DB GRANT가 각각 독립적으로 관리되어, 신규 역할 추가 시 네 곳 중 하나를 빠뜨리기 쉬운 구조"다. 이 RBAC 스캐폴드를 이식할 때는 반드시 **304 문서(§4.3)가 제안하는 "역할×리소스×액션을 하나의 선언적 소스에서 코드생성"하는 방향을 함께 검토**할 것 — 스캐폴드만 복사하고 이 교훈을 빠뜨리면 같은 사고가 신규 프로젝트에서도 반복될 가능성이 높다.

## 3. 디자인 시스템(Zen UI) 이식 가이드

### 3.1 컴포넌트 — 그대로 이식 가능

`src/components/ui/`의 `ZenButton`·`ZenCard`·`ZenInput`·`ZenSelect`·`ZenTextarea`·`ZenBadge`·`ZenDataGrid`·`ZenErrorView`·`ZenAurora`·`ZenUI` — 비즈니스 로직과 결합되어 있지 않은 순수 프레젠테이션 컴포넌트다. 그대로 복사해 사용 가능하며, `Zen` 접두사만 신규 프로젝트의 네이밍 컨벤션으로 바꾸면 된다.

### 3.2 디자인 토큰 — 분리 작업 필요

`src/app/globals.css`에 CSS 커스텀 프로퍼티로 토큰이 정의되어 있으나(`--color-brand-*`, `--zen-shadow-*`, `--zen-glass-*` 등), **순수 디자인 토큰(색상·그림자·트랜지션)과 ZENITH 레이아웃 상수(`--sidebar-width: 280px`, `--header-height: 64px` 등)가 한 파일에 섞여 있다.** 예: `--color-accent: #f59e0b; /* Logistics Amber */` — 값 자체는 범용이나 주석이 도메인 특화다.

이식 시:
1. 순수 토큰(색상 팔레트·그림자·트랜지션·폰트 변수)만 별도 `tokens.css` 등으로 분리 추출
2. 레이아웃 상수(사이드바 너비 등)는 신규 프로젝트 화면 구조에 맞게 재정의
3. Tailwind v4 CSS-first 방식(`tailwind.config.*` 파일 없이 globals.css 안에서 `@theme` 등으로 정의)을 그대로 따를지, 별도 config 파일 방식으로 바꿀지는 팀 선택

## 4. 다국어·통화·테마·커스텀필드·워크플로우 이식 가이드

304 문서(Redmine 비교분석) 검토 시 다루지 않았던 나머지 기술 영역을 코드 실사 기준으로 점검한 결과다. 이 다섯 영역은 성숙도 편차가 크다 — **그대로 이식 가능한 것은 하나도 없고, 전부 "패턴은 참고, 구현은 보강 필요"** 등급이다.

### 4.1 다국어(i18n) — 라우팅 골격은 이식 가능, 네임스페이스 충돌 위험 있음

- **구성**: `next-intl`, `src/i18n/routing.ts`(ko/en/zh/ja, 기본 ko) + `src/i18n/request.ts` + `src/app/[locale]/...` 라우트 구조. `messages/{locale}.json`이 기능별 네임스페이스(`Common`/`Navigation`/`Orders`/`UpsInvoice` 등 45개)로 중첩 구성 — flat 구조 아님
- **결함**: 번역키 관련 결함 최소 3건(DEF-115, DEF-061, DEF-B-023). 특히 DEF-B-023은 **네임스페이스를 다른 화면이 재사용하다 28개 키가 충돌**해 페이지당 25건 이상 `MISSING_MESSAGE` 오류가 난 사례 — 네임스페이스 소유권 규칙 부재가 근본원인
- **갭**: 로케일 전환 UI 컴포넌트 자체가 없음 — 라우팅/미들웨어 레벨엔 4개 로케일이 연결돼 있는데 실제 사용자가 언어를 바꿀 방법이 UI에 없음
- **판정**: 라우팅/설정 골격은 그대로 이식. 다만 **네임스페이스 소유권 컨벤션**(어느 화면이 어느 네임스페이스를 쓰는지 명문화)과 **로케일 전환 UI**를 함께 추가해야 재발을 막는다

### 4.2 통화(currency) 처리 — 표시 컴포넌트만 재사용, 변환 로직은 비추천

- **구성**: 공통 변환 유틸리티 없음 — 표시는 `ZenCurrencyDisplay.tsx`(`Intl.NumberFormat` 기반, currency/code-prefix/code-suffix 3종 변형)로 처리하지만, 실제 환율(`applied_exchange_rate`) 값과 변환 로직은 `invoice.ts`/`daily-billing.ts`/`settlement.ts`/`invoice-generator.ts`에 **각각 인라인으로 흩어져 있음**(중앙화 안 됨)
- **결함**: 통화/요율 관련 결함 최소 7건(DEF-B-021 KRW/USD 오표기, DEF-B-032, DEF-B-013/014, DEF-067, DEF-088 등) — 이번 세션에서 다룬 DEF-B-031~034 연쇄도 넓게 보면 같은 계열
- **판정**: `ZenCurrencyDisplay` 표시 컴포넌트만 그대로 재사용. **변환/환율 로직은 이식 비추천** — 중앙화된 단일 함수 없이 여러 곳에 흩어진 구조 자체가 이 세션에서 확인한 결함들의 근본 원인과 같은 패턴(§4.1 GOV_COMMON.md 이식표에서 다룬 "단일 소스" 원칙 위반)이다

### 4.3 화면 Skin/테마 — 이식 비추천, 처음부터 다시 설계할 것

- **구성**: `next-themes` 패키지가 `package.json`에 있으나 **`ThemeProvider`/`useTheme` 사용처가 코드 전체에 단 한 곳도 없음**(설치만 되고 미사용). 다크모드는 Tailwind `dark:` 유틸리티 클래스를 컴포넌트마다 수동으로 흩뿌리는 방식이며, `data-theme` 토글이나 `localStorage` 영속화 없이 OS `prefers-color-scheme`에만 반응
- **결함**: DEF-B-030(상세 테이블이 요약 테이블 마크업을 복사하면서 `dark:` 변형을 통째로 누락)이 이 취약성을 정확히 보여줌 — 테마 적용이 컴포넌트별 수기 작업이라 강제 메커니즘이 없음
- **판정**: **이식 비추천**. 설치돼 있는 `next-themes`를 실제로 연결(ThemeProvider + 토글 + 영속화)하고, 시맨틱 컬러 토큰(예: `bg-surface`, `text-default`)을 통해 다크모드가 컴포넌트 작성자의 수기 작업 없이도 자동 적용되는 구조로 새로 설계하는 게 낫다

### 4.4 커스텀필드 — 304 문서 §4.4 참조

이미 [304 문서](304_RBAC_CUSTOMFIELD_WORKFLOW_ENGINE_REVIEW.md) §4.4에서 다뤘다 — **순수 EAV(Redmine 방식)는 기각, JSONB+필드정의 테이블 하이브리드를 권장**(Postgres 기반 프로젝트 한정). ZENITH_LMS엔 현재 커스텀필드 기능 자체가 없어 이식할 기존 코드가 없고, 신규 프로젝트에서 필요해지면 304 §4.4의 설계 원칙부터 적용할 것.

### 4.5 워크플로우 엔진 — 304 문서 §4.5 참조 + DECISIONS.md #13 진행상황 확인

이미 [304 문서](304_RBAC_CUSTOMFIELD_WORKFLOW_ENGINE_REVIEW.md) §4.5에서 다뤘다 — 도메인에 **"변형 축"**(ZENITH의 `transport_mode`처럼, 같은 리소스가 축에 따라 다른 규칙을 갖는 경우)이 있는지 먼저 확인하고, 있다면 (역할×변형×상태전이) 관계형 트리플 테이블로 처음부터 설계할 것을 권장한다. ZENITH_LMS 자체는 이 설계를 아직 적용하지 않았고(`.planning/DECISIONS.md` #13, 통합 vs 분리 여부 보류 중) 기존 `canChangeStatus()`가 변형 축 없이 역할×상태만 다루는 상태다 — 신규 프로젝트라면 이 갭을 처음부터 피할 수 있다.
