# 실DB 테스트 헬퍼 사용 가이드 (TASK-1161 / Issue #1347)

> 작성: B_Kai (2026-11-18) · 근거: 문서 231 §10 #4 확정, PoC 단계 1 보고서 §5.3·§8.5
> 이 문서는 **가이드**다. 규칙 의무화(R-09 개정)는 Aiden이 별도로 진행한다.

## 1. 왜 필요한가

기존 실DB 통합 테스트 33개 파일은 `psql()`(10개), 수제 `makeJwt()`(4개),
`SUPABASE_SERVICE_ROLE_KEY`(11개)를 파일마다 복붙해 셋업했다.
신규 테스트 1건당 준비 비용이 높고 flaky 원인 추적이 어려웠다(보고서 §5.3).

공용 헬퍼: **`tests/integration/helpers/db.ts`**

## 2. 필수 규칙 5가지

| # | 규칙 | 이유 |
|:-:|:--|:--|
| 1 | **로컬 전용** — URL 호스트가 `127.0.0.1`/`localhost`가 아니면 헬퍼가 즉시 throw | `.env.local`이 원격(Pilot 실데이터)을 가리킬 때 고정 ID `DELETE`가 실DB를 지우는 사고 방지(R-14) |
| 2 | 조직·사용자·프로필은 `createTestOrg()`로만 생성 | 공용 seed 의존 0, 테스트별 고유 접두사, 자기완결 정리 |
| 3 | `makeJwt()`는 `orgId`를 반드시 포함 | 시드 계정의 `app_metadata.org_id = null`로 RLS가 조용히 실패하는 함정 차단 |
| 4 | service_role은 **픽스처 셋업·정리에만** | RLS 동작 검증은 `getUserClient(jwt)`(anon + 사용자 JWT)로 수행 |
| 5 | 추가로 만든 행은 `identity.addCleanup(fn)`, 종료 시 `identity.cleanup()` | 등록 역순(LIFO)·멱등 정리 |

## 3. 최소 사용 예

```ts
import { afterAll } from 'vitest';
import { createTestOrg, getServiceClient, assertOrgIdClaim } from './helpers/db';

describe('신규 실DB 테스트', () => {
  let identity: Awaited<ReturnType<typeof createTestOrg>>;
  let supabase: ReturnType<typeof getServiceClient>;

  beforeAll(async () => {
    supabase = getServiceClient();                 // 셋업 전용
    identity = await createTestOrg({ prefix: 'my_tc' });
    assertOrgIdClaim(identity.jwt, identity.orgId); // JWT ↔ DB 프로필 org_id 대조

    // 테스트가 만든 행은 addCleanup으로 등록
    identity.addCleanup(async () => {
      await supabase.from('my_table').delete().eq('org_id', identity.orgId);
    });
  });

  afterAll(async () => {
    await identity.cleanup();                      // LIFO + 헬퍼 3종 정리, 2회 호출 무해
  });
});
```

## 4. API 요약

| 함수 | 역할 |
|:--|:--|
| `createTestOrg({ prefix?, role?, orgType? })` | `zen_organizations`·`auth.users`·`zen_profiles` 생성 + 고유 접두사 + `cleanup()` 반환 |
| `makeJwt({ sub, email, role, orgId, allowMissingOrgId? })` | HS256 JWT(`app_metadata.org_id` 포함). 음성 테스트만 `allowMissingOrgId: true` |
| `assertOrgIdClaim(token, expectedOrgId)` | JWT 클레임이 DB 프로필 값과 일치하는지 검증 |
| `psql(sql)` | `docker exec … psql -f -`. SQL을 **stdin 전달**(셸 보간 없음). 컨테이너는 env → `config.toml` → 단일 매칭 순, 0/2개면 throw |
| `getServiceClient()` / `getUserClient(jwt)` | service_role / anon+JWT 클라이언트. 둘 다 로컬 가드 적용 |
| `identity.addCleanup(fn)` / `identity.cleanup()` | 등록 역순 실행, 멱등 |

## 5. 트리거 주의사항 (`on_auth_user_created`)

`auth.users` INSERT 시 `handle_new_user()` 트리거가 `raw_user_meta_data.org_id`를 읽어
`zen_profiles`를 **자동 생성**한다(`20260418184000_sync_auth_metadata.sql`).
헬퍼는 트리거를 억제하지 않고, 생성된 프로필의 `role`·`status`·`org_id`를 `UPDATE`로 정정한다.
직접 프로필을 먼저 INSERT하면 트리거와 충돌하므로 **절대 하지 않는다.**

## 6. 신규 테스트 등재

`tests/**`에 새 Vitest 파일을 추가하면 `npm run check:lrtm`의 미등재 래칫에 걸릴 수 있다.

등재 규칙을 따른다(머지 전에는 맵 본문에 섹션 번호를 임의 부여하지 않는다).
