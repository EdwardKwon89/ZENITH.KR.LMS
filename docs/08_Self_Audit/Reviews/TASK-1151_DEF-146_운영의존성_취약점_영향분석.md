## 0. 결론 요약 (먼저 읽을 것)

### 0.1 3줄 요약

1. **`next` 16.2.4는 16.x 계열 보안 권고 33건(치명 5·고 13)의 영향 범위 안에 있다.** 다만 코드 실사 결과 **실질 도달 가능한 것은 미들웨어 우회 3건(HIGH) + Server Action/RSC DoS 3건(HIGH)** 이며, 나머지 치명 항목(원격 코드 실행 계열)은 기능 미사용·플랫폼 조건 불일치로 현재 도달 경로가 없다.
2. **코드 수정 없이 버전 상향 + 락 갱신만으로 critical 2건·high 11건 전량 해소가 가능하다** — `next` 16.4.6, `@sentry/nextjs` 10.78.0, `zod` 4.6.7, `next-intl` 4.15.1, `resend` 6.38.1(P0) + `npm update`(락 내 semver 호환 갱신, P2 ①). 모두 같은 메이저 내 상향이며 React 19.2.4 peer 조건도 충족한다. **단 `xlsx` 1건은 P1(소스 전환)이 필요**하고, `brace-expansion`·`browserslist`·`fast-uri`·`dompurify`·`ws`는 P0가 아니라 **락 갱신으로만** 해소된다(§4.1).
3. **`xlsx`(0.18.5)만 npm 레지스트리에 수정판이 없다.** SheetJS는 npm 배포를 중단하고 자체 CDN으로 이전했다(현행 0.20.3). 대체 여부는 Aiden 설계 확정이 필요하다(§5).

### 1.2 `npm audit`의 한계 — 이 문서가 하는 일

`npm audit`은 **권고의 영향 버전 범위에 현재 버전이 들어가는지만** 본다. ① 그 취약 기능을 우리가 호출하는지(도달 가능성) ② 우리 배포 환경(Vercel/Linux)에서 성립하는지 ③ 입력을 공격자가 통제할 수 있는지는 보지 않는다.

### 2.1 왜 "도달 불가"인가 (항목별 근거)

**① GHSA-2464 (SVG RCE)** — 결함의 실체는 `sharp`/libvips 계열 이미지 파서다. 전제조건은 (a) 공격자가 SVG를 이미지 최적화 엔드포인트에 넣을 수 있고 (b) glibc 기반 Linux에서 실행될 것.
- (a) 불충족: `next.config.ts`에 `images` 설정이 없어 `dangerouslyAllowSVG`는 기본값 **false**(SVG 요청은 400 거부), `remotePatterns`도 비어 있어 원격 URL 불가. `next/image` 사용처는 `src/app/[locale]/page.tsx:118` 파트너 로고 3건(`/partners/{sntl,globallink,zenithlink}.png`)뿐으로 **PNG 고정 자산**이다. 동적 SVG를 반환하는 엔드포인트도 없다(`src/app/api` 6개 전수 확인).
- (b) 부분 충족: 운영은 Vercel(glibc)이고 Dockerfile은 `node:22-alpine`(musl)이다. AWS 이관 후 musl에서는 이 권고 자체가 성립하지 않는다.
- ※ 운영 의존성 `sharp` 0.34.5는 `next`의 optional 의존성이며, `next` 16.4.6이 `sharp ^0.35.5`를 요구하므로 **next 업그레이드만으로 해소**된다.

**② GHSA-2xp9 (AVIF RCE)** — AVIF 입력이 필요하다. 저장소 내 AVIF 자산·생성 경로 0건. 이미지 최적화 대상은 위 PNG 3건뿐이다.

**③ GHSA-p293 (Windows RCE)** — Windows 호스팅 전제. `next.config.ts`의 `output: 'standalone'`, `vercel.json` cron 3건, Dockerfile(AWS ECS Fargate) 어디에도 Windows 실행 환경이 없다.

**④ GHSA-vcvr (`next/og` RCE)** — `next/og` 또는 `ImageResponse` import 0건(전수 grep). OG 이미지 동적 생성 기능을 쓰지 않는다(`opengraph-image*` 라우트 0건).

**⑤ GHSA-673q (`use cache` RCE)** — `'use cache'` 지시자 0건, `cacheComponents`/`dynamicIO` 설정 없음. 빌드 산출물도 전 라우트 `ƒ (Dynamic)`이며 사전 렌더는 `/_not-found`·`/_global-error`·`/favicon.ico` 3건뿐이다.

> ⚠️ **주의**: 5건 모두 "지금은 도달 불가"이지 "안전"이 아니다. ④⑤는 향후 캐시/OG 기능을 도입하는 순간 즉시 위험이 되고, ①은 `dangerouslyAllowSVG`를 켜는 순간 위험이 된다. **버전 업그레이드가 유일한 근본 해소**이며, 위 기능 도입 시 재분석이 필요하다.

### 3.1 미들웨어 우회 3건 (① ② ③) — 이번 분석의 최우선 항목

**전제 조건 충족 여부**

| 권고 전제 | 본 프로젝트 | 충족 |
|:--|:--|:--|
| App Router 사용 | `src/app/[locale]/**` 전체가 App Router | ✅ |
| 동적 세그먼트 라우트 존재 | `[locale]`, `orders/[orderId]`, `support/qna/[id]`, `voc/[id]` 등 다수 | ✅ |
| 미들웨어가 인가를 수행 | `src/middleware.ts` → `authGuard()`(`src/lib/auth/proxy.ts`)가 **역할 기반 라우팅 게이트** | ✅ |

**실질 영향**

- `src/middleware.ts`의 matcher는 `'/((?!_next/static|_next/image|favicon.ico|...).*)'`로 사실상 전체 경로를 잡고, `authGuard()`가 ① 미인증 리다이렉트 ② 정지 계정 차단 ③ 유지보수 모드 ④ 역할별 라우트 허용(`DEFAULT_REDIRECTS`/`ORG_ROUTE_MAP`)을 담당한다.
- 다만 **완전 무방비는 아니다**:
  - `(dashboard)` 그룹 레이아웃(`src/app/[locale]/(dashboard)/layout.tsx:14-22`)이 `supabase.auth.getUser()`로 **세션을 서버측 재검증**하고 미인증 시 `/login` 리다이렉트한다 → 권고 원문의 "서버측 세션 검사 라우트는 여전히 보호됨" 조건에 해당.
  - 데이터 접근은 대부분 서버 액션에서 재검증된다. `src/app/actions/admin/*.ts` 15개 파일 중 5개가 `validateAdminAction()`(역할 검사 포함)을 사용하고, 예: `listMembers`(`admin/member.ts:279`)는 역할 검사를 수행한다.
- **그럼에도 위험한 이유**: 역할 게이트가 미들웨어에만 있는 지점이 남아 있다.
  - `admin` 하위 `page.tsx` **22개 중 11개는 서버측 역할 검사 코드가 없다**(예: `admin/members/page.tsx`는 `'use client'`). `admin/layout.tsx`도 존재하지 않아 상위 역할 게이트가 없다. `(dashboard)/layout.tsx`는 세션만 재검증한다. → 미들웨어를 우회하면 **비관리자 로그인 사용자가 관리자 화면 셸/메뉴를 렌더**할 수 있다.
  - 가장 구체적인 지점은 `admin/ups-rates/page.tsx`다. 서버 컴포넌트가 `requireAuth()`(세션만) 호출 후 `zen_agency_pricing_policies`(대리점 할인율 정책)·`zen_ups_fuel_surcharges`를 **직접 조회해 props로 전달**한다. 데이터를 공급하는 `src/app/actions/ups/rates.ts`도 전 함수가 `validateUserAction()`만 쓴다(역할 검사 0).
- **반대 근거(과장 금지)**: `admin` 액션 15개 모듈을 전수 집계하면 `checkPermission()` 사용은 0건이지만, **`validateAdminAction()`(6개 모듈) 또는 인라인 `USER_ROLES` 비교(6개 모듈)** 로 역할을 검사한다. 예: `listMembers`(`admin/member.ts:279`)는 `validateAdminAction()`, `createSurcharge`(`admin/surcharges.ts:24`)는 `profile.role !== USER_ROLES.ADMIN`. 즉 "미들웨어만 뚫리면 전부 유출"은 아니다. 상세 표는 DEF-147 §1.2.
- 결론: **직접 데이터 유출은 확인되지 않았으나(액션 가드·RLS가 2차 방어), 인가가 미들웨어 단일 의존인 화면이 11개 남아 있다.** CVSS 8.1을 그대로 적용하기는 어렵지만 **HIGH로 취급해 즉시 해소**(= `next` 16.4.6 상향)해야 한다. 상세는 DEF-147.

### 3.2 Server Action / RSC DoS 3건 (④ ⑤ ⑥)

- 공격 표면이 매우 넓다: `'use server'` 모듈 **54개**, `export async function` **270개**, API 라우트 6개.
- 완화 장치는 미들웨어의 IP당 **100 req/60초**(`src/lib/security/rate-limit.ts`) 뿐이며, 이는 **요청 수**를 제한할 뿐 **요청 1건의 처리 비용**은 제한하지 않는다. Server Action 본문 크기는 기본값 1MB(`serverActions.bodySizeLimit` 미설정).
- 단일 대형 요청으로 서버리스 인스턴스를 고갈시킬 수 있다. RSC 렌더 DoS(⑥)는 인증 전 페이지에도 적용된다.
- 판정: **도달 가능(HIGH)**. 데이터 유출은 아니지만 가용성 침해이며, Vercel 과금·SLA에 직결된다.
