# 231 테스트 커버리지 전략 가이드 v0.2 — B_Kai 교차 검증

용어: D1~D9=테스트 차원(Dimension), DEF=결함 등록 번호, PoC=개념 검증(Proof of Concept), vacuous 단언=값을 확정하지 않는 단언(vacuous assertion), RLS=행 수준 보안(Row Level Security).

## 점검 1 — 반영표 대조 (본인 의견)

**결론**: 내 의견의 취지가 삭제·축소된 항목은 없었다. 다만 ① 출처 병합으로 기여 귀속이 흐려진 3건, ② 본문에는 반영됐으나 반영표에 없는 4건이 있다. "반영" 표기 후 본문 누락은 내 항목에서 발견하지 못했다.

**근거**:
- #23 "규칙4: 에러 코드 단언 (R)" — 내 규칙4 제안은 vacuous 단언 금지 **패턴 목록·허용 예외**(§7-4 첫 문장에 반영)이고, Riley 것은 에러 코드 단언(§4.8)이다. 별개 제안인데 R 단독 표기.
- #12 "(R·B) 핵심 6개 테이블+GRANT, fixture 헬퍼" — 6개 테이블은 내 원문에 없다(내 것은 조직/사용자/무소속 fixture 헬퍼·정리 패턴). #21·#24도 R·B 병합 → 각자 기여 검증 불가.
- #14가 R 단독인데, 내 2.4의 "커버 맵 유지 주체·갱신 시점" 지적이 §5.3에 반영됨.
- 표에 없는 본문 반영: §4.1 "순수/상태결합 축 분리", §4.2 fast-check 국소 적용, §6 "미실행 분기 목록 중심"과 "되돌리기↔커버리지 병행", §4.1 초안 링크.

**수정 제안**: 병합 행을 `(R: … / B: …)`로 분해하고, 본문-only 반영 4건을 행으로 추가.

## 점검 3 — 내부 모순·실행 불가

1. **§7-2 vs R-08/R-17**: "1차 커밋=실패하는 테스트"는 GOV_COMMON R-08 "커밋 전 `test:regression` PASS"(`:77`, `:333`)와 R-17 커밋 순서에 정면 위배. → `it.todo`/`describe.skip`으로 스펙만 고정(둘 다 green) 후 구현 커밋에서 활성화.
2. **§4.3 vs §5.3/§7-7**: D3-B는 "매트릭스에 행 추가 없으면 완료 불인정"인데, 파일은 "PR 직접 수정 금지, 주기 일괄 갱신". Agent가 완료 조건을 스스로 충족할 수 없다 → D3-B 매트릭스의 위치·행 추가 주체를 명시.
3. **§4.8 vs §7-4**: §4.8은 적용 시점을 §10#9로 유보, §7-4는 에러 코드 단언을 즉시 규칙으로 둠 — 발효 시점 상충.
4. **§6 vs §7 말미**: "되돌리기 검증 PR 필수 증적"은 즉시 의무처럼 보이나 말미는 "규칙 3·4만 현행 관행 명문화" — 효력 불명.
5. **§5.1 vs §8.1-1a④**: 분할 시점이 "PoC 1단계 병행"과 "1a"로 이중 기재. R-09(`:108`)는 회귀 맵 갱신을 상시 의무화하는데 1,129줄 초과 방치 → 중간 규칙(최소 증분·형식 동결) 부재.
6. **로드맵 게이트 누락**: 단계 1은 "코드 변경 없이 측정만"이나 변이(Stryker)·커버리지(v8) 측정은 devDependency·config 추가를 요구. 도구 승인은 미결 #1로 분리돼 단계 0에 없다 → "1-0 도구 승인" 게이트 필요. 단계 2 fast-check도 동일.
7. **§8.3**: 선정 10건이 PoC 3모듈 범위 내라는 제약이 없어 D6/D7/D8/D9 선정 시 "신규 기법 검출" 판정이 불가. "가능하면 D3-B"도 단계 2의 필수 미니 PoC와 어긋난다.
8. **§4.1 완료 기준**: "결정표 행 수 = 테스트 행 수"는 negative·예외 테스트가 붙으면 항상 깨진다 → "각 행 ↔ 테스트 추적 링크"로 대체.

## 점검 4 — B_Kai 역할 (1a·8.3 실행 가능성)

**결론**: 1a는 "도구 없이 즉시 가능"이 아니다(①②③④ 중 ②만 가능). 8.3은 실행 가능하나 조건 보강이 필요하다.

**근거**:
- **① 차단**: `105_DOMAIN_KNOWLEDGE.md` §3-2/3-3/3-4가 코드와 불일치. 예) 105 WAREHOUSED→PACKED·HELD·RETURNED vs `status-machine.ts:13`의 REGISTERED·SCHEDULED·RELEASED 추가, 105 OPERATOR 3개 vs `:36` 8개, 105 "WAREHOUSED 수정 불가" vs `getOrderEditScope` WAREHOUSED+UPS 전체 수정(`:133-145`). §7-1은 "근거 문서 선갱신+승인"을 요구 → 105 정합화 Task가 선행해야 한다. 105에는 AGENCY·INDIVIDUAL·MANAGER·CLAIMED·DISPOSED도 없다.
- **③ 차단**: 현행 검증은 스키마가 아니라 명령형 `string[]`(`validate-payload.ts:33-77`). "스키마 초안"은 신규 설계이고 대상 경로가 Team B 영역(§10#3 미결) + R-11 명세 선행 → B_Kai 단독 즉시 불가.
- **④ 차단**: 1,129줄 공유 문서에 CODEOWNERS 전량 Aiden — §5.3이 경고한 동시 수정 위험. Aiden 또는 스크립트 단독 수행이 타당하다.

- **권고 순서**: ④(Aiden) → ② → ①(105 정합화 후) → ③(Team B·Ds-11 후). "즉시"가 아닌 "선행 2주" 항목으로 재정의.
