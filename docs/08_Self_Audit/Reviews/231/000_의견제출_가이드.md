## 1. 이 검토의 목적

SAR·회귀 테스트 중심의 현행 품질 체계가 충분한지 점검하고, 업무 분기·입력 예외·권한·외부 연동 등 **사각지대를 체계적으로 도출·측정하는 방법**(문서 231)이 현실적으로 쓸 만한지 **구현·검증 담당 관점**에서 평가한다. 성과가 있으면 향후 MLFF BOS 개발에도 도입을 검토한다.

문서 231은 **초안(v0.1)** 이다. 틀린 곳, 빠진 곳, 시행이 어려운 곳을 **솔직하게** 지적하는 것이 목적이다. 동의만 나열하는 보고서는 가치가 낮다.

## 3. 무엇을 검토하는가

### 공통 질문 (두 Agent 모두)

1. **문제 진단(§1)**: "현행 체계의 한계 4가지"가 실제 작업 경험과 맞는가? 틀린 진단이나 빠진 한계가 있는가?
2. **차원 모델(§3, D1~D9)**: 빠진 차원, 겹치거나 불필요한 차원이 있는가?
3. **케이스 도출 방법(§4)**: 실제로 따라 할 수 있는가? 어느 부분이 막연한가?
4. **Agent 준수 규칙(§7)**: 현재 업무에서 지키기 어려운 규칙은 무엇인가? 이유는?
5. **PoC(§8)**: 대상 3모듈(상태 전이 / 운임 엔진 / SHXK payload 빌더)과 단계 구성이 적절한가? 더 나은 대상이 있는가?
6. **반대 의견**: 이 문서에서 **채택하지 말아야 한다**고 보는 항목이 있는가?

## 4. 제출 방법

1. `_TEMPLATE_review.md`를 복사해 `riley_review.md` 또는 `bkai_review.md`로 저장한다.
2. 양식의 모든 섹션을 채운다. 해당 없으면 "해당 없음 (사유)"를 적는다.
3. 제출 완료 후 **Edward에게 "제출 완료"를 알린다** (파일 경로 포함).
4. 제출 후에는 수정하지 않는다. 정정이 필요하면 파일 끝에 `## 정정 (날짜)` 섹션을 추가한다.

## 5. 제출 후 절차 (Aiden)

1. 두 보고서가 모두 제출되면 쟁점별로 취합한다 (합의 / 상충 / 단독 의견).
2. 231을 v0.2로 개정하고, 개정 이력에 **의견 반영표**(반영 / 부분 반영 / 미반영 + 사유)를 남긴다.
3. 상충 의견은 임의로 결정하지 않고 Edward에게 판단을 요청한다.
4. 보고서 파일은 지정 경로를 명시해 개정 PR에 함께 커밋한다 (다른 미커밋 변경분과 혼입되지 않도록 경로 지정 커밋).
