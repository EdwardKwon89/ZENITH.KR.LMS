## 1. 총평 (3~5줄)

**결론: 수정 후 채택.** SAR+회귀의 사후 대응 한계와 mock으로 잡기 어려운 결함군(D3·D4 등)을 분리해 다루려는 방향, D1~D9 차원 모델과 PoC-성과판정 기반 도입은 실무적으로 타당하다. 다만 규칙의 시행 시점/의무 수준, 커버 맵 운영 R&R·근거 형식, PoC 기준선·재현시험 프로토콜이 구체화되지 않으면 “문서는 있으나 운영되지 않는” 상태가 되기 쉽다. v0.1의 문제 진단은 저장소 현황(coverage 설정 미확인, 커버 맵 파일 부재, 301 Gate 2 문구 모호)과 대체로 부합한다.

### 2.3 케이스 도출 방법 (§4)
(막연하거나 따라 하기 어려운 부분, 빠진 점검 항목)
- **결정표/전이 매트릭스(§4.1)**: 예시는 이해 가능하나, 실제 작성 시 “조건 축을 어디까지 쪼갤지”(예: 역할, 현재 상태, 대상 상태, 리소스 소유, transportMode, measured 상태 등) 기준이 더 필요함. `getOrderEditScope`처럼 상태 외 파라미터가 결과에 영향을 주는 함수는 단순 상태 전이표만으로 부족할 수 있음.
  - 근거: `src/lib/logistics/status-machine.ts` — `isOrderPartiallyEditable(status, transportMode)`, `getOrderEditScope(status, transportMode)`에서 `WAREHOUSED + UPS` 특수 분기 확인.
- **입력 점검표(§4.2)**: 유형별 값 목록은 유용하나, **필드 간 교차 제약**(예: 전화/휴대폰 중 1개 이상 필수, 국가별 우편번호/도시 필수 조합), **정규화 전/후 값** 비교 기준, **다건 품목 배열의 부분 실패 메시지 일관성**이 추가되면 좋음.
  - 근거: `validateShxkPayload` — 발송/수취 연락처 OR 조건, 품목별 인덱스 에러 누적, `unit_code` 허용값 검사 등 확인.
- **속성 기반(§4.2)**: “반례를 고정 회귀로 커밋” 원칙은 좋으나, 생성기(seed) 고정·재현 방법·실행 시간 상한을 함께 정해야 CI/로컬에서 운영 가능.
- **권한 매트릭스(§4.3)**: 자기완결 fixture 언급은 좋으나, **조직/소유 관계 셋업 패턴**(자기 조직·타 조직·무소속) 템플릿이 있으면 도출 난도가 낮아짐. (구체 템플릿 존재 여부 미확인)
- **외부 계약(§4.4)**: 스키마 1회 정의는 동의. “관측된 신규 제한 발견 시 스키마 우선 갱신” 절차는 좋지만, 명세와 실제 응답이 충돌할 때의 우선순위/기록 위치를 명시하면 좋음.

### 2.4 커버 맵·검출력 측정 (§5·§6)
(운영 가능성, 갱신 누락 방지책, 도구 도입 비용에 대한 의견)
- **커버 맵 운영 가능성**: 형식(모듈×차원, 🟢/🟡/🔴/- + 근거 링크 필수)은 명확해 좋음. 다만 유지 주체·갱신 시점·리뷰 체크포인트가 없으면 쉽게 stale해짐. `LIVE_REGRESSION_TEST_MAP.md`가 이미 과대(문서 언급 DEF-B-157)인 상황에서 이중 관리 부담을 줄이는 설계가 필요.
  - 근거: 231 §5.1, §5.2. 커버 맵 파일 부재(본 세션 확인).
- **갱신 누락 방지 제안**: (a) PR 템플릿/체크리스트에 “해당 모듈 커버 맵 칸 변동” 항목 추가(도입 승인 후), (b) 모듈 소유자 기준 주기 점검(릴리스/스프린트 단위) 중 하나를 택해 명시, (c) 🟢는 테스트 경로+식별자(파일/케이스명)까지 링크.
- **검출력 측정(§6)**: 분기 커버리지(v8)는 도입 가치가 있으나 “미실행 분기 목록” 중심 해석 원칙을 운영 규칙으로 못 박아야 함. 되돌리기 검증의 PR 증적 공식화는 실익이 있으나 증적 형태(커밋/로그/스크린샷 등) 표준이 필요.
- **도구 도입 비용(의견)**: `fast-check`는 특정 모듈(입력 검증/정규화)에 국소 도입 시 유지보수 대비 효용이 있을 가능성이 높음. `Stryker`는 실행 시간이 길어 핵심 모듈 한정·비CI 정기 실행 시작(231 §8.3 제안)에 동의하나, 실제 시간/설정 복잡도는 본 저장소 기준 미측정.
  - 근거/한계: 도구 미도입 상태(coverage 설정 부재 확인). 실행 시간·flaky 영향은 **미확인**.

### 4-3. 변이 테스트·속성 기반 테스트 도입 비용 관점
- **속성 기반(fast-check)**: 입력 검증/정규화/파서·빌더처럼 순수 함수 성격이 강한 영역에 국소 적용 시 작성·유지보수 비용 대비 가치가 있을 것으로 봄. 다만 생성기 설계 품질에 따라 무의미한 입력 탐색/느린 실행이 될 수 있어, 대상 모듈 선별과 seed 고정·시간 제한이 필요.
- **변이 테스트(Stryker)**: 설정·실행 시간·등가 변이(equivalent mutant) 해석 비용이 커서 전 모듈 상시 적용은 부담 가능성이 큼. 231 제안처럼 핵심 모듈 한정, 비CI 정기 실행으로 시작하는 것이 현실적.
- **종합**: 도입 자체보다 “어디에 어떤 불변식/변이 범위를 걸 것인가” 선정 비용이 큼. PoC에서 실제 시간/발견 가치 측정 후 확대 판단에 동의.
- 근거: 231 §6, §8.3. 본 저장소 기준 실행 시간·CI 영향·도구 설정 난이도는 **미확인**.

### 4-4. 현재 “되돌리기 검증”과 비교한 §6 측정 방식의 실익
- **되돌리기 검증(현행 수동)**: 해당 변경·해당 테스트에 대한 직관적 검출력 확인으로 실익이 큼(“이번 수정에 대한 테스트가 실제로 깨지는가”). 다만 사람 의존·범위가 변경분 근처로 제한됨.
- **§6 측정(커버리지/변이 점수)**: 실행 공백(미실행 분기)과 단언 약함을 **변경과 무관하게 체계적으로** 드러낼 수 있어 보완재 성격이 강함. 특히 핵심 모듈의 누적 품질 관리에 유리.
- **의견**: 둘은 대체 관계가 아니며 병행 가치가 있음. 실익 극대화를 위해 되돌리기 검증은 PR 증적(재현 가능한 형태)으로 표준화하고, 커버리지/변이는 핵심 모듈 정기 점검 지표로 쓰는 절충이 적절.
- 근거: 231 §6, §7-3/4, Team B 관행(문서 서술). 실제 PR 증적 품질/누락률은 **미확인**.

- **AI Agent 작성 테스트의 품질 리스크**: Agent가 테스트를 생성할 때 구현 코드를 그대로 옮긴 단언이나 통과 목적의 약한 단언이 섞일 위험이 있음. 231의 “명세 기반 도출·vacuous 금지·되돌리기 검증”은 이 리스크 완화에 중요하므로, PoC에서 Agent 산출 테스트에 대해 “명세 근거 표기 여부”와 “되돌리기 시 실패 여부”를 별도 샘플링 점검 지표로 두는 것을 권장.
- **운임 엔진 PoC 범위 주의**: 운임 계산은 경계값·조합 폭발이 커서(구간/zone/요율카드 유무/할증 등) 전체 분기 망라를 목표로 하면 범위가 빠르게 커짐. PoC 단계 2에서는 금전 영향이 큰 결정표 행과 최근/과거 DEF 관련 경계부터 우선 적용하고, 속성 기반은 “불변식 1~2개”로 좁게 시작하는 편이 현실적일 수 있음(대상 코드 경계 **미확인**).
- **커버 맵과 R-08/R-09의 접점**: 커버 맵(§5)이 “현재 공백 가시화”라면, R-08/R-09 산출물(회귀 실행·확장)은 “공백 해소 이력”에 해당함. 두 자산을 연결하는 최소 규칙(예: 커버 맵 🟢 전환 시 근거 테스트/PR 링크 기재)을 두면 중복 관리 부담을 줄이면서 추적성을 확보할 수 있음.
- **실DB(D3) 테스트의 안정성 전제**: 자기완결 fixture 원칙은 필수이나, 역할/조직/정책 셋업이 복잡하면 테스트 작성 비용과 flaky 위험이 함께 증가할 수 있음. 공통 fixture 헬퍼(조직·사용자·롤 시드/정리 패턴)를 PoC에서 함께 정리하면 이후 D3 확장 비용을 낮출 수 있을 것으로 예상됨(현행 헬퍼 존재 여부 **미확인**).
