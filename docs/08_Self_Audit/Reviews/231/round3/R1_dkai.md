## 점검 4 — 구현자(D_Kai) 적용 가능성

**결론**: §4.9만으로는 **신규 Issue 1건을 채울 수 없다**. 막히는 지점은 다음 4개다.

| 막히는 항목 | 이유 |
|:--|:--|
| `AC ↔ 케이스 추적` | Issue에 AC 번호 체계가 없다. `.agent/tasks` 444건이 DoD를 쓰고 "인수 조건/Acceptance"는 0건(확인). 번호를 구현자가 임의 창작하게 된다 → `Issue DoD 항목 번호`로 대체 권고 |
| `테스트 케이스 ID` | §4.1:120은 "배열 길이 = 실행 건수"만 규정. `it.each` 개별 케이스 ID 부여 규칙 없음 → `DTC-<모듈>-<n>` 같은 규칙 필요 |
| `vacuous 단언` | 정의 없음. `toBeDefined()` 단독인지, 다른 단언과 병기하면 허용인지 불명. 정규식/AST로는 "단독"을 판정하기 어려워 집행 불가 |
| `105 §` | 저장소에 105가 3개(`105_DOMAIN_KNOWLEDGE`/`105_MULTITEAM_GOVERNANCE`/`105_MODEL_CAPABILITY_MATRIX`). 양식은 "105 §"만 요구. 또 §7-1이 §3을 근거에서 배제하므로 "105 §3 제외" 주석 필요 |

**추가 반론**: §7-2:299의 "`it.fails` 우선"은 **LMS 적용 대상 대부분에 오적용**된다. Pilot 운영 중 Issue의 다수는 기존 동작의 회귀 고정·커버리지 보강인데, 이미 통과하는 동작을 `it.fails`로 쓰면 그 자체가 실패한다. "미구현 동작/결함 재현에 한정"을 명시해야 한다.

**Pilot 부담**: 위험 2개 이상 Issue는 결정표+입력 점검표+실DB 테스트로 PR당 수시간이 든다. 운영 중 6명(Team A 3·B 3)이 매 PR 수행은 비현실적이며, 현 문서 구조로는 §10 #14 미결과 무관하게 발효된다.
