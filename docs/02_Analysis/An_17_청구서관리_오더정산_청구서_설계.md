## 0. 결론 요약

1. 업무개요는 **두 단계**다. (A) **오더정산** = UPS 최종 청구서 기준으로 오더 원가·매출을 확정(오더 단위), (B) **청구서** = 정산 완료 오더를 **조직×월×차수**로 묶어 발행(청구 단위).
2. 현재 시스템은 (A)의 절반(원가 입력·환율·재계산)은 있으나, **"오더정산 완료" 상태가 없고**, (B)는 **개념이 다르다** — 현재 `zen_invoices`는 **오더 1건당 1청구서**(`metadata.source_order_id`)이고 일일 마감(`daily-billing`) 방식이다. 월 차수 묶음·오더 중복 포함 금지·취소 시 오더 해제 구조가 없다.
3. 따라서 **(B)는 신규 모델(청구서 헤더 + 청구서-오더 연결)** 이 필요하다. 기존 인보이스 데이터는 건드리지 않고 병행(레거시 유지)하는 안을 권장한다.
4. **JSJung 결정(2026-11-18)**: Q1 **+7% 가산 유지**, Q3 **오더 중복 금지는 티어별 1회**, Q4 **UPS 오더만 신규 방식·그 외는 기존 유지**. 이에 맞춰 §2·§3·§8을 갱신했다. 남은 쟁점(Q2·Q5~Q10)은 §8 참조.

## 3. 도메인 모델 설계

### 3-1. 오더정산 상태 (R3)

`zen_orders`에 컬럼 추가(안):

| 컬럼 | 타입 | 설명 |
|:--|:--|:--|
| `cost_settlement_status` | text CHECK (`NOT_SETTLED`/`SETTLED`) default `NOT_SETTLED` | 오더정산(원가 확정) 여부 |

- 전이: `NOT_SETTLED → SETTLED`(Admin이 원가 저장+“정산 완료” 실행), **`SETTLED → NOT_SETTLED` 되돌리기는 청구서에 미포함 상태에서만 허용**(포함 중이면 거부).
- “정산 완료” 시점에 `zen_ups_actual_cost` 존재를 필수로 검증.
- **청구서 후보 조회 조건** = `transport_mode='UPS'` ∧ `cost_settlement_status='SETTLED'` ∧ 대상 조직 소속 ∧ 기간 내 ∧ 다른 청구서 미포함.

### 3-1b. 원가 계산 규칙 통합 (Q1 결정 반영)

**규칙**(확정 사항 + 기존 코드 의미 유지):
- 가산 대상은 **기본운임만** (현행 `recordActualCostAndFinalize`와 동일). 유류할증료·급증수수료·기타 부가운임은 UPS 청구서 금액 그대로.
- 가산율은 `UPS_COST_SURCHARGE_RATE`(0.07) 상수 **한 곳**에서만 참조. 리터럴 `1.07` 금지.
- 환율은 **출고확정일** 기준(HKD→KRW, 기본운임 통화가 다르면 해당 통화→KRW), 반올림은 현행(`Math.round`) 유지.
- 계산식: `기본운임 원가(KRW) = 기본운임(UPS 청구액) × 환율 × 1.07`, 나머지 항목은 `금액 × 환율`.

**설계 변경 제안**(구현 Task 1에서):
1. 순수 함수 `computeUpsActualCostKrw(input, rates)` 하나로 통합 → `recordUpsActualCost`·`recordActualCostAndFinalize`·`previewUpsActualCost` 모두 사용. 입력 경로에 따라 원가가 달라지는 현 문제 제거(회귀 테스트로 두 경로 동일 결과 고정).
2. **UPS 청구서 원금액(raw)과 가산 후 원가를 구분 저장**: 대사(UPS 청구서 vs 시스템)에는 raw가 필요하다. 신규 컬럼 `base_freight_raw`(+통화)와 `cost_surcharge_rate`(적용률 스냅샷), 가산 후 `total_cost_krw`. 요율이 훗날 바뀌어도 과거 오더 원가가 불변.
3. `*_hkd` 컬럼에 KRW가 섞이는 의미 혼재는 위 통합 시 통화 컬럼과 함께 일관되게 정리(필요 시 마이그레이션 + 기존 행 백필 — 별도 설계 의견 Task).

> 확인 요청(Q1-a): “+7%”는 **기본운임에만** 적용하는 현행 의미가 맞는지 확인 부탁드립니다(유류·급증에도 적용이면 규칙이 달라집니다).

### 3-2. 청구서 모델

기존 `zen_invoices`(오더 단위)는 **유지**하고, 월 차수 청구서는 **신규 2개 테이블**(안):

**`zen_billing_statements`** (청구서 헤더)

| 컬럼 | 설명 |
|:--|:--|
| `id`, `statement_no` | `ST-YYYYMM-NN-<seq>` (유일) |
| `issuer_org_id` | 발행자(Admin 또는 대리점 조직) |
| `billed_party_type` | `ORG`(등록 조직) / `ADHOC`(수기 화주) — R11 |
| `billed_org_id` | 청구 대상 조직. **`ADHOC`이면 NULL** (등록 대상이면 필수) |
| `billed_name`, `billed_biz_no` | 청구 대상 표시명·사업자번호 **스냅샷**. `ADHOC`은 입력값(필수 `billed_name`), `ORG`는 발행 시점 조직명 |
| `billed_key` | 차수 채번·중복 방지용 정규화 키: `ORG:<org_id>` 또는 `ADHOC:<정규화 화주명>`(공백 압축·소문자·앞뒤 공백 제거) |

| `period_year`, `period_month`, `round_no` | 월·차수 (유일: issuer+**billed_key**+년+월+차수) |
| `period_from`, `period_to` | 포함 기간 |
| `total_amount`, `currency`(KRW) | 헤더 합계(항목 합) |
| `status` | `DRAFT`→`ISSUED`→`CLOSED` (+ 삭제는 DRAFT 한정 행 삭제) |
| `issued_at/by`, `paid_at`, `closed_at/by`, `created_at/by` | 감사 |

**`zen_billing_statement_items`** (청구서-오더)

| 컬럼 | 설명 |
|:--|:--|
| `statement_id` FK(ON DELETE CASCADE) | 헤더 |
| `order_id` FK | 오더 |
| **`order_id` UNIQUE** | **R5-2: 한 오더는 하나의 청구서에만** (DB 레벨 강제). 헤더 삭제 시 CASCADE로 자동 해제 → R7 충족 |
| `charge_weight_kg`, `base_freight`, `fuel_surcharge`, `surge_fee`, `other_charges`, `line_total` | **스냅샷**(발행 후 오더 값이 바뀌어도 청구서 불변) |

- 티어별 금액 원천: `ADMIN_TO_AGENCY`=대리점 대상 매출액, `AGENCY_TO_SHIPPER`/`ADMIN_TO_SHIPPER`=화주 대상 매출액. (오더에서 이미 재계산된 값을 스냅샷)
- 유일 제약을 `order_id` 단독으로 둘지 `(order_id, tier)`로 둘지는 **Q3**: 한 오더가 Admin→대리점 청구서와 대리점→화주 청구서에 **각각 한 번씩** 들어가는 것은 정상이어야 한다(서로 다른 티어). 따라서 **`UNIQUE(order_id, tier)`** 가 정확하다.

- **CHECK**: `(billed_party_type='ORG' AND billed_org_id IS NOT NULL) OR (billed_party_type='ADHOC' AND billed_org_id IS NULL AND billed_name IS NOT NULL)`.
- **수기 화주 청구서의 조회 경로**: 청구 대상 조직이 없으므로 아래 RLS 경로 ②(청구받은 조직)는 해당 없음 → **발행자 본인(경로 ①)과 Admin 감독(경로 ③)만** 조회. 수기 화주는 시스템 사용자가 아니므로 `/shipper/statements`에 노출되지 않는다. Excel·PDF는 발행자가 전달.
- **수기 화주 오더의 소유 식별(코드 실측)**: 대리점 사용자가 "내 정보 사용"으로 등록하면 `shipper_id` = **대리점 자기 조직**, 화주명은 `zen_orders.shipper_name`(자유 텍스트, TASK-B-295 #1100), 사업자번호는 `shipper_biz_no`에 저장된다. 반면 `agency_org_id`는 *등록한 사용자 조직이 `zen_agency_shippers`에 연결된 화주일 때만* 채워지므로(`orders.ts:158-168`) **대리점이 직접 등록한 수기 화주 오더는 `agency_org_id`가 NULL**이다. 따라서 후보 조회는 `agency_org_id`가 아니라 **`shipper_id = 발행 대리점 조직`** 로 범위를 잡는다.

### 3-3. 청구서 상태 머신 (R7~R9)

```
 (생성)           (발행)             (입금확인)
 DRAFT ───────▶ ISSUED ───────────▶ CLOSED
   │ 취소(=삭제)     │ 취소·삭제 불가      │ 불가
   ▼               ▼
 (행 삭제, 오더 해제)   (조정은 별도 규칙)
```

| 상태 | 가능한 행위 | 불가 |
|:--|:--|:--|
| DRAFT | 오더 추가/제외, 취소(삭제) | — |
| ISSUED(확정) | 입금확인, PDF/조회 | 취소·삭제·오더 변경 |
| CLOSED(마감) | 조회 | 일체 변경 |

- 취소·삭제는 **생성자 본인**만(R7). 발행 후 오류는 **조정 청구서**(Q6)로 처리.
- 부분 입금(`PARTIAL`)은 요구에 없으므로 **전액 입금확인만** 지원(Q7 확인).

### 6-5d. 수기 화주 청구 (R11, 2026-11-18 추가)
- **S4 청구 대상 선택**을 2가지 방식으로 한다: ① **등록 화주/대리점**(기존 선택) ② **수기 입력 화주**(대리점 전용). 수기 선택 시 화주명 입력칸이 자동완성(과거 오더의 수기 화주명 목록)을 제공하고 사업자번호는 선택 입력.
- **표기 변형 경고**: "(주)ABC"·"ABC 주식회사"·"abc"처럼 한 화주의 표기가 오더마다 다를 수 있으므로, 입력값과 유사한 다른 화주명이 있으면 "유사 화주명 N건 — 함께 조회" 칩을 보여 주고 사용자가 포함 여부를 고른다. 후보 목록에는 **오더별 화주명 열**을 표시해 사람이 최종 체크한다.
- **청구서 표시명은 발행자가 입력한 값을 스냅샷**한다(오더별 표기가 달라도 청구서에는 한 이름).
- **중복 방지**: 같은 오더는 티어별 1회 규칙(`UNIQUE(order_id, tier)`)으로 등록/수기 어느 경로로 만들어도 이중 청구되지 않는다. 한 오더가 등록 화주 경로와 수기 경로 양쪽에 동시에 잡히는 일은 없다(등록 화주 오더는 `shipper_id`가 그 화주, 수기 오더는 `shipper_id`가 대리점 자신).
- **범위 제외**: Admin이 수기 화주 대상으로 청구서를 만드는 경우는 이번 범위에서 제외(Admin→대리점/직거래 화주는 등록 조직만). 필요 시 후속.
