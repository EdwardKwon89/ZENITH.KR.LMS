## 1. 현상 (확인된 사실)

1. `src/lib/auth/proxy.ts:68-70`은 유지보수 모드에서 비플랫폼 사용자를 `/{locale}/maintenance`로 리다이렉트한다.
2. 그러나 점검 모드 페이지는 `src/app/[locale]/(maintenance)/page.tsx`에 있고, **`(maintenance)`는 라우트 그룹**이라 URL 경로에 포함되지 않는다 → 실제 생성 경로는 `/[locale]`(=`/ko`)이다.
3. `src/app/[locale]/page.tsx`(루트 랜딩)와 경로가 충돌하며, 두 항목 모두 `/[locale]`로 매핑된다.

```
# .next/app-path-routes-manifest.json (16.2.4 / 16.4.6 동일)
/[locale]/(maintenance)/page => /[locale]
/[locale]/page               => /[locale]
```

4. 따라서 `/ko/maintenance`는 **존재하지 않는 경로**(404)이고, 루트 `/ko`는 랜딩 페이지가 렌더된다.
5. 증적: `docs/99_Manual/E2E_1153_Result/1153_13_maintenance_mode.png` — 플래그 ON 상태에서 화주 계정이 `/ko/maintenance`로 이동했으나 `404 This page could not be found.` 표시.
6. 관리자(플랫폼) 계정은 유지보수 모드에서 정상 통과(`/ko/orders`, 증적 `1153_14`), 플래그 원복 후 정상 복귀(`1153_15`).

## 2. 영향 범위

- `MAINTENANCE_MODE` 활성화 시 **비플랫폼 사용자 전원**이 점검 안내를 보지 못하고 404를 보게 된다.
- 리다이렉트 자체는 동작하므로(URL 변경) 미들웨어 로직 문제가 아니라 **라우트 배치 문제**다.
- 본 결함은 16.2.4에서도 동일하다(`app-path-routes-manifest.json` 16.2.4/16.4.6 비교). **DEF-146 P0 상향으로 유발된 회귀가 아니다.**

## 3. 조치안 (권고)

| 안 | 내용 | 비고 |
|:--|:--|:--|
| **A (권고)** | `src/app/[locale]/(maintenance)/page.tsx` → `src/app/[locale]/maintenance/page.tsx`로 이동 | 라우트 그룹 오용 수정. `messages/*.json`의 `Maintenance` 네임스페이스는 그대로 사용 가능. 루트 `/` 충돌도 함께 해소 |
| B | 프록시 리다이렉트 대상을 `/{locale}`로 변경 | 랜딩 페이지가 점검 안내를 겸하지 않으므로 부적절 |
