## 현상 (확인함, 운영 DB·로그 직접 조회)
- 오더 등록은 `createOrder`(오더 생성) 후 `createOrderServices`(서비스 저장)를 **별도 단계로 순차 실행**한다(`src/components/orders/OrderRegistrationForm.tsx:879` → `:897`). 서비스 저장이 실패하면 오류 토스트만 띄우고, **이미 생성된 오더를 되돌리거나 정리하지 않는다**(`:898-914`).
- 사용자는 등록 화면에 남아 오류 문구를 보고 다시 제출할 수 있어, 재시도마다 **새 오더가 생성된다**.
- 2026-11-23 10:45:29~10:46:15, 운영에서 4회 시도로 오더 4건(ZEN-2026-000046~49)이 `REGISTERED` 상태·서비스 0건·요금 스냅샷 0건으로 남았다. 테스트 오더라서 같은 날 취소 처리했다.

## 영향 범위
- 서비스 저장이 실패하는 모든 경우(예: DEF-158)에 서비스가 없는 오더가 쌓인다. 화면에는 "Submission Failed"로 표시되어 사용자는 등록이 실패한 것으로 오해하기 쉽다.
- 중복 오더는 정산·재고·추적에 잘못된 데이터를 남길 수 있다(영향 정도는 미확인).

## 권장 조치 (설계 결정 필요)
1. 오더 생성과 서비스 저장을 하나의 원자적 처리로 묶는다. 운영 DB에 `create_order_services_atomic` 함수가 있으므로(정의·호출처는 이 DEF에서 확인하지 않음) `create_order_atomic`과의 결합 또는 이를 활용한 보상 처리를 먼저 검토한다(적합성은 미확인).
2. 서비스 저장 실패 시 생성된 오더를 상태 전이 규칙에 따라 정리(취소)하고, 사용자에게 "오더가 생성되지 않았다/생성됐다"를 명확히 알린다.
3. 제출 버튼 중복 클릭·재제출 방지(제출 중 비활성화, 실패 후 재제출 시 기존 오더 재사용).
4. 회귀 테스트: 서비스 저장 실패를 주입해도 오더가 남지 않거나, 재제출 시 중복 오더가 생기지 않는 것을 단언한다.
