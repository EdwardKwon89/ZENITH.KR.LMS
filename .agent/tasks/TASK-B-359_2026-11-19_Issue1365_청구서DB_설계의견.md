## [설계 의견] — Jaison 확정 대상 (4개 영역 + R11)

### 영역 1 — 헤더·항목 스키마 (WBS 3.1·3.5)

**확정 사항(재론 금지)**: `UNIQUE(order_id, tier)`, 헤더 DELETE 시 항목 CASCADE, R11 CHECK(`ORG⇒billed_org_id 필수` / `ADHOC⇒org NULL·billed_name 필수`), 차수 유일키 `issuer + billed_key + 년 + 월 + 차수`, 금액 KRW 스냅샷.

**Q1-1. `billed_key` 저장 방식** (배정 코멘트 지정 필수 항목)

| 안 | 내용 | 장점 | 단점 |
|:--|:--|:--|:--|
| **(G-1) GENERATED STORED 컬럼 (권장)** | `billed_key text GENERATED ALWAYS AS (CASE WHEN billed_party_type='ORG' THEN 'ORG:' \|\| billed_org_id::text ELSE 'ADHOC:' \|\| lower(btrim(regexp_replace(billed_name, '\s+', ' ', 'g'))) END) STORED` | 정규화를 **DB가 강제** — 어떤 경로(SQL·RPC·백필)로 insert해도 동일 키. 이중 차수 방지가 도메인 핵심이므로 앱 실수 노출면 0. 유일키에 그대로 사용 | 정규화 규칙 변경 시 마이그레이션(rewrite+백필) 필요. `lower`/`btrim`/`regexp_replace(text,text,text)`/`uuid::text` 모두 IMMUTABLE이어야 함(착수 시 `pg_proc` 확인) |
| (G-2) RPC/앱이 계산해 일반 컬럼 저장 | `create_billing_statement` RPC가 계산·저장 | 규칙 변경 시 앱 배포만 | 다른 insert 경로(관리 SQL·후속 액션)가 틀린 키를 넣을 수 있음 — UNIQUE는 "틀린 키"를 막지 못함(동일 키가 다른 키로 발급되어 차수 중복 방지 실패) |
| (G-3) 저장 컬럼 없이 표현식 유일 인덱스 | `UNIQUE(issuer_org_id, (정규식 표현식), year, month, round)` | 저장 불필요 | 인디버깅·목록 쿼리에서 키 가시성 없음, 표현식 복합 유일키 관리 부담 |

- **리스크(G-1)**: 규칙 변경 시 기존 키 재생성 필요 → 백필은 후속 Task에서 `cost_legacy_snapshot`류 스냅샷 없이 원자리 그대로 교체 가능(키는 채번용 보조값이라 원본 아님) — 허용.

**Q1-2. `statement_no` 구성과 유일성 확보** (`ST-YYYYMM-NN-<seq>`)

- 해석: 설계 예시(`ST-202610-01-1` B대리점 / `ST-202610-01-2` C사, 둘 다 "2026-10 1차")상 **NN=차수(01), seq=월 내 전체 순번**으로 보인다. → **확인 요청: NN이 차수인지 티어(01=ADMIN_TO_AGENCY)인지 명확히 해달라**(둘 다 예시와 부합, 표시 문자열에 영향).

| 안 | 내용 | 판정 |
|:--|:--|:--|
| **(S-1) 월 글로벌 카운터 테이블 (권장)** | `zen_billing_statement_seq(period_year, period_month, last_seq, PK(y,m))` + RPC에서 `INSERT … ON CONFLICT DO UPDATE SET last_seq=last_seq+1 RETURNING` 원자 증분 → seq 부여 | **권장** — RLS 가시성 문제 없음(타 발행자 행을 볼 필요 없음), 단일 문장 원자성, `UNIQUE(statement_no)` 보조. 취소(DRAFT 삭제) 시 번호 gap은 **허용**(세금계산서 등 실무에서도 취소번호 공백 일반 — 감사상 오히려 재사용보다 안전) |
| (S-2) 같은 월 `MAX(seq)` 재조회 | RPC가 헤더 테이블에서 MAX+1 | **기각 후보** — RLS로 타 발행자 행이 안 보여 MAX가 작게 나와 `UNIQUE(statement_no)` 위반 → `SECURITY DEFINER`로 우회해야 하는데 그러면 함수 내부 권한 명시 검증이 추가로 필요 |
| (S-3) seq = 차수 단순화 | `ST-YYYYMM-{round}` | **기각** — 다른 billed 간 동일 월 동일 차수가 충돌(예시의 …-01-2 존재와도 불일치) |

**Q1-3. 항목(Items) 스냅샷 컬럼**: `charge_weight_kg, base_freight, fuel_surcharge, surge_fee, other_charges, line_total` (모두 numeric, KRW) + `tier` + `order_id UNIQUE`는 확정. 추가: `created_at`만 두고 발행 시각 등은 헤더에서 참조(중복 저장 없음). — 이견 없으면 그대로 진행.

### 영역 2 — 채번 RPC (WBS 3.2)

**Q2-1. RPC 경계**

| 안 | 내용 | 판정 |
|:--|:--|:--|
| **(B-1) 헤더 insert 포함 통합 RPC (권장)** | `create_billing_statement(issuer, billed_key, year, month, tier, …) → {id, round_no, statement_no}`: advisory lock → `round=max+1` → seq 증분 → 헤더 INSERT(DRAFT, 항목 0건·합계 0) → RETURN. **한 트랜잭션** | **권장** — "순번만 반환" RPC는 반환 후 insert 사이 race가 남아 이슈 DoD "병렬 호출 번호 중복 없음"을 보장할 수 없다(번호를 확정하려면 반드시 무엇인가를 persist해야 함). Task 3의 `createBillingStatement`는 이 RPC 호출 후 항목 insert·합계 갱신을 **별도 RPC(`add_statement_items`, DRAFT 한정)** 로 이어붙인다 — 헤더가 먼저 DRAFT로 존재하는 것은 Q5(초안 편집 없음)와도 상충 없음(생성 트랜잭션 내에서만 항목이 채워짐) |
| (B-2) 순번 반환 전용 `next_billing_round(…)` | max+1만 계산·반환 | 기각 — persist 없음 → 동시성 미보장 |
| (B-3) counter 테이블로 차수도 증분 | seq·round 모두 카운터 | 기각 후보 — 취소 후 재사용 불가(gap) + 발행 안 된 DRAFT가 번호를 영구 소진. round는 max+1+재사용이 자연스럽다 |

**Q2-2. 동시성 메커니즘**: `pg_advisory_xact_lock(hashtext('billing_round:' || issuer || ':' || billed_key || ':' || year || ':' || month))` 선취 후 `max(round_no)+1` (트랜잭션 종료 시 자동 해제). **보조 안전망**: `UNIQUE(issuer_org_id, billed_key, period_year, period_month, round_no)` — lock 유무와 무관하게 최후 방어. seq는 Q1-1(G-1) counter로 별개 원자 연산.
- 단, `billed_key`가 GENERATED STORED면 UNIQUE 키에 그대로 포함 가능(G-1과 시너지).
- **RLS 주의**: RPC가 `SECURITY INVOKER`면 caller RLS가 적용 → 발행자 본인 행만 보므로 `max(round)`가 자기 행만 본다(**동일 (issuer,billed) 경쟁만 lock으로 보호 — 정상**). seq counter 테이블은 글로벌 값이라 별도 정책 필요 → counter 테이블은 `SELECT/INSERT/UPDATE`를 authenticated에 허용하는 단순 정책(숫자 하나, 민감정보 없음) 또는 RPC를 `SECURITY DEFINER`로 두는 안 중 **INVOKER+별도 정책 우선**(DEFINER는 함수 내부 권한 검증 의무가 커짐).
- **서버 액션 주의**: 채번·생성 서버 액션은 **user-session client(`validateUserAction`)로만** 호출할 것 — `createAdminClient`(service_role)는 RLS를 우회하므로 쓰지 않는다(권한 경로 ①②③이 무의미해짐).

### 영역 3 — RLS (WBS 3.3, An_17 §3-4 확정안)

- **쓰기(INSERT/UPDATE/DELETE)**: `issuer_org_id = 내 org`만 (WITH CHECK 포함).
- **SELECT 3경로**: ① `issuer_org_id = 내 org`(전 상태) ② `billed_org_id = 내 org AND status IN ('ISSUED','CLOSED')`(DRAFT 비노출·읽기 전용) ③ Admin 감독(읽기 전용, 전 상태).
- **ADHOC(수기 화주)**: `billed_org_id`가 NULL이므로 경로 ② 미적용 → ①(발행자)·③(Admin 감독)만.

**Q3-1. 경로 ③ "자기 소속 대리점"의 정의** (이슈 문구 그대로 확정 필요)

| 안 | 내용 | 판정 |
|:--|:--|:--|
| **(C-a) role 기반 전체 대리점 (권장)** | `role IN ('ADMIN','ZENITH_SUPER_ADMIN') AND issuer_org.type='AGENCY'` → 모든 대리점 발행분 감독 | **권장** — 현행 감독 패턴과 일치(`shipper-invoices.ts:40` ADMIN 전체, `agency_shippers_admin_all` 정책, iss684 storage RLS의 ADMIN 전체). "소속"을 플랫폼 Admin=전체 대리점으로 해석 |
| (C-b) Master-Sub `parent_id` 한정 | ADMIN의 org이 Master Agency인 경우 자기 Sub-Agency 발행분만 | 기각 후보 — 로컬 DB `parent_id` 0건, Master Agency(#605)는 SNTL 전용 특수 케이스. 플랫폼 Admin에게는 대상 대리점이 정의 안 됨 |
| (C-c) `zen_agency_shippers` 연계 | — | 기각 — agency↔shipper 관계 테이블로 Admin 소속을 표현하는 구조가 없음 |

- **질문**: 이슈 문구 "자기 소속 대리점"이 (C-a)의 "전체 대리점"과 같은 의미인지 확인 요청. 다르면 대상 org을 정의해달라.

**Q3-2. 구현 형태**: SELECT 정책 3개(경로별 분리 — 어느 경로가 열렸는지 감사·디버깅이 쉬움, 정책 OR 결합은 Postgres 정책 체계상 자연스러움). 항목 테이블은 헤더 종속 SELECT 정책(`EXISTS (SELECT 1 FROM zen_billing_statements s WHERE s.id = statement_id AND <헤더 3경로>)`), 쓰기는 헤더 경로 ① + `s.status='DRAFT'` + 발행자 본인.
- 서버 액션 측: 타 생성자 상세 요청은 **미존재와 동일 응답**(An_17 §5-2) — RLS가 row를 안 돌려주므로 자연스럽게 달성, 별도 처리 불필요.

### 영역 4 — 상태 전이 제약 (WBS 범위 4번, "트리거 또는 RLS/제약 중 택1")

| 안 | 내용 | 판정 |
|:--|:--|:--|
| **(D-1) 트리거 (권장)** | ① `BEFORE UPDATE ON zen_billing_statements`: 상태 전이 화이트리스트 `DRAFT→ISSUED`, `ISSUED→CLOSED`, 동일 상태 허용(부분 컬럼 수정), 그 외 `RAISE` ② `BEFORE INSERT/UPDATE/DELETE ON items`: 헤더 `status<>'DRAFT'`면 거부 ③ `BEFORE DELETE ON 헤더`: `status<>'DRAFT'`면 거부 | **권장** — (a) `WITH CHECK`는 **NEW만 보므로 OLD→NEW 전이 자체를 표현할 수 없다**(DRAFT→CLOSED 직행을 막으려면 OLD 값이 필요한데 RLS는 못 본다). (b) service_role(관리 SQL·백필)에도 예외 없이 적용되는 유일한안. (c) 취소=삭제(헤더 DELETE DRAFT 한정)·발행 후 항목 변경 불가를 한곳에서 강제 |
| (D-2) RLS만으로 | UPDATE 정책 `USING(status='DRAFT') WITH CHECK(status IN ('DRAFT','ISSUED'))` 등 정책 페어로 전이 제한 | 기각 단독안 — 논리는 동작하나 정책 2중 페어가 어렵게 읽히고, **service_role 우회**, 관리 경로에서 깨지기 쉬움. RLS는 "누가"(접근), 트리거는 "언제"(상태 기계)로 분리하는 편이 명확 |
| (D-3) CHECK 제약만 | 값 집합 CHECK | 기각 — OLD를 못 봐서 전이 불가(현재 `status IN (...)` 값 집합 CHECK는 유지하되 전이는 불가) |

- **유지 보조**: `UNIQUE(order_id, tier)`(항목), `UNIQUE(statement_no)`, 차수 유일키, R11 CHECK, `SETTLED`류 상태 값 CHECK.
- **권장 조합(요약)**: D-1 트리거(전이·삭제·항목변경) + RLS(접근·경로) + UNIQUE/CHECK(값·유일성) — 3층 상호 보완.
