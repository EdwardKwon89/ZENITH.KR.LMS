### 영역 4 — 오더 `billing_status` 연동 (이슈 2번: "설계 의견에서 확정")

현행 `zen_orders.billing_status` (`PENDING`→`INVOICED`→`PAID`)는 레거시 `invoice-generator.ts:176`이 `INVOICED`로갱신. 신규 청구서와의 관계:

| 안 | 내용 | 판정 |
|:--|:--|:--|
| **(A) 발행 시 `INVOICED`, 입금확인 시 `PAID` 연동 (권장)** | `issueBillingStatement`에서 오더 일괄 UPDATE(`WHERE id IN (...) AND billing_status='PENDING'`), `confirmStatementPayment`에서 `PAID`. `cancelBillingStatement`(DRAFT)는 **연동 없음**(발행=확정 원칙과 일치) | **권장** — 레거시와 값이 동일한 개념(PENDING→INVOICED→PAID)이라 이중 청구 방지 화면(`billing_status` 필터)이 신규·레거시 공통으로 동작. 컷오버 이후 오더만 신규 대상이라 레거시 인보이스와 **같은 오더에서충돌하지 않음**(Q4 확정) |
| (B) 연동 없음 (`billing_status`는 레거시 전용) | 신규 청구서는 자체 `status`만 관리 | 기각 — `billing_status`로 "청구됨"을 가르는 화면·리포트가 신규 오더에서 무시됨 |
| (C) DRAFT 생성 시에도 `INVOICED` | — | 기각 — 발행=확정 원칙(R8) 위반, 취소 시 되돌리기 복잡 |

- **TOCTOU 방어**(코멘트 5번): 연동 UPDATE는 **조건부**(`WHERE id=ANY(...) AND billing_status='PENDING'`)로 원자 처리. 발행·취소·입금확인의 상태 전이는 서버 선(先)조회가 아니라 **조건부 UPDATE(`WHERE status='DRAFT'` 등)의 `rowCount` + DB 트리거·CHECK**로 확정(이중 방어). 0건이면 사유 분기(`already_closed` 등).

### 영역 6 — 동시성·부분 저장 없음 (DoD 2·3번)

- **동시 중복 담기**: `createBillingStatement`는 ① RPC `create_billing_statement`(헤더 원자 생성) → ② 항목 일괄 INSERT를 **한 트랜잭션**(`supabase.rpc`는 개별 트랜잭션이므로, 항목 INSERT 실패 시 헤더 rollback 위해 `DELETE`(DRAFT)로 보상하거나 **RPC 확장 대안** 제시 — 아래 Q-A). `23505` 발생 시 `order_already_inclusive`로 매핑하고 **부분 저장 0**을 보장.
- **상태 전이**: 조건부 UPDATE `rowCount=0` → 사유 분기(선조회 믿지 않음).

**Q-A (확인 요청)**: 항목 INSERT를헤더 생성과 **하나의 RPC로 묶을지**(설계 확장 — `add_billing_statement_items(statement_id, order_ids[])` 신규 RPC, 헤더 DRAFT 보증+항목 원자 INSERT+합계 갱신). **권장: 신규 RPC 안** — 보상 DELETE 로직보다 원자성이 명확하고, Task 4(S4 화면)의 "선택 오더 재검증"도 같은 RPC 안에서 처리 가능. 반대안은 서버 액션에서 트랜잭션 없이 이중 INSERT(부분 저장 리스크 주석 필요).

### 조건 4 — 금액 스냅샷 원천 표 (실측 2026-11-20, **2차 실측으로2건 정정**)

**원칙**: 클라이언트 금액은 **절대 사용하지 않는다** — DB 원천에서 읽는다.
**티어 규칙**(An_17 §3-3): `AGENCY_TO_SHIPPER`·`ADMIN_TO_SHIPPER` = 화주 대상 매출 / `ADMIN_TO_AGENCY` = 대리점 대상 매출.

| # | 1차 표(초안) | **정정 후** | 근거 |
|:-:|:--|:--|:--|
| 1 | 대리점 tier = `metadata.platform` 단일 원천 | **`metadata.agency` 우선 → platform 폴백** | 실측: `platform.totalSellingPrice`=419,574.846 ≠ 대리점 청구액 `agency.agencyCostPrice`=286,014.85. agency 4필드 합(200,340+61,771.5+23,903.346+0)=286,014.846≈`agencyCostPrice`. `ups-actual-cost.ts:205-206`와 `invoice-generator.ts:117-121` 모두 **agency 우선·platform 폴백**. `discountRate=0.4`가 기본운임에만 적용(200,340 = 333,900×0.6) |

- **화주 tier 원천 검증**: `zen_order_costs` 합(402,879.846) = `metadata.shipper` 4필드 합(317,205+61,771.5+23,903.346+0) **정확히 일치** → 두 원천 등가. `invoice-generator.ts:70`(`calculateTotalAmount(unbilledCosts)`)과 동일한 `zen_order_costs`를 채택(증감·조정 반영되는 원장).
- **기타 유형 누락 방지**: `other_charges`를 "NOT IN 3종"으로 정의 → `UPS_ACTUAL_ADJUSTMENT` 등 미래 유형도 `line_total`에 포함(금액 누락 0). `line_total`은 **항상 4개 합 = 전체 `is_revenue=true` 합** (불변식).
- **통화 가드**: `is_revenue=true` 행에 `currency<>'KRW'`가 있으면 생성 거부(`unsupported_cost_currency` → 서버에서 `generic` 매핑). 헤더 통화는 KRW 고정이라 무전환 합산은 금액 오염.
- **rounding**: `agencyCostPrice`(286,014.85)와 4필드 합(286,014.846)은 0.004 차이 — `line_total`은 **4필드 합**(불변식 우선)을 쓰고, 차이는 ±0.01로 문서화.
